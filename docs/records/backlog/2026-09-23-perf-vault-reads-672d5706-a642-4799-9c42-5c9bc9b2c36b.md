# Graph requests reuse one fresh vault read

## Product pass

The owner asked for the next measured performance improvement after PRs #1807 and #1808. A 5,000-document synthetic vault took roughly 133 ms to load once, but several read requests loaded it two or three times. Cold Git evidence dating was also measured; reducing its history window left an old cited path undated, so its semantics were preserved.

- Prior: 2026-08-17 (50), "Guard the bytes read, not the mtime number", remains standing. Every request still loads current bytes; write-time conflict checks and stable-file snapshot guards are untouched.
- Outcome: `orient`, with identical graph and uncertainty results available sooner. Evidence observed; internal reversible change; truth, transfer, agent-write, and human-correction boundaries unchanged. PO route: two-way solo.
- Recovery proof: given the same vault bytes, every affected query returns the same result while each document is opened only once per request. A same-mtime edit or deletion must appear on the next request, and selecting one project must not narrow whole-vault validation.
- PO run: `f24a7fcc-927b-42b8-87ca-13805ac13218`. Owner clarity and later-task reuse are unmeasured.

## Implementation

The compiled graph cache can return the documents it just loaded alongside the artifact. The cache still reloads files and checks content signatures on every request, including artifact cache hits; it does not retain the document array. Graph compilation, project scoping, validation, body-dependent queries, and meaning-readiness checks share that request's loaded documents. Standalone validation and write paths keep their existing fresh reads.

This is reuse of one document load, not an atomic snapshot of the whole filesystem. No public tool arguments, schemas, fields, scope limits, warnings, or write guards changed. Ontology inspection found that the existing compiled-cache and graph-query responsibilities remain accurate; no vault write was needed.

## Paired measurement

One process, the same 5,000-document fixture, warmed artifact cache, seven alternating-order samples per implementation, median handler time including JSON serialization. MCP startup and transport are excluded. The prior handler is retained outside the checkout for the comparison. Separate-process measurements showed large variation even in unchanged controls, so they were not used for the speedup claim.

| Operation | Before ms | After ms | Reduction |
|---|---:|---:|---:|
| Health | 530.48 | 386.68 | 27.1% |
| Agent brief | 773.83 | 497.35 | 35.7% |
| Growth plan | 329.52 | 198.71 | 39.7% |
| Maintenance plan | 478.25 | 353.39 | 26.1% |

Unchanged single-load controls remained approximately stable: overview 156/148 ms and node profile 146/142 ms. All six complete before/after responses matched, both as direct handler results and as captured MCP structured responses. The synthetic fixture has unqualified meaning and many findings; speed does not establish ontology quality, and those findings were not removed to obtain the result.

## Regression proof

- A real-file isolated-process test counts descriptor opens for eight query operations. Every request opens all five fixture documents exactly once, including a non-node document and a second project outside the selected scope.
- Same-mtime content edits, deletions, caller mutation isolation, full-vault validation in project-scoped briefs, and standalone validator freshness are verified.
- Deliberate duplicate growth reads, duplicate validation reads, project-only validation, and mtime-only cache signatures each turn the guards RED. The original implementation is restored after each probe and the focused suites return GREEN.
- `checks:changed` recommends both direct suites and `test:mcp:unit`; the existing MCP CI lane includes the new root-level test file. No extra command or CI policy was added.
