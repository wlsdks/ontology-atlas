### Addendum 2026-11-28 — the rest of the lean items

**Decision**: `postWriteMaintenance` is `{ nextAction, stepsAboutTouched }`, as the Rust writers already answer: one executable step, else the first judgement, and the count of steps about the nodes the write touched. The maintenance plan takes `touching` and scans up to 500 candidates per generator before it keeps the touched ones, so a step about a node just written is not lost behind steps about other nodes, and a cycle is a step about each node on it. Build-write `findings` use the same argument (row 74). A project source is fingerprinted as `inventory-v3`: for a repository the index blob ids (`ls-files --stage`) plus the bytes of only the files `status` reports changed; for a folder with no repository one walk of sizes and times. Names are NFC and ordered by code point. No file count bounds it, so the 16,000-file cut (`source-inventory-cap-16000`) no longer applies to the MCP probe.
**Why this approach**: two readings of "one next action" were weighed. Keeping the whole-vault plan and filtering its first 100 steps (the old way) made the answer depend on how much other work the vault had; asking the plan about the touched nodes makes a write cost the same on a vault of 100 nodes and of 10,000. For the fingerprint, hashing every file again (the old way, byte-compatible with the app) costs time and memory in the size of the repository; the index already holds a content id per tracked file, so only the changed files are read. Measured as the median of three runs on the second call: `connect_project_source` 940 to 490 ms on this repository (9,594 files), 727 to 329 ms on 50,000 tracked files and 1,016 to 431 ms on a 50,000-file folder; `finalize_project_meaning` 1,498 to 785, 971 to 795 and 1,114 to 766 ms; peak memory 300 to 291, 234 to 198 and 265 to 227 MB. `validate_vault` is unchanged (579 to 577 ms here): its cost is the vault. The probe alone takes 0.16 s on 50,000 tracked files and 0.22 s on the folder.
**`sourceReads` kept as is**: the citation grammar (`mcp/src/meaning/source-range-citation.mjs`) is `source:<path>#L<start>-L<end>@sha256:<64 hex>`, and a vault write accepts only that form as evidence. The pinned citation is what an agent copies into a body or an `evidence:` line, so it must carry its own hash to stay valid there; putting the hash once in a file header would make the agent assemble it, and a wrong assembly is refused only at write time. The cost is one 64-character hash per read of a file (three reads of one file spend 384 of 8,069 characters, 5 percent). The hash in a continuation call (`expectedSha256`) is a guard against the file changing between two reads, not a citation, and stays.
**Dissent**: the app still computes `inventory-v2` and stops at 16,000 files, so a receipt one side minted reads as changed on the other until the app's probe is ported; `source-inventory-bound.contract.test.ts` pins only what both still share (depth, hashed bytes, pruned names). A folder without Git is fingerprinted from sizes and times, so an edit that keeps both is not seen; a repository is exact.
**Rust**: `write_aftermath.rs` asks the plan for 5 steps and counts the steps it got, and the plan caps each generator at that limit before it keeps the touched nodes, so `stepsAboutTouched` never exceeds 5 and a step about a touched node can be dropped behind other nodes' steps. Node answers the full count, so `rename-concept`, `merge-concepts` and `safety/audit-lines-for-each-writer` differ at `stepsAboutTouched` until Rust scans 500 candidates when `touching` is set and reports the filtered total instead of the length of the cut list. `delete_concept` passes no slugs on both sides, so both answer `{ nextAction: null, stepsAboutTouched: 0 }`; neither names a step for the referrers a delete leaves, which `backlinks` lists.
**Falsifier**: a write on a vault with more than 100 steps outranking the touched node reports no step about it, or a source of more than 16,000 files is reported truncated.
