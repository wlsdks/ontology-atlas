## 2026-11-24 — The app owns the ACP adapter download; only the person's start of a conversation triggers it

**Why**: owner, 2026-11-24: in-app agents feel weak, and the first download of the pinned npx adapter (`acp-registry.json`) progressed only while the agent panel stayed open. The download ran as the first step of the session's own `npx` process, and unmounting the panel kills that process tree, so leaving mid-download threw the progress away and could leave a half-written `_npx` entry for the doctor's `npx-cache` check.
**Prior**: decision (89) and `surfaces.md` "Installing an agent tool for the user": downloads happen only on a person's action; Node and CLI installs are Rust-owned and outlive the settings sheet. `local-first.md`: no outbound transfer the person did not start.
**Decision**: Rust fetches the adapter into npx's own cache (`npx -y [--before] --package=<pinned spec> -- node --version`, `src-tauri/src/acp/install/adapter.rs`) on a thread the app owns, one per runtime; a second request waits on the one in flight. One moment triggers it, the one that already downloaded before this change: a chat panel starting a conversation (`acp_prepare_adapter`, awaited before `acp_start`). The doctor's `npx-cache` fix still only deletes a broken entry, and refuses while a fetch writes it. Nothing fetches at app launch, after an update, or on choosing a runtime in settings. Rust refuses the fetch for any runtime the session start refuses (`chat_eligible`), so the page cannot use it to install another registry package. The npx child gets the session's environment policy, a PATH without `node_modules/.bin`, its own process group, and dies with the app. Closing the panel never cancels the fetch; the reopened panel and the doctor read its state from the install progress event (`job: "adapter"`) and `acp_install_progress`. No new host: the same pinned spec and `--before` cutoff reach the same npm registry the session's npx used. This is not an "installing an agent tool for the user" install (`surfaces.md`): it is the session launch's existing download into npx's own cache, moved ahead of the session, so showing a command and an app-owned location do not apply.
**Dissent**: a prefetch at launch or right after a pinned-version bump would remove the wait entirely; it is new traffic the person did not start, so it needs its own owner decision.
**Falsifier**: a byte of the adapter downloads before a conversation start; a runtime outside `chat_eligible` fetches; an npx fetch survives the app's exit; leaving the panel mid-download stops the download; two npx downloads of one adapter run at once; a session start downloads the adapter itself after a finished fetch.
