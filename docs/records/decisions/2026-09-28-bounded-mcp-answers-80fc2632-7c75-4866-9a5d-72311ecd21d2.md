## 2026-09-28 — Large MCP answers are bounded by each tool's own default

**Why**: owner, 2026-09-27: keep the MCP server low on memory. At 12k nodes each brief embedded the whole 30 MB `validate_vault` report, a bare `compile_ontology` was 44 MB and an unlimited `find_evidence` 12.8 MB; each is sent twice and sets the server's peak.
**Prior**: extends 2026-08-14 "A large ontology list marks omissions and reads through to the end" (its paging shape) and 2026-08-14 (7) (counts plus a `nextCall`). 2026-08-17 (66) stands.
**Decision**: briefs keep whole-vault counts and every path drift but carry 20 problem files and a `validate_vault` `nextCall`; `validate_vault` pages by `offset`/`limit` (default 100) and its hint names the next call with the caller's `repoRoot` and `limit`; `compile_ontology` answers its summary unless `full: true` or a page argument; `find_evidence` returns 50 unless `limit` says otherwise. Each answer puts its page, hint or `nextCall` first. Text and `structuredContent` both stay.
**Dissent**: a generic 128 KiB cut in `ok()` would bound every tool at once; review found it cut write previews and receipts with dead-end hints and overwrote `read_source`'s own `truncated`, so each tool bounds itself instead.
**Falsifier**: an agent that reads a brief's 20 rows as the whole vault, a page walk that loses or repeats a file, or a tool that again answers tens of MB by default.
