## 2026-10-02 — The map draws a folder while it is still being read

**Why**: the owner asked on 2026-10-02 that a folder stop arriving all at once. Measured at 120 ms per native answer, a 10,000-document vault showed nothing for 77.7 s, because the map waited for the last file and the app paid one native call per file.
**Prior**: narrows the rule in `docs/ARCHITECTURE.md`, "Vault mode", item 7: destination content commits only after one local manifest is ready. That rule now holds for every destination, write, check and count except the map, which draws `partialManifest` while `status` is still `loading`.
**Decision**: the build reads the project, `domains/`, `capabilities/` and `elements/` before other documents; in a folder of 400 or more documents, once the read has run 0.2 s, it publishes what has arrived at most once a second, quartering a large subfolder only among the first three publishes. A smaller folder reads in well under a second and arrives whole, as before. Only the map opts in: it draws only documents already read, glides marks that move and keeps the overview framed; the INDEX says "reading N of M documents". The first part drops the previous folder's manifest and file handles, and writes are refused until the folder has loaded, so an edit can never land in the folder being left. The app reads 64 Markdown files per native call (`read_vault_text_files`), never under a dot folder. The finished manifest equals a build that publishes nothing.
**Dissent**: a vault that ignores the folder convention gets quarters of one flat folder instead of a domain-first reveal, and every publish rebuilds the map's world, so a slow read of a huge vault spends more main-thread time in total than one build would.
**Falsifier**: a person reads a partial map as the finished one (a missing node reported as absent, a check run on part of a folder), or a mark is seen to jump while documents arrive; then hold the map until the capabilities have arrived and publish nothing earlier.
