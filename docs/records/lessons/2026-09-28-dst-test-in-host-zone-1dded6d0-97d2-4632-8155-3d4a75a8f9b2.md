**Observed**: on main, `src/entities/library-round/model/round-record.test.ts` "a daylight-saving day keeps the wall clock" built its dates with `new Date(y, m, d, h, min)` in the host zone (Asia/Seoul here, UTC in CI), neither of which has a transition, and passed. The same `nextDueAt` compared with a brute-force wall-clock reference under ten pinned `TZ` values failed 8 of 136 cases in America/New_York alone: after 01:55 EDT on 2026-11-01 a five-minute round's next run was 07:00Z instead of 06:00Z (a 65-minute gap), and on 2026-03-08 a two-hour round ran at 03:00 and 05:00 EDT instead of 04:00. My first replacement then passed three hand-picked DST cases yet skipped 06:00 EDT for a six-hour round on the same spring day; only the reference comparison caught it.
**Cost**: unknown for the shipped defect; in this investigation one wrong rewrite and two extra probe runs.
**Suspected cause**: an assertion about wall-clock time that does not pin `process.env.TZ` tests whatever zone the machine has, and hand-picked cases cover only the transitions the author thought of.
**Proposed change**: rule — one line in `.claude/rules/testing.md`: a test of wall-clock or calendar math pins `process.env.TZ` to a zone with the transition it claims, restores it afterwards, and compares with a brute-force reference where that is cheap. `fix/automations-work-for-real` does this for `round-record.test.ts` (America/New_York, Europe/Berlin, America/Santiago).
