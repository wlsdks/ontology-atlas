## Why this direction

`ontology-atlas` should feel like a compact graph workbench, not a documentation
portal with a graph attached. The visual direction is still restrained: dark or
light neutral surfaces, one indigo accent, dense but readable controls, and no
decorative gradients. The product value comes from a stable task handoff over
the same local markdown graph:

- **Topology + INDEX** — overview, selection, path/focus, reachability, and
  source evidence.
- **Workshop** — one typed relation write at a time, backed by frontmatter or a
  read-only MCP packet.
- **Insights** — five maintenance questions with one active panel and a
  tab-scoped agent handoff.

The retired tree/ego hub and ERD Builder are not alternate modes. Headers,
cards, and navigation preserve the selected concept while moving between
Topology inspection, Workshop writing, Insights maintenance, and source docs.

## v2 — "Circuit × Constellation" (B2+) Visual Language

> Fidelity standard: `docs/prototypes/topology-b2plus.html` (owner-approved, the only fidelity source). Implementation standard: `src/widgets/topology-map-v2/` + `--topology-v2-*` / `--topology-chrome-*` tokens in `app/globals.css`. The entire expression architecture is in [`TOPOLOGY-V2-DESIGN.md`](./TOPOLOGY-V2-DESIGN.md). This section is the **working rulebook** for extending that language to pages outside topology — it is not marketing copy.

### v2 Language Definition — 6 Axes

1. **Machined surface.** All shapes/cards read like "machined parts" with a 1px stroke + neutral fill tier. Canvas nodes allow only one monochrome vertical sheen (`--topology-v2-node-sheen-tint` + blend `0.6`) — it dissolves in the far-field, and DOM cards do not simulate sheen (the ban on decorative gradients remains from v1).
2. **Engraved mono numerals.** Counts/aggregates use a mono font on a 1px dark shadow (`--topology-v2-numeral-shadow`) with a bright face (`--topology-v2-numeral-face`) — engraved, not printed. Numbers always point to actual data (node count · relationship count · census). Decorative numbers are forbidden.
3. **Kind = shape, not color.** project=hex plate · domain=square chip (pin-tick) · capability=circle · element=pad+via (drill hole). The primary channel for kind distinction is **shape**, and color only subtly shifts the fill/stroke brightness tier. Panel/card kind miniatures reuse the same `--topology-v2-node-*` tokens as the canvas. Do not revert to UI that distinguishes kind by color.
4. **Signal = State (power/pulse).** Indigo means "powered on" — fresh node stroke, powered dot (`--topology-v2-panel-power-on`), active highlight. Comet pulse means "current flowing" — live traversal of `depends` relationships (accelerated from ego, `--topology-v2-edge-pulse-speed[-ego]`). Stale uses dashed border + low-chroma surface. Do not use signal color if it does not explain the state.
5. **Calm chrome / fluid canvas boundary.** The canvas is fluid — spring camera, altitude crossfade (circuit ↔ constellation smoothstep), breathe. Chrome (panels/rails/pills) is static precision instrumentation — read as measurement tools rather than touch surfaces on 1920 desktops via `--topology-chrome-*` density (controls 32~36px, icons 11~12px, title 12px, eyebrow 9px). Fluid motion does not leak outside the canvas.
6. **Single indigo + single amber-hub exception.** Same as v1 charter. Amber (`--topology-v2-amber-hub`) is only for one hub ring. Introducing a second chromatic color like cyan has precedent in Guardian rejections (cyan second-color defect, TOPOLOGY-V2-DESIGN verdict a5) — do not retry.

### Page Rollout Application Rules

Rollout order: gateway → docs(`/docs` Source Vault)/ontology hub(`/ontology`) → projects(`/projects`, `/project/[slug]`)/insights(`/ontology/insights`) → download(`/download`).

**What to bring to pages** (global language):

| Token | Role | Value |

Since lint passed if `var(` was present in the value, it became a state where *only color was tokenized* and geometry was free. Within that were 2 light source inversions and 1 layer inversion (blur 90 > dialog 80). Now the gate (a check that automatically blocks violations) looks at **which token** (geometry allowlist), not `var(` presence — 23 → 0.

  Do not hand-write new drop-shadows in JSX. If a new role is truly needed,
  **submit a token creation PR first**.

### 1. Shape — kind is shape, not color

**Channel choice is itself part of the specification.** Kind uses shape rather
than color as its distinguishing visual variable. As Jacques Bertin argues in
*Sémiologie graphique* (1967), **hue cannot express order**
(`.claude/agents/design-infoviz.md`). This app already reserves hue for two
different meanings: **hierarchy** through the brightness/depth ladder (project
⊃ domain ⊃ capability ⊃ element; see "Map Ink Ladder" below), and
**state** through color itself (three signal tones plus power/pulse). Adding a
third hue meaning for the unordered category of kind would contaminate both
working channels, so kind is carried by shape.

| kind | shape | canvas source | DOM source |

|---|---|---|---|
| `project` | hex plate | `hexPoints()` → `bodyPoints()` (`render/node-shapes.ts`) | `<polygon>` (`shared/ui/topology-v2-kind-glyph.tsx`) |

| `domain` | square chip (4 pin-tick legs) | `squarePoints()` → `bodyPoints()` | `<rect>` |

| `capability` | circle (no shape deformation) | `bodyPoints()` → `null` (already a circle) | `<circle>` |

| `element` | square + center via-hole (drill hole) | `bodyPoints()` body + separate via arc in `draw()` | `<rect>` + center `<circle>` |


**Both gateways must render the same mapping** — merely listing it in the table isn't enough to enforce this (consistent with the principle "specs are enforced by lint"). Each file has only validated consistency within itself (`node-shapes.test.ts`, `topology-v2-kind-glyph.test.tsx`), meaning nothing checked whether the two files **shared** the same mapping. The contract test `tests/contract/node-kind-shape-parity.contract.test.ts` (added 2026-08-01) fills this gap: we broke one side's mapping with a probe to confirm failure (e.g., forcing it to draw domain silhouettes as circles is immediately caught).

Shapes converge to circles based on `farT` (far-distance progress) — once `FULL_CIRCLE_FAR_T = 0.985` is exceeded, they are always circles. Corner radii interpolate from `minCornerRadius`(kind-specific minimum corner ratio — e.g., project is 14% of the radius) to `r`(full circle) via `interpolateCornerRadius(minCornerRadius(kind, r), r, farT)` — this is a continuous morph, not a silhouette swap (`docs/TOPOLOGY-V2-DESIGN.md` §3.1).

Decorations (pin-tick, via-hole, double hairline) are material expressions rather than silhouettes and are drawn only under the radius-`farT` gate (fading at a distance). The threshold is defined by the top constant block in `node-shapes.ts` (`DOMAIN_PIN_MIN_HALF_EXTENT`, etc.) as the single source of truth — do not duplicate values in this document (duplication is the start of drift, Carbon).

The node icon set (geometry/lines, see "Personalization" section #21 below) never changes this mapping — only the render **style** (`glyphStyleDescriptor`) toggles between fill+sheen and stroke-only.

### 2. Radius — Fixed Ladder

| kind | world radius | token |

|---|---|---|
| project | 30 | `--topology-v2-radius-project` |
| domain | 17 | `--topology-v2-radius-domain` |
| capability | 11 | `--topology-v2-radius-capability` |
| element | 7 | `--topology-v2-radius-element` |

`radiusForKind()` (`ui/topology-world.ts`) is the single lookup point. The values themselves are a **design decision** enforcing a strict hierarchy, so lint/contract tests cannot judge them — changing them requires re-convergence at the same evidence level (45 rounds of research + systematic review) as described in the "Map Ink Ladder" section.

We correct the optical illusion where squares appear larger than circles by reducing their radius — `DOMAIN_HALF_EXTENT_RATIO = 0.86` (shape half-angle = 86% of circle radius), element is 92%. Even with the same `r`, a square's corner area is larger than a circle's, making it look optically inflated — this is an optical correction, so it remains a constant rather than a ramp (a list of stepped values), for the same reason we don't enforce spacing optical corrections (see "specs are enforced by lint" and "spacing is not enforced").

### 3. Size Scale — magnitudeScale (child count becomes size)

`computeMagnitudeScale(kind, childCount, maxChildCount, k)` (`ui/topology-world.ts`) is the single source:

```
scale = clamp(1, 1.4, 1 + k × (√childCount − 1) / √maxChildCount)
```

- **Only domain and capability are scaled.** Project usually has 1–a few per vault, making relative size comparison meaningless, and **element is defined as always a leaf**, so `childCount` is always 0 — the function filters out `kind !== "domain" && kind !== "capability"` first, immediately returning `1`(base). The answer to "why is leaf 1.0?" is this: leaves have no countable children.
- **`childCount ≤ 1` also uses base (1.0)** — the previous log compression reduced nodes below the median to *below* base, creating a false signal of "small node." Now it's always at least base, signaling only "this node is unusually large" and never "unusually small."
- **Why √?** — It's gentler than log, preventing excessive compression of gaps while still compressing large differences. The goal is to provide ranking cues ("which is larger"), not proportional claims like a bar chart (Shneiderman overview-first — detailed comparison is for after clicking).

  ⚠️ **2026-08-01 Measurement Correction**: The `--topology-v2-radius-magnitude-k` token comment in `app/globals.css` read "log compression" until just before writing this section — the actual implementation (`computeMagnitudeScale`) had already switched to **√ (square root)** compression, but the comment hadn't caught up. This is left here as an example of what happens when the same fact is written in two places (code comment + this doc): one gets fixed while the other silently remains wrong. The comment has now been corrected along with this discovery.
- **1.4 Upper Bound** — Ensures max/min stay within the same kind ladder even at a distance (e.g., a domain should never appear larger than a project, which would invert the hierarchy).
- `k = --topology-v2-radius-magnitude-k` (0.45, `app/globals.css`) — Scale intensity. Changing this recalculates all domain/capability node sizes, so 0.45 itself is a finalized design value (requires owner approval before arbitrary adjustment).
- **Different channel from badge numbers (§4)** — Size uses `childCount` (direct children only), while numbers use `descendantCount` (all descendants). "Large" and "high number" can yield different answers on the same screen — an intentional dual channel (preemptive size + readable number).
- Gate: `computeMagnitudeScale` describe block in `ui/topology-world.test.ts` — project/element invariant (=1), clamp bounds, base when `childCount ≤ 1`, defense for `maxChildCount`/`k = 0`.

### 4. Engraved Numbers — When and What to Count

`drawEngraved()` (`render/node-shapes.ts`) draws "engraved" numbers using a 1px dark shadow + light face (looking pressed in rather than printed). Display conditions require **all three** to be met:

1. **Kind is only project or domain** — capability/element never display (`showCount` in `topology-frame-draw.ts`).
2. **Screen radius exceeds `ENGRAVED_COUNT_MIN_RADIUS` (13px)** — prevents numbers from appearing larger than glyphs at a distance.
3. **`farT < 0.9`** — fades out upon entering far-distance (overview).

The number value is `node.count = descendantCount` (total descendants, a different channel from §3's `childCount`) — `ui/topology-world.ts`. Project numbers are drawn in amber (hub/Layer-0 tone), domain in neutral tone (`numeralTokens` branch inside `draw()`).

Gate: Display conditions (kind, radius, `farT`) are sourced from constants in `node-shapes.ts` and the `showCount` condition in `topology-frame-draw.ts`. There is **no** contract test yet to catch regression of literal values (13, 0.9) — left as technical debt (follow-up: export `ENGRAVED_COUNT_MIN_RADIUS` for a short snapshot unit test).

## Brand mark — "Hex Constellation" (candidate A, confirmed 2026-07-18)

> Source: `docs/prototypes/app-icon-concepts.html` (candidate A, 48px master + 20px thumbnail). Implementation: `src/shared/ui/brand-mark.tsx` (`BrandMark`).

The mark reuses the same shape vocabulary as the v2 kind glyph above instead of
inventing a new one: a **hexagon** (= project shape, §2.3 "kind = shape, not
color") with **six vertex nodes** (graph nodes) and **spokes** converging on a
**center hub** — the hub is stroked amber, the same single-exception amber
tone as the v2 hub ring (§2.3.6, `--color-status-warning` family /
`#d4b478`). Large it reads as a constellation graph; small it collapses to
the hexagon — the mark is never a separate pictogram bolted onto the product,
it's the same shape language shrunk to a badge.

**Two detail levels** (`BrandMarkProps.detail`):

- `"full"` (default) — spokes + six vertices + hexagon + amber hub. Use at
  ≥32px — nav rail avatars, in-app headers, marketing surfaces.
- `"compact"` — hexagon outline + amber hub only, spokes/vertices dropped.
  Use at ≤24px (favicon, macOS Dock at small sizes, dense chrome) where thin
  spokes would just be noise.

**Color contract**: lines and vertices use `currentColor` so a caller can tone
the mark via CSS `color` (e.g. dim it inside a disabled state) — this is the
one shared-UI SVG allowed to do that, because it is a monochrome brand glyph,
not a data mark. The amber hub is a fixed constant
(`BRAND_MARK_AMBER = '#d4b478'`) exported alongside the component, because it
carries fixed brand meaning (hub node) independent of surrounding text color.
Static, non-React SVG/PNG exports (`app/icon.svg`, macOS `.icns`/`.ico`) can't
inherit CSS `currentColor`, so those bake the same indigo (`#8b97ff`) +
`#d4b478` amber as literal fixed values — this is the one place hardcoded hex
is correct instead of a token reference, because the file has no DOM to read
tokens from.

## Top-tier Quality Bar

Ontology Atlas should feel like a designer-grade macOS workbench for a local
ontology, not a web dashboard that happens to run in a desktop shell. The target
is **Apple-level clarity and continuity** plus **Toss-level product finish**:
every action should feel calm, direct, and obviously useful, while still keeping
the restrained graph-workbench language that makes the product trustworthy for
developers and AI agents.

This bar changes how we judge UI work:

- **Action quality** — every primary control should answer "what happens next?"
  in the label, tooltip, aria label, and resulting state change. If a command
  writes or validates the graph, the next proof surface should be one click
  away.
- **Motion quality** — motion is a semantic contract, not decoration. Use it to
  confirm command feedback, preserve continuity between focused nodes, reveal
  staged changes, or explain graph-state transitions. Keep it fast,
  interruptible, transform/opacity-based, and fully compatible with
  `prefers-reduced-motion`.
- **Ontology expression** — visible UI should name the ontology handle it is
  operating on: kind, slug, relation type, proof target, path, or graph query
  contract. Avoid hiding the ontology behind generic document/editor language.
- **Agent usability** — screens that change the graph should expose copyable
  MCP/CLI proof packets or direct handoffs so Claude Code/Codex can verify the
  same state the human just changed.
- **Performance honesty** — graph DB-style affordances must show result
  contracts, limits, partial evidence, and cache/query readiness. A pretty graph
  without query evidence is not enough.

### Deemed unnecessary (and why)

- **W3C DTCG (Design Tokens Community Group) JSON export.** The first stable version came out in 2025.10, sponsored by over 24 organizations with a growing tool ecosystem — but the problem this standard solves is the **round-trip between Figma ↔ Style Dictionary ↔ code**. Creating new DTCG JSON would mean values are written in **two places** (`app/globals.css`) — exactly the pattern this document repeatedly rejected. When consumers arise (e.g., actual Figma library adoption), add a script to **generate** from `globals.css` (manually maintained second source of truth is prohibited, build-time derivation is allowed — pattern like `docs-vault:build`).
- **Component JSON manifests (Meta Astryx type).** This is an app-builder pattern for "agents picking and assembling components from a component library." This product is a single application where humans+agents directly edit TSX in the same repository, so it needs "rules to follow" not a "list of components to pick" — that role is already handled by `.claude/rules/design.md` + lint + contract tests. Creating a manifest would create a fourth place saying the same thing differently from those three.
- **Separate `DESIGN.md` (Google Labs format).** The problem this format solves (YAML tokens for machines + prose rationale for humans in one file) is already solved by this repository in other arrangements — tokens are in `app/globals.css` (CSS itself is a machine-parsable format), rationale is in this document (prose for humans). Adding a third file means three places to verify "are tokens really these values?" Since agents already read the repo directly, the benefit of separate manifests (reduced query costs) for remote agents doesn't apply here.
- **Component-specific "explicit anti-pattern" metadata fields.** Industry cases (Spotify Encore type) are problems for **libraries** with dozens to hundreds of components. The "anti-patterns" in this repository already exist in one place — the "Anti-AI Design Criteria" section (below) + `forbidden.md`. Scattering them per component creates a new drift surface itself.

### Three ambers, three rules (the recurring audit false-positive)

Every colour audit re-opens this, because a grep for "amber" returns three
unrelated families. They are governed by different rules, and a finding is only
a defect if it names the right one:

| Family | Value | Rule |
| --- | --- | --- |
| **Hub amber** | `--topology-v2-amber-hub` / `BRAND_MARK_AMBER` `#d4b478` | One hub ring + one Layer-0 container, plus two written exceptions (agent focus ring, `?recent=` spotlight). A third on screen is a defect. |
| **Brand mark** | the same `#d4b478` in the nav-rail logo | Not an expansion — it is the product's mark, one instance per route, never data. Written down here so audits stop re-filing it. |
| **Kind tone** | `capability` `rgba(211,159,73,.94)` (amber) · `element` `rgba(124,166,141,.94)` (eucalyptus) | A **data mark**. Allowed only where colour is the sole identity channel — the kind-census strip, map dots, tree chips. Composition bars whose segments are already identified by order + adjacent numerals use the app bar grammar (indigo primary + neutral + 1px seam) instead. Never a surface, rail, or callout. |
| **Footprint trail** | `--color-footprint-trail` `#e8c47a` (2026-07-29, added) | Deliberately a DIFFERENT value from hub amber, not an extension of it — same family, split value, so "center" (hub) and "walked" (trail) never collapse into one meaning. **Bar colour is neutral + one indigo.** Indigo marks the primary series only —
the leading row in a one-value ranking (`DomainCompositionGrid`), the capability
segment in a two-value composition (`DomainCapacityBar`). The boundary between
two segments is carried by a **1px seam** (a gap that lets the track colour
show through), not by hue: indigo against neutral measures 1.12:1, far under the
3:1 graphic threshold, so the separator has to be colour-independent — the route
WCAG 1.4.11 sanctions.

The earlier rule ("bar colour follows the number of series") granted every
two-series bar a licence for two chromatic data marks. Measured cost on

track, so it never separated by luminance, only by hue, and that hue axis
(orange↔green) is the one red-green colour deficiency (~8% of men) cannot
resolve. Order (capability always left), the unit word, and the adjacent
numerals were already carrying identity three times over; the colour was
duplicate ink.

#### Do not overlay Latin-only decorations on Korean (2026-07-26)

The owner read `What goes out`, `Sent records`, and `It's your choice to commit` with double spaces in the [AI Connection] panel. The i18n string contained only a single space — the gap was not between words but in the **space glyph**.

The cause is two Latin conventions being overlaid on Korean.

| Decoration | What it does in Latin | What it does in Korean |
|---|---|---|
| `uppercase` + wide tracking eyebrow | Uppercase subheading structure | No uppercase. **Only letter-spacing** expands |
| `font-mono` sentence | Signal that it's code/identifier | JetBrains Mono is a Latin subset, so Korean falls back, and **only spaces** remain as monospaced advances |

Rule:

- **Do not apply `font-mono` to Korean sentence text.** If a line mixes paths/identifiers
  with Korean, wrap **only the machine string** in a mono span
  (`<span class="font-mono">.ontology-atlas/llm-audit.jsonl</span> · commit choice …`).
- The **Korean placeholder** for mono input fields should revert to body font — the value is a machine string, but
  the prompt is not.
- Do not use mono/uppercase/wide-tracking eyebrows for Korean sentence subheadings.
  Provide hierarchy only through size and ink.
- Keep Latin eyebrows themselves (they are normal signals in English labels/tabs/legends). The prohibition is on
  **overlaying them on Korean**.

**Bilingual surfaces condition decorations by locale (2026-07-26 entry check E-10).** If the same
component renders both ko and en, removing decorations entirely is over-treatment —
the eyebrow is a normal signal in en. `useLatinEyebrow(tracking)` in `src/shared/lib/latin-eyebrow.ts` is the single source for this verdict:

```tsx
const eyebrow = useLatinEyebrow("tracking-[0.2em]");
<p className={`text-caption text-[color:var(--color-text-quaternary)] ${eyebrow}`}>
```

- ko → empty string (decoration 0). en → `font-mono uppercase tracking-…`.
- **Machine strings are exceptions** — monospace is preserved for glyphs like gauge numbers, folder paths, and shortcuts where width matters. Only the adjacent **Korean words** change.
- Unregistered locales are treated as non-Latin (it's costlier to apply incorrect decorations).
- Components rendered outside the intl provider cannot use this hook — instead of hiding via fallback, place a provider mock in tests (`useLocale: () => "ko"`).

Measured evidence (1512×950 dark, full getComputedStyle): the first screen's 7 ko instances had tracking
1.36~1.8px + mono fallback + uppercase overlaid on Korean → now 0 instances. en unchanged.

#### Labels do not touch node outline lines (2026-07-26 entry check E-4)

The baseline for canvas labels comes from **one place**: `render/labels.ts#resolveLabelBaselineY`. `draw()` and the bbox build in `topology-frame-draw.ts` use the same function — if they diverge, the measured box and the actually painted text will be placed at different positions.

- Label anchors use the **drawn** screen radius (including magnitudeScale · breathe · entrance ramp ·
  selection's 1.12 growth). Using the nominal radius causes names of large/selected nodes to fall inside the shape.
- Ensures minimum clearance (`LABEL_NODE_CLEARANCE` 3px) between the outline drawn **outside** the node disc (selection ring +6px) and the glyph. If only offsets are used, the glyph will pierce the ring as it grows upward from the baseline — this cannot be resolved at any zoom level (the font scales with it).
- Ego member/hover node discs are passed to the label placer as **reserved**
  (`NODE_DISC_LABEL_PRIORITY` = 1: selection/hover labels do not yield, only passive labels move aside). Reservations have an owner (`ownerId`) that exempts its own label.
- The order of yielding is **flip first, suppress later** — if the bottom is blocked, try the space above the node once; only drop the label if that is also blocked (preventing "nameless shape" recurrence).

### Map ink ladder — one depth axis, two others (2026-07-31)

Product of 45 rounds of map research + system stone verdict. **Structure is the contract, not values.**

**Starting point**: All **eight** edge/node strokes on the map failed WCAG 1.4.11 (3:1) —
the brightest project stroke was 2.78:1, the darkest contains-l2 was 1.59:1.
The hierarchy stone's physical measurement captured the same issue from a different angle: contains line peak luminance 14.4
vs background 13.3 is **effectively absent**, and the brightest thing on screen was not the connection line but
the summary chip (102.5). **The map's job is to show connections, yet connections were the blurriest.**

**Depth axis (`--topology-v2-ink-depth-*`)** — single source of truth. Node strokes and
containment edges are **drawing the same tree depth twice**, so they reference the same values:

| Row | Token | Contrast | Alias |
|---|---|---|---|
| leaf | `--topology-v2-ink-depth-leaf` | 3.22:1 | `node-stroke-element` · `edge-contains-l2` |
| mid | `--topology-v2-ink-depth-mid` | 3.42:1 | `node-stroke-capability` · `edge-contains` |
| top | `--topology-v2-ink-depth-top` | 3.96:1 | `node-stroke-domain` · `edge-contains-l0` |

Initially, I listed the two groups separately, and the third pair converged within a 0.02 contrast ratio **by chance**.
That’s luck, not a contract — if you fix one side, it drifts apart without any warning.
*"If a value is written in two places, the drift has already begun."* (Carbon).

**Outside the axis:**

- **`node-stroke-project`(4.63:1)** — One step on the depth axis. It has no corresponding containment
  edge (since there is no parent above the project), so it holds its own value. This is the
  brightest mark on this map.
- **`edge-depends`(3.61:1)** — Not a hierarchy but a relationship **category**. It is distinguished by a separate channel (dashed line + indigo tint) rather than a step on the lightness ladder. Therefore, it does **not impose an upper bound between ladders** like *"edges must be ≤ 80% of node strokes"* — that rule assumes the two ladders compete, but containment edges share the same axis as nodes, while depends is on a completely different axis, so they are not comparable. The only constraints are:
  **WCAG 3:1 or higher**, and **not exceeding the brightest mark (project)**.

**Chrome is darker than content** — the cluster chip rest is at the **bottom step** of the lamp
(`--topology-v2-cluster-chip-{border,ink}-rest`, 3.01/3.14:1). It is darker than any node but still respects the WCAG lower bound (it must not be unfindable as a control). **Not using indigo for rest is key** — indigo is this app’s single accent; if chrome used it constantly, it would compete with the user’s intended target. It wakes up to indigo on hover/focus.

**Gate**: `tests/contract/topology-ink-contrast.contract.test.ts` enforces ① the 3:1
lower bound, ② the order of the two ladders, ③ the **alias relationship itself** (not the value but the `var()` reference), ④
the out-of-axis rule for depends, ⑤ that chips are darker than any node, and ⑥ that gates do not degrade. Lint cannot catch this — it requires background color and WCAG formulas for judgment.

⚠️ **Deprecated rule**: During research, I invented *"edge contrast upper bound = node stroke × 0.8"*
but later deprecated it. Since WCAG only provides lower bounds, this was an invention of this study; after unifying the axes, it became clear that **the premise was wrong** (two expressions share the same axis, so there is no reason to suppress one by 20%). To revive it, you must first demonstrate why the two ladders are in a competitive relationship.

### Relief/Topology motion tokens

Motion is product feedback. Use these tokens for click focus, camera movement,
panel entry, drag settle, and focus confirmation before adding bespoke easing:

- `--topology-motion-focus-duration`: short focus confirmation.
- `--topology-motion-panel-duration`: panel/support chrome entry.
- `--topology-motion-camera-duration`: camera pan/zoom continuity.
- `--topology-motion-drag-settle-duration`: post-drag settle.
- `--topology-motion-ease-standard`: default topology state transition.
- `--topology-motion-ease-out`: landing/settle transition.

New motion must name what it explains: selection, camera relocation, drag
movement, path construction, composer blocking, or command feedback. Motion
that only makes the screen feel busy fails the design system.

### Motion Syntax (usability motion family, Phase 3 2026-07-25)

The usability motion for "verifying meaning" in the map contextual editor and insights (`/ontology/insights`) is built only on the **single duration/easing family** below. Use only transform/opacity; glow, bounce-loop, and ambient loops are prohibited.
3-step ramps are ≤240ms (above that, only **exception tokens with a name and reason** — currently 2:
`--agent-panel-reflow-duration` 260ms panel reflow · `--overlay-spring-response`
300ms overlay spring. Both have critical damping so their physics are correct; what was misaligned was not the code but this sentence).
`prefers-reduced-motion` is immediately neutralized by the global rule in the `app/globals.css` base layer.

- `--motion-fast: 120ms` — **Verification**. Confirming a state that has already occurred (hover/focus/color/
  rotation/chip crossfade/tab content crossfade/picker origin scale).
- `--motion-base: 180ms` — **Movement**. Surfaces changing position (popovers/panels/cards/
  backdrops/docking entrance/exits). Matches Chrome's 180ms rhythm.
- `--motion-settle: 240ms` — **Settling**. The signature that something is done (satellite repositioning (FLIP)·
  commit convergence/completion linger).
- `--motion-ease: cubic-bezier(0.25,0.1,0.25,1)` — The common easing for the three above.
- `--topology-motion-camera/drag-settle: 420/720ms` — **Map canvas only**
  continuity. Referencing this from a DOM surface is a defect.

#### Choose by usage, not value — and don't use classes if it's the default (2026-07-27)

The ramp existed for a long time, but only one component referenced it. The cause was not taste but
**plumbing**: over 500 `transition-*` utilities were running on Tailwind's `--default-transition-duration` (factory default 150ms) and the default curve, and among the 30 scattered `duration-<n>` literals in the code, 12 had manually re-typed that factory value — a number no one ever chose effectively became the app's default motion.

So we swapped the default duration/easing in `@theme` for ramp tokens. Result:

- **Don't use duration classes if it's the default.** Unspecified transitions automatically
  become `--motion-fast` + `--motion-ease`. Over 500 places that didn't change a single class
  now ride the ramp.
- **Conversely, specifying means "this is not verification."** Where surfaces
  appear or disappear, **specify `--motion-base` and write the reason next to it** — in this replacement, the help popover, "Back to Top" button, and 3 map internal entry buttons fell here (leaving them to default would cause flicker instead of fade).
- **Elements receiving ramp duration go with the same family easing.** Swapping only duration
  leaves half of the "common easing for the three" family definition unkept.
- **Writing numbers directly is blocked by lint** (`no-restricted-syntax`, ratchet mirror).
  Map-specific spots using `--topology-motion-*` remain as-is.

Empirical measurement (1512×950 dark, headless Chromium, rAF value-ramp sampling) — how this change altered the ramp's shape: Document tree row hover changed from `0.15s cubic-bezier(0.4,0,0.2,1)` (first frame 2.5% · peak 4th · ramp width 108ms) to `0.12s
cubic-bezier(0.25,0.1,0.25,1)` (first frame 15.4% · peak 2nd · ramp width 92ms). The total displacement is the same, only the time distribution shifted forward — not near the pop threshold (70%), but improved toward the "instant response" (response visible in the first frame) discipline.

#### Motion budget goes to the protagonist (2026-07-27)

The family above defines "how much," this section defines "for whom." It's a principle derived from empirical measurement: When clicking an INDEX row, the concept popover (the object the user summoned) reaches 88.8% of the luminance ramp in the first frame via hard cut, while the background map ego focus received 100ms easing — and the two stages were misaligned by 250ms, running separately. The motion budget was spent on the background, not the protagonist.

1. **The protagonist gets it first.** When one input changes multiple surfaces, the transition belongs to the attention winner designated by the Design Guardian verdict. If the winner is a hard cut (first frame delta share >70%) and the background uses easing, that's a defect. Both being instant response (hard cut) is allowed — what's prohibited is inverted allocation, not restraint.
2. **One input = one event.** Stages spawned by the same input start in the same frame.
   If the start difference exceeds `--motion-fast`, humans perceive it as two separate events.
   Stagger only when showing causality (cause first); intervals ≤ `--motion-fast`.
3. **Verdicts via measurement.** Not screenshots, but frames — measure and compare the first frame share of the winner ROI and background ROI. This principle cannot be caught by lint (elements without transitions have no literals, so all value rules pass integrity checks).
   So the gate is the Motion item in the Guardian verdict: a verdict that can't answer with the winner's transition token name is incomplete.

Position relative to existing disciplines: "Exit via the path entered" (direction symmetry) · "Instant response" (first frame
33ms) · "Interruptible" · "Not turning off but equivalent" (reduced-motion) are rules **within a single surface**; these principles are rules for **allocation between surfaces**. Translated Apple HIG's purposeful motion and Tufte's ink budget (emphasis ink goes where information is greatest) into this app's syntax.

#### What exhaustive measurement taught us (2026-07-28)

By remeasuring the full screen, we learned **three facts that supersede the principles above**. All three are of the type "written correctly in rules but not actually enforced," so they are guarded by contract tests, not documentation.

**① Exit plays forward under its own name.** Exit reversing the entrance keyframe via `reverse` **does not play where only classes change on the same element.** CSS animations do not restart if `animation-name` remains the same, even if duration/direction change; since the start time is unchanged, an already-finished animation interpreted upon meeting `reverse` + `both` jumps immediately to the "post-end" state, showing the **end state of reverse playback instantly**.
Node popover close empirical: opacity `1 → 0` in **1 frame**, then only transform
`1 → 0.9877 → 0.9829 → 0.9804` — **the already invisible element shrinks slowly.**
Looks correct when read, and duration/easing are all tokens so value rules pass integrity checks.
Gate: `tests/contract/exit-motion-restart.contract.test.ts`.

**② `!important` reverses layer order — write equivalents within the same layer.**
The global reduced-motion kill rule (`*`, specificity 0,0,0) lives inside `@layer base`.
Writing equivalents **outside the layer** loses even with specificity (0,3,0):
between important declarations, layer order is inverted, so the one inside the layer wins. When toast equivalents were written at the end of the file, the computed value remained `0.01ms` (verified empirically). **Even if a rule exists, wrong placement means it's as if it doesn't.**

**③ Don't attach movement curves to opacity-only classes.** `.map-overlay-in`
only changes opacity but rode the movement expo curve (`--topology-motion-ease-out`), which hits 47% in the first frame (empirical 45.9%) — a large surface effectively turned on via hard cut. `.topology-chrome-in` is the other half of what we learned on 2026-07-27: "brightness and movement must not share curves." Without a movement axis, what remains is brightness's curve, i.e., the app-wide ramp (`--motion-ease`). Ramp width intact, first frame share drops from 45.9% → 16.1%.

**Frequency eats budget.** Surfaces triggered by hover/focus are encountered dozens of times a day, so objectively fast curves feel slow at that frequency. The answer is curve adjustment, not budget reduction: high-frequency surfaces use `0~--motion-fast`; movement/settling ramps belong to events happening a few times a day (mode switches/surface replacements/commit convergence). This discipline isn't enforced by md but by the shared selector array in `eslint.config.mjs` — hover/focus variants and movement/settling durations coexisting in the same className string are caught.

**Swap takes two frames.** Where two surfaces alternate occupying the same spot (INDEX collapse ↔
expand, settings sheet open ↔ close), if only the arriving surface gets entrance syntax, the user's target object gets 0 frames while the background (mere result) gets 200ms — structurally violating verdict①. `src/shared/lib/use-presence.ts`'s `usePanelPresence` /
`useSurfaceSwap` capture the frames they emit; the departing side is immediately neutralized via `inert` +
`pointer-events-none`. Exit windows share a single `EXIT_WINDOW_MS` — varying per surface recreates the defect.

**Crossfade must wrap reflow.** If only content fades but container height changes in 1 frame, text bleeds and boxes jump (insights tab empirical: height 878.5 → 605px, full document 246px jump). `useSwapHeight` measures the height **just before** replacement in the handler (if measured in effect, it's already the new layout so transitions always go from self to self), transitions to the empirically measured new height in one step, then returns to `auto`.
Height is a jittering axis so don't apply it for reduced-motion users.

**WCAG 2.2 §2.3.3 exceptions are real exceptions.** The standard explicitly excludes **user-initiated** movement (scroll/pan/pinch). While the canvas camera's reduced-motion snap cut wheel/pinch/pan, for reduced-motion users this meant the **entire viewport instantly jumped in one frame** — worse than the intended easing and removing even clues to "where did I go." Snap applies only to **app-initiated movement** (ego dive/fit/auto-align).

#### List row expansion — exit via the path entered (2026-07-26)

The canonical contract for the surface where an inline card opens upon row click ([AI Connection] vendor list).

- **One surface, two states.** Drawing different rows per state (replacement) leaves nothing to transition.

  different curves per direction. If it simply vanishes without folding, "Cancel" reads as
  "something went wrong" rather than "cancelled" — because the screen lacks clues to distinguish
  whether the disappearance was intentional or a bug.
- **Height transitions in px.** `height: auto` does not interpolate,
  and `grid-template-rows: 0fr↔1fr` only handles open/close, failing to support **content swap** (input form →
  registered action). When the consumer continuously writes actual content height via ResizeObserver,
  open/close/swap/reflow converge into a single mechanism.
- **Siblings yielding space signifies "these three are siblings."** If the expanded row's height
  grows continuously, the pushing down of subsequent rows is also continuous. Since the parent dialog's height
  follows the same curve, expansion reads as "growth" rather than "jitter."
- **duration**: Height `--motion-base` (180ms), content opacity/2px `--motion-fast`
  (120ms). Content is one step faster — on open, space appears first then text enters;
  on close, text clears first so the empty box doesn't appear to close.
- **JS does not replicate ms.** The exit unmount timer reads `--motion-base` via
  `getComputedStyle` (cached once at module level).
- **`prefers-reduced-motion` provides an equivalent rather than disabling it.** By overriding the global rule
  (`transition-duration: 0.01ms !important`) only on this surface,
  we remove shaking axes (height·translate) but keep non-shaking ones (opacity 120ms). This is because motion in this interaction is **evidence of causality** — a completely static screen
  cannot distinguish whether something disappeared because I clicked "Cancel" or because the app broke. The override rule must appear **later in source order** than the global block to win (if the order is reversed, it silently fails).
- **Accessibility**: It remains in the DOM during folding (≈180ms), so the detail area becomes
  `inert` immediately upon closing — invisible input fields do not remain in tab order/screen reader scope. We do not pay accessibility costs for exit motion.
- **Undo happens on that frame.** "Cancel", header toggle, and Esc converge into a **single function**, avoiding confirmation dialogs (confirmation is excessive for discarding an unentered state). Even with entered content, it discards quietly — losing it is just a matter of pasting again, and this card's confirmation budget is already spent by the [Delete] 2-step confirmation.


### The reduced-motion equivalent is a list, and tests enforce that list (2026-07-26)

The above contract ("providing an equivalent rather than disabling") existed **only in documentation** for a while. The only selector actually enforcing it was `.ai-row-disclosure`; other surfaces were hard-cut by the global rule (`animation-duration: 0.01ms !important`). Frame measurement: Settings sheet 150ms easing → **98.9% of total delta in 1 frame**, Insights tab transition 150ms → 1 frame. Writing specs only in documentation does not ensure compliance.

Now, **the surface requiring an equivalent is a list**, and `tests/contract/reduced-motion-equivalent.contract.test.ts` blocks deviations between that list and globals.css. Rule set:

2. **Crossfade types reclaim time** — `.insights-tab-crossfade` ·

   `.app-settings-panel-in` · `.topology-chrome-in` / `-out` ·

4. **The override block must appear later in source order than the global block.** If it appears first, it silently fails.
5. **No literal ms rewrites.** Equivalents reclaim time only via tokens (the gate checks this).

### Tokenization Contract For Relief/Topology

Relief/Topology is not allowed to rely on "looks better" CSS. A visual value is
valid only when it is a named workbench decision, an ontology-reading decision,
or a verified interaction decision.

Use named `--topology-*` tokens or add a documented token before changing:

- panel width, reserved map space, padding, radius, border, surface, shadow, and
  z-order intent;
- relation label width, selected relation card density, chip rhythm, footer
  height, disclosure thresholds, and proof row layout;
- dim/scrim treatment for a blocking composer, modal, destructive confirm, or
  write surface;
- camera, focus, panel, drag, path, composer, and reduced-motion durations or
  easing;
- MCP/CLI handoff markers that prove the selected fact, evidence, quality, and
  next action stay visible.

Relation-label handoff state is aggregated on the skeleton-cards root with
`data-relation-label-handoff-contract="label-level-mcp-cli-fallback"`. Every map
label hit target must expose its gate, primary MCP action, CLI fallback command,
fact route, quality, and evidence; when a map label is selected, the root also
mirrors the selected label's handoff state so installed-app WebView evidence can
prove the label is an actionable ontology fact, not just a decorative badge.

Relation-label geometry is also a frame-level contract. The skeleton-cards root
must expose `data-relation-label-geometry-contract="frame-positioned-hit-targets"`
with after-render expected/ready/pending counts, so a visible scan label is
proved to have real viewport-clamped hit-target geometry before the user opens a
relation card.

Each new topology token needs:

- **product reason**: the user problem it reduces, such as overlap, unclear
  current action, unreadable relation evidence, or untrustworthy handoff;
- **state/layer**: map, support panel, focus/path, transient, blocking
  composer, or utility chrome;
- **responsive fallback**: compact, 14-inch fullscreen, 1920x1080, and
  2560x1440 behavior;
- **WebView/test marker**: deterministic evidence that the token is active and
  the relevant overlap/transient count remains acceptable.

Treat W3C/DTCG-style design tokens as the principle: design decisions should be
portable, named, inspectable, and testable across tools. This repo does not
copy third-party component skins, palettes, layouts, screenshots, assets, or
animation signatures.

### Touch & tablet responsive contract (2026-07-23, Responsive Audit Round)

Width breakpoints alone cannot express "tablet = touch" — a 1024px display could be a fine-pointer laptop or a coarse-pointer 12.9" iPad. Thus, the touch axis is a **separate contract**:

- **`--touch-target-min: 44px`** (`:root`) + **`@media (pointer: coarse)`**
  block serve as the single source. In coarse mode, `--app-nav-rail-tile-height` (32→44) ·
  `--topology-chrome-control-height` (clamp 32–36→44) ·
  `--topology-shortcut-sheet-close-size` are promoted to 44px. Fine-pointer retains density. No dark/single/color changes — only height/Hit area.
- **Bottom tab bar reservation** — For `<lg` where BottomTabBar exists, surfaces anchored to the bottom or having scroll ends must subtract/pad `--topology-mobile-bottom-tab-reserve`
  (56px + safe-area). Application points: expanded INDEX (`--topology-index-bottom-inset`) · bottom-right gauge
  (`--topology-relation-legend-bottom-inset`, bottom-specific separate token) · datasheet max-height (`--topology-v2-panel-bottom-reserve` single knob) · content page main `max-lg` bottom padding. **"Blocked by tab bar behind it is a defect"** — when creating new bottom-anchored surfaces, contract from this reservation.
- **`<md` expanded INDEX = full-bleed sheet** — `--topology-index-width` switches to `calc(100vw - 2 * var(--topology-index-inset))` at `<md`. Narrow screens use "one main view at a time": expand for sheet (map is context), collapse for full map. The boundary shares md (768) with GlobalSearch's sheet↔floating split — sheet-like surfaces share this boundary.
- **Honest degradation** — Do not force desktop workbench (macOS app window) surfaces (e.g., Builder 3-pane) into tablet widths. The Builder canvas gate is lg (1024)+; below that, tree editing + topology fallback is correct.

### Shell body slot — No-compression contract (2026-07-27)

**Scroll containers do not compress their children.** The shell (`AppShell`) owns viewport height, and the body slot scrolls; that slot is a flex column. Page roots use `min-h-full` to fill the slot, and this **explicit min-height overrides the flex item's automatic minimum size (= content height)**. Thus, when content exceeds viewport height, flex shrinks the page box to viewport height, causing content to overflow visibly — scrolling works, but **the bottom reservation declared by the page is trapped at the shrunk box bottom**.

Measured (at defect time): Download's last line sat exactly on the viewport bottom (0px margin),
and at 768px, the project detail's last line went **17px behind** the bottom tab bar (project list had 9px margin). The touch contract's "blocked by tab bar is a defect" reappeared in this form.

The prescription is **the shell declares it once** — direct children of the body slot are not compressed.
Forcing pages to remember `shrink-0` actually failed: after fixing one screen, the same defect persisted across four sibling routes (project list · project detail · insights · download). The structure pages must remember disappears on the next screen.

- Growing (`grow`) remains unchanged, so vertical centering of short content is **unaffected** (measured: top/bottom margins of centered box 415/415px, identical before/after prescription · screenshot bytes identical).
- The gate has two layers — `src/app/providers/AppShell.test.tsx` (prescription in place) + `tests/e2e/scroll-end-gap.spec.ts` (measures scroll end margin/tab bar occlusion via **actual layout**). jsdom does not perform layout, so it cannot see pixels.

`/git` (history) is a destination where **form splits into state**. Since dimensions, not code, support this split, all values are tokens.

|---|---|---|
| `--git-setup-measure` | 520px | Single task column width before connection (no web/folder, before recording starts) |

**Three contracts matter more than values.**

## Product Surface Hierarchy

Operational pages should expose intent before visual flourish:

1. **Primary task** — what the user can do on this screen now.
2. **Graph evidence** — node count, relation count, warnings, health, or query
   packet readiness.
3. **Next graph action** — Workshop for a frontmatter-backed write, Insights
   for maintenance, or Topology for spatial/path inspection.

Avoid making large explanatory panels the first thing users read. Prefer compact
action and handoff strips that name a concrete destination (`Check in map`,
`Edit relation`, `Concept doc`, `Copy next action`) and why it is useful. The retired
`Browse / Write / Query` cards, tree/ego hub, ERD Builder rails, and query
cockpit are not current chrome and must not be revived by documentation or
design guards.

Topology is the browse and decision surface. Its INDEX panel may project the
project → domain → capability → element hierarchy, but the canvas and
datasheet keep typed relations, evidence, and impact visible. Selecting a row
or node must preserve one canonical graph handle across map focus, detail,
Workshop deep-link, and source-document handoff. `/ontology` is only a
compatibility redirect to `/topology?index=expanded`; do not design a second
ontology hub behind it.

Workshop is the write surface. The center card plus fixed compass bearings
explain the current node and allowed relation directions; empty line-art
sockets invite one relation at a time. A writable vault lands real
frontmatter, while a read-only vault produces an MCP packet. Completion is the
center-card border and plain progress caption, not game reward, glow, loot, or
a hidden draft canvas. `/ontology/edit` is only a compatibility redirect to
this surface.

Insights is a maintenance board, not a generic analytics dashboard. Its exact
five questions are **Do next / Composition / Connections / Boundaries /
Freshness**. `?tab=` restores the selected question, `TabBar` exposes one
selected tab, and only the matching `tabpanel` is visible. The first viewport
should answer the selected question with real graph data; the bottom handoff
row copies the matching MCP/CLI action without making raw query syntax the
visual winner. A fixed three-tab dashboard, reader-persona lanes, or a large
query cockpit is retired structure.

Source/setup surfaces should expose the vault execution contract before setup
actions. Use compact `Files` / `Graph` / `Agent` cells to show that local
markdown remains the source of truth, frontmatter compiles into graph/query
surfaces, and MCP agents read the same vault. Action cards can follow, but the
first native-app entry must make the ontology workbench contract clearer than
the document-editor mechanics. The `Agent` cell should expose a copyable graph
DB runtime gate, so Source Vault can prove the same read-first agent loop
without sending the user to a deeper panel first. Its visible replay markers
should name `relation_name_parity` and `pattern_walk` / `project_map`, so the
source route reads as the start of graph verification rather than a document
reader with an agent button.
The global entry label and page header for `/docs` should say `Source` /
`Source Vault`, not `Docs`, because that route is the local markdown source and
agent setup surface for the graph. First-viewport counts and vault badges should
say `source records` / `records`, not `docs`. Keep `document` language for
individual markdown files and evidence rows, but avoid making the route identity
read like a documentation portal. Palette groups, search sections, empty-state
prompts, and tree navigation labels should say `Source records` / `Source tree`
when they name the surface rather than one specific markdown file.

## Anti-AI Design Criteria

Anti-AI design does not mean colorless UI. It means every visual decision has a
job that a local-first ontology workbench needs, and nothing is added just to
look generated, glossy, or broadly SaaS-like.

Apply these checks before shipping ontology surfaces:

- **Color is a keyed data mark, not atmosphere.** Kind color may identify
  `project` / `domain` / `capability` / `element` / `unknown`, but the surface
  must also show a label, icon, size, position, or legend. This follows WCAG
  2.2 SC 1.4.1 and Apple HIG color guidance: do not rely on color alone.
- **Color area stays proportional to evidence value.** Graph marks can use
  high-contrast fills because they are small data points; panels and cards use
  neutral surfaces, compact swatches / markers, and low-alpha borders. Avoid
  full-height colored rails inside detail cards; they read as decorative
  generated-callout chrome before they explain the data.
- **Qualitative, not theatrical.** Kind colors are nominal categories, so they
  use a quiet qualitative palette in the ColorBrewer sense. Avoid neon yellow,
  magenta, or over-saturated "AI dashboard" tones when label/icon/shape can do
  the separation work.
- **No generated-gloss signals.** Decorative gradients, glass blur, glow rings,
  aurora backgrounds, oversized rounded cards, and scale-hover motion are
  regressions unless a specific native-system state requires them.
- **Craft is verified in small contracts.** The design drift guard must catch
  forbidden patterns, focused tests must lock role labels and tone attributes,
  and browser/native verification must prove the UI reads as a workbench rather
  than a decorative demo.
- **No floating-box soup.** A screen with several unrelated cards, popovers,
  prompts, minimaps, HUD buttons, and inspectors visible at the same visual
  weight is not "rich"; it is an attention failure. One surface owns the
  current action, support surfaces stay visibly weaker, and blocking surfaces
  dim or suppress the rest.
- **No stacked transient UI.** Popovers, context menus, hover previews, and
  selected cards may not cascade as unrelated layers. Opening a new transient
  surface closes the previous unrelated one; opening a composer/modal demotes
  or closes transient surfaces and blocks parent-map interaction.
- **No tokenless positioning.** Panel width, radius, padding, shadow, elevation,
  z-order intent, and topology motion must use named tokens or marker-backed
  contracts. One-off `clamp(...)`, shadow, or easing values in JSX are treated
  as design debt unless the same change adds a token and verifier.
- **No modal without modality.** A write composer, destructive confirm, or
  decision dialog must visibly separate itself from the map through a dim,
  scrim, or blocked interaction state. If the background still appears equally
  actionable, the modal/composer fails.
- **No elevation noise.** More shadow does not mean more hierarchy. Elevation
  must describe map/support/focus/transient/blocking layer order consistently
  (dark theme only — light mode was retired 2026-07-19).

## Arrows carry information or they don't ship

Owner verdict, 2026-07-26, on seeing `Open from map →`:

> *"I don't like arrows next to text like that? It feels AI-ish."*

A trailing arrow after a link label adds no information. The label already says
where you're going, and the control already looks like a control. What the arrow
actually signals is *generated marketing chrome* — it's the visual tic of a
landing page that wants you to click something. On a workbench where the same
label appears a dozen times, it becomes noise a dozen times over.

**The rule is not "no arrows."** It's that an arrow must be carrying something
the words aren't:

| Allowed — the arrow *is* the data | Forbidden — the arrow is decoration |
| --- | --- |
| `{source} → {target}` — a path between two nodes | `Open Document →` |
| `Old → Recent` — an ordering | `Details →` |
| `Settings → Developer` — a menu path to follow | `View Details` |
| `Click TOC → jump to location` — cause and effect | label + trailing `ArrowRight` icon |
| Leading `↗` on a link that **leaves the app** (`target="_blank"`, an external deeplink) — it warns before the click | Trailing `↗` on in-app navigation |
| `ChevronRight`/`ChevronDown` as a disclosure state, or prev/next on a carousel | |

The test: **remove the arrow and read the label aloud. If nothing was lost, it
was decoration.**

### The gate has to reach the markup, not just the strings

`tests/contract/label-decoration.contract.test.ts` scans three things now, and
the third one was added because the first two were not enough:

1. every `messages/*.json` string, for a trailing arrow;
2. a bare `↗` in JSX, unless the element declares `data-external-link-marker`;
3. **a lone arrow element that sits at the end of a label** — matched by what
   follows it, not by which glyph it is.

(3) exists because the rule shipped on 2026-07-26 exempted `→` wholesale, on the
grounds that every standalone `→` in this repo was an infix data arrow. One day
later the workshop's primary save button read `Confirm and Save <span>→</span>` —
the repo that wrote the rule broke it, under its own exemption. **A rule whose
range is too short fails exactly like no rule at all.**

The exemption is gone; the discrimination moved to position. An arrow element
whose next non-whitespace sibling is the parent's closing tag is trailing
(decoration); anything else after it means the arrow sits between two things
(data). Measured before enabling, as `.claude/rules/design.md` requires: 3
trailing (all the same save-button family) and 7 infix across `src` + `app`.

## Dimensional regularity — when content length varies

Owner verdict, 2026-07-26, on a card grid whose rows didn't line up:

> *"The box sizes don't match? It doesn't look clean, it looks crooked… I prefer neatness."*

This is the recurring failure mode of a data-driven UI: the layout is regular in
the code and irregular on screen, because each card's height is decided by how
many words its content happened to have. A grid only reads as a grid when the
eye can find a repeating rhythm; content-driven height destroys that rhythm
without anyone having chosen it.

**The principle: the container's dimensions are a design decision, not a
byproduct of its contents.** Concretely:

- **Fix the anatomy, not just the box.** A card in a repeating set has the same
  named slots in the same order — head / measure / list / foot. A slot that is
  sometimes absent is worse than a slot that is sometimes empty, because absence
  moves everything below it.
- **Reserve the optional clause's space.** If a caption is sometimes
  `2 elements` and sometimes `2 elements · 1 more competency`, the caption line still
  occupies one line either way. Do not let an optional clause change the card's
  height.
- **Truncate list slots to a fixed count.** Show N items and a remainder
  caption — never "however many fit." N is a design decision made once.
- **Equalize rows, not just columns.** CSS Grid stretches items within a row by
  default, so cards in the same row already match; rows do not match each other.
  When the set is meant to read as one field, make the row height uniform.
- **Truncation is a layout tool, not a failure.** Long titles clamp; they do not
  get to reflow the grid. Pair every clamp with the full value on hover/focus or
  in the detail surface, so nothing is actually lost.

The cost is real and must be paid knowingly: reserved slots create visible empty
space in small vaults. Accept that cost only where the set is genuinely a
repeating field the eye scans. **A one-off card should size to its content** —
regularity is for repetition.

> There is no carve-out. Every Don't above holds **app-wide, including the
> contextual editor and change-review surfaces**.

## Page header — English caption + Korean h1

The header on each operations page (currently `/ontology/insights`) follows a **two-line pattern**. The user-facing Korean title is the primary heading, and the English category caption serves as a micro identifier that yields one step in the visual hierarchy.

```
[English category caption — text-caption / mono / uppercase / tracking-caption / quaternary color]
[Korean h1 — text-display / signature weight / primary color]

</p>
<h1 className="text-display font-[var(--font-weight-signature)]">
  Ontology Tree
</h1>
<p className="text-body-lg text-[color:var(--color-text-secondary)]">
  Approved nodes and relationships …
</p>
```

> This snippet was corrected to use ramp utilities on 2026-08-04. The previous example
> showed `text-2xl`/`text-sm`/`text-[10px]` as-is, but while the code zeroed those values,
> **the document was teaching off-ramp values to the next person**.

### Intent

- **English caption** — A category-area identifier for the page. The mono + uppercase + spacing combo enables fast visual recognition of "where you are," but stays weaker than the main heading so the Korean h1 reads first.
- **Korean h1** — The name users actually call it. Korean is the primary heading, so all body copy / descriptions / CTAs maintain a consistent Korean tone.
- **Two-line separation** — Mixing English and Korean on a single line (e.g. "Ontology") is forbidden. Each line stays in a single language with a single tone.

### Legitimate English caption examples

- Page categories: `Ontology`, `Workspace`, `Manual node`, `Get started`.
- System metadata: `ID Recommendation`, `Beta`, etc. — only intentional English identifiers. Sentence-style English is forbidden (translate to Korean).

### Consistency rules

- Caption font size stays in the `9px ~ 10px` range. Tracking ranges from `0.10em ~ 0.18em`.
- Within a single page, keep caption tokens consistent (mono / uppercase / tracking / color). System tokens will eventually be unified under a CSS var like `--font-caption-mono`.
- Use the English caption only once per page (top header). Don't repeat English category labels in the body — avoid duplicating the visual hierarchy.

### Surfaces where this applies (current)

`/ontology/insights` — follows this pattern. (`/ontology/edit`, the ERD builder,
was retired 2026-07-24 → it now redirects to `/ontology/studio`, the workshop (Compass Stage).)

The public surfaces `/`, `/topology`, `/docs`, `/projects`, `/project/[slug]` use the standalone Korean h1 pattern (without an English eyebrow caption) — these are the browse surfaces, not the operations surfaces.

## Geometry & Type Codex (R5, 2026-07)

> **Specify every box's size down to the pixel, identical everywhere.** This section is a **codebook** pinning text size, radius, and padding to token names. Value source:
> `app/globals.css` `@theme` "Geometry & Type Codex" block. Off-ramp
> literal `text-[Npx]` / `rounded-[Npx]` below are **forbidden** — if a new value is needed,
> add it only via a PR creating a new token (do not sneak in inline arbitrary values).

**Empirical basis (before substitution, 2026-07):** `text-[Npx]` hardcoding **29 size variants · 1,184 instances**,
arbitrary radius **18 variants**, card padding 4 variants. This dispersion was converged to the ramp below.

### Type ramp — 7 steps

Tailwind v4 `--text-*` namespace creates `text-<step>` font-size utilities. Letter-spacing is managed **separately** via `--tracking-*` pairs —
if auto-combined with `text-<step>`, ~1,000 elements' tracking would change at once,
braking the "codification redesign" principle. New code must pair them together (Apple optical principle: small steps get positive tracking for legibility, large steps get negative tracking for cohesion).

| Row | Token (utility) | px | Tracking pair (utility) | Target |
|---|---|---|---|---|
| caption | `--text-caption` (`text-caption`) | 9.5 | `+0.04em` (`tracking-caption`) | micro-labels, legends, timestamps |
| label | `--text-label` (`text-label`) | 11 | `+0.02em` (`tracking-label`) | chips, badges, secondary labels |
| body | `--text-body` (`text-body`) | 12.5 | `+0.005em` (`tracking-body`) | default body text, list rows |
| body-lg | `--text-body-lg` (`text-body-lg`) | 14 | `0` (`tracking-body-lg`) | emphasized body text, subtitles |
| title | `--text-title` (`text-title`) | 16 | `-0.01em` (`tracking-title`) | panel/card titles |
| display | `--text-display` (`text-display`) | 23 | `-0.022em` (`tracking-display`) | page headlines |
| hero | `--text-hero` (`text-hero`) | 30 | (no tracking pair — only use explicit tracking when consumption is specified) | hero headline |
| hero-lg | `--text-hero-lg` (`text-hero-lg`) | 34 | (no tracking pair — legacy `tracking-hero` retired to consumption 0 on 2026-08-18) | legacy gateway headline — the top-of-page text from when maps covered the full screen |
| monument | `--text-monument` (`text-monument`) | clamp(40, 5.8cqw, 96) | `-0.018em` (`tracking-monument`) | **Gateway Monument Headline** (remade on 2026-08-18) — the sole slot where typography takes over as maps leave the first screen. Line-height pair is ratio `--leading-monument` (1.08); since it uses clamp, creating px pairs would require size-specific tokens (display-tight class). |

**Closest-convergence rule** (on substitution): Snap each literal px to the nearest step
(±1px absorbed by ramp). Exactly between steps (e.g. 15px) goes to the upper step; off-ramp values (≥1.5px deviation) remain only via "explicit exceptions" below.

**Calling a non-existent step renders at root 16px** (recorded 2026-07-27). Since Tailwind
creates no class for undefined steps, names not in the ramp like `text-large` are **syntactically valid but apply no size**. This is invisible to any value checker — non-existent things leave no hardcoding literals either,
falling outside `type-ramp-coverage`'s view, and tsc/eslint do not check strings.
Two empirical cases existed: `text-callout` (found manually in #618), `text-large`
(node name on workshop center card — the screen's protagonist was only 1.28x larger than satellite card names at 12.5px. Converged to `text-display` on 2026-07-27).

The gate is `tests/contract/type-ramp-step-defined.contract.test.ts`. **Why not ESLint**: The judgment requires the actual token list from `app/globals.css`, but `no-restricted-syntax` uses AST selectors and cannot reference other files.
Copying step names into the rule would cause that copy to drift from the ramp, making the gate blind to its own gaps. So we build it as a contract test that reads the source to judge.

If a new step is truly needed, do all three in one PR: ① Ramp in `app/globals.css` ② Table in this doc ③ Registration in `src/shared/lib/cn.ts`.

### Line-height ramp — 9 steps (2026-07-27)

Tailwind v4's `--leading-*` namespace creates `leading-<step>` utilities.
**Line-height is not an independent ramp but a pair of size** — the repo's
real data says so: the trend for named utilities is already fixed px (`leading-4/5/6` = 16/20/24px,
121 instances), and the scale-fixed contract has already codified one pair (Chrome label 11px + 16px line-height).
This aligns with the dimensional regularity charter — **line-height is the seed of line height**
so it must be fixed in px so that the rhythm of repeated card sets does not depend on character count or language.

The values are on a 2px grid, and the three pairs (label 16 · body 20 · title 24) already have
the **same values** as the previously used
`leading-4/5/6`. This is not a new specification but merely naming what is already the trend.

| slot | token (util) | value | pair (font) | ratio | usage — when to choose this line-height |
|---|---|---|---|---|---|
| caption | `--leading-caption` (`leading-caption`) | 14px | caption 9.5 | 1.47 | micro-labels, transcripts, 9–10px secondary text |
| label | `--leading-label` (`leading-label`) | 16px | label 11 | 1.45 | chips, badges, chrome labels, card descriptions. **The locked contract of 16px** |
| body | `--leading-body` (`leading-body`) | 20px | body 12.5 | 1.60 | default body text, list rows, panel paragraphs, TOC rows |
| body-lg | `--leading-body-lg` (`leading-body-lg`) | 22px | body-lg 14 | 1.57 | emphasized body text, subtitles |
| title | `--leading-title` (`leading-title`) | 24px | title 16 | 1.50 | panel/card titles |
| display | `--leading-display` (`leading-display`) | 28px | display 23 | 1.22 | page headlines (wrappable) |
| hero | `--leading-hero` (`leading-hero`) | 34px | hero 30 | 1.13 | hero headlines (wrappable) |
| hero-lg | `--leading-hero-lg` (`leading-hero-lg`) | 38px | hero-lg 34 | 1.12 | gateway headlines (max 2 lines) |
| display-tight | `--leading-display-tight` (`leading-display-tight`) | 1.06 | free | — | **Slots read as a single block** — hero/section titles, card names, large numbers. **Max 2 lines** |
| prose | `--leading-prose` (`leading-prose`) | 1.7 | free | — | **User-written text** — markdown viewer/editor, detailed body, pre. Upper bound for long reading widths |

**One-line verdict**: If the app's UI text, use the **pair** of that size; if user-written text, use
**prose**; if names/numbers, use **display-tight**.

**Reason for only 2 free steps being out of bounds**: These two are steps that overlay sizes outside the ramp (`clamp()` hero,
nested sizes inside markdown), so fixing them in px would require tokens for each size. The ratio is the intent (cohesion/relaxation) here.

**Boundary of display-tight**: Using it on text or sentences stacking 3+ lines (descriptions/body) is a defect — Korean characters have top-line final consonants and bottom-line initial consonants that touch. Up to 2 lines is allowed (the download hero uses `<br />` for 2 lines in real usage).

**Korean sets the upper limit of values.** Korean fills the character box tighter than Latin, so the same
line-height looks denser. Thus, shared ramp values are set to **the spacing Korean requires**, and Latin follows that spacing (Latin is generous with wide line-heights, but Korean is not generous with narrow ones). **No locale branching** — apps mix two languages in one paragraph (Korean vault data within an en UI), so branching would disrupt the line height of the same paragraph.

**Must register with tailwind-merge.** If you don't register the step in `LEADING_RAMP_STEPS` of `cn.ts`, classes won't be dropped, but **conflict merging won't occur** — both survive in `cn('leading-body', cond && 'leading-prose')` and CSS source order decides the winner. It's quieter than size ramp drop accidents, so you can't find the cause even by looking at the screen. Gate: `cn.test.ts`.

**Companion auto-binding — enabled (B2, 2026-07-27).** Defined `--text-<step>--line-height` for all 7 steps in Tailwind v4, so one `text-<step>` carries line-height. This binding is necessary to close the spec — if you only define pairs, **places without line-height classes** remain outside the spec and render with inherited 1.5, and hardcoding checks/ratchets can't see *missing
classes* (a blind spot similar to unregistered steps quietly rendering at root 16px). 927 instances were in that state.

Radius measured before/after with the same conditions (1512×950 dark · ko/en · 8 screens) before enabling:

| character | count | line-height |
|---|---|---|
| 9.5px caption | 94 | 14.25 → **14** (−0.25) |
| 11px label | 186 | 16.5 → **16** (−0.5) |
| 12.5px body | 70 | 18.75 → **20** (+1.25) |
| 14px body-lg | 30 | 21 → **22** (+1.0) |
| 23px display | 8 | 34.5 → **28** (−6.5) |

Of 746 elements, 388 changed, and of those, **380 had |Δ| ≤ 1.25px** — mostly one-line
chips/labels so pixels don't even move. **Only 8 places had box height changes ≥ 2px**, all page headlines (`/projects` · `/ontology/insights` · `/docs` empty state ·
`/git`). That 34.5px was a product of inherited 1.5 that no one ever chose, and line height is returned to design decision per the dimensional regularity charter. The 186 labels dropping to
16px is **the value already codified in the locked contract**, so binding doesn't violate the contract but converges 186 places to the value the contract states.

**Since font-size doesn't change at all, line breaks cannot theoretically increase.** Zero places where repeated card set uniform height broke (line-height is determined only by size, so one set moves together). Same 8 places + 1 two-line label (42 → 44px) even at 1024·768.

**Explicit `leading-*` wins over companion** — the explicit classes laid down by B1 in 74 places act as shields. But within `cn()`, **order matters**: tailwind-merge assumes "size also determines line-height," so subsequent `text-<step>` absorbs preceding `leading-*`. Before binding, this assumption was false, and absorbed places quietly fell to inherited 1.5; after binding, it became true. Recommended notation: size first · line-height second. Gate:
`cn.test.ts`.

**`--leading-hero` creates no pixels today — still kept.** Both 2 call sites of `text-hero` in the repo already have explicit leading attached (`leading-tight` · `leading-display-tight`, both with "single-line cohesion" intent written in code). Kept for future: if hero is used without leading later, it will receive **34px** instead of inherited 45px. Removing it would create exceptions where only the top two ramp steps lack pairs; no exceptions is the value of the spec. Don't delete as *"zero usage so dead token"* —
`--pad-panel` precedent (unused tokens are misinformation) differs. That was a value no one used, but this is a value **carried by** the `text-hero` utility.

**`--leading-hero-lg`(38px) has the same status** (new 2026-07-29). The only consumer today, `/download` headline, has explicit `md:leading-hero-lg`, but `--text-hero-lg--line-height` binding is needed to close the ramp top without exceptions.

**Why is hero-lg 34px.** On a surface where maps cover the full screen, a 30px headline competes with background weight. At 34px, the ratio with lead (`text-body` 12.5) becomes **2.72**, falling within the reference hero band (2.5–3.0). Line-height 38px continues the trend of ratios tightening toward the ramp top (1.217 → 1.133 → **1.118**). (Tracking pair `tracking-hero` was re-retired with 0 consumers in the gateway remake on 2026-08-18.)
Promotion trigger was **the second consumer**: `DesktopVaultWelcome` was already bypassing the ramp with `md:text-[34px]` + eslint-disable.

#### Conditional size trap — new failure mode created by companion binding

After binding, **switching only font size conditionally misaligns the pair.** Arbitrary sizes (`text-[Npx]` · `text-[length:…]` · clamp) have no companion, so the original step's line-height remains at that breakpoint too.

Full measurement found 2 instances, actual misalignment 1:

| slot | verdict |
|---|---|
| `/git` headline — `text-title` + `sm:text-[length:var(--text-display)]` | ⚠️ **Mismatch.** 23px font with title pair 24px line-height (1.04) — exceeds repo max. Corrected to `sm:text-display` |
| desktop welcome hero — `text-hero` + `leading-tight` + `md:text-hero-lg` | Safe. **Explicit leading covers both sizes**. (2026-07-29: legacy `md:text-[34px]` + eslint-disable removed as 34px became a ramp step — the moment consumption becomes two places is when to promote the value to a name) |

**How to judge**: If an element has both a ramp size step and conditional arbitrary size,
check if explicit `leading-*` exists. If not, it's a defect. Two ways to fix —
① Use ramp utilities for conditional sizes too (pairs follow) or ② Attach explicit line-height to directly set both sizes.

**Don't bypass ramp tokens with arbitrary length.**
`text-[length:var(--text-display)]` looks the same size as `text-display` but **loses the line-height pair**. Arbitrary references for ramp **outside** size tokens (rail labels · Chrome titles etc. dedicated
tokens) are justified — there is no ramp to bypass.

The gate has two layers: bypass references are caught by **lint** (`arbitrarySizeSelectors`), and mismatched generic types are caught by **contract tests** (`tests/contract/type-ramp-leading-pair.contract.test.ts`) — the latter requires the entire class of a single element for judgment, which cannot fit into a single AST selector when split by `cn()` arguments.

### Content Icon Ramp — 3 Steps (System Established 2026-08-04)

The size vocabulary for **content icon glyphs** (lucide) sitting next to body text or labels. The canonical values are `--icon-*` in `app/globals.css`, and the JS mirror for prop channels is `ICON_SIZE` in `src/shared/ui/icon-size.ts` (structured identically to MOTION mirrors — lucide's `size={N}` numeric prop cannot read `var()`).

| Section | Token / Mirror | px | Adjacent Type | Purpose |
|---|---|---:|---|---|
| sm | `--icon-sm` / `ICON_SIZE.sm` | 12 | `text-label`(11) · `text-body`(12.5) | **Default.** Glyphs in rows, chips, and buttons (most frequent actual measurement: 77 locations) |
| md | `--icon-md` / `ICON_SIZE.md` | 14 | `text-body-lg`(14) | Emphasis body text and subtitles |
| lg | `--icon-lg` / `ICON_SIZE.lg` | 16 | `text-title`(16) | Icon next to title · Standalone icon |

**Why this ramp was created.** The 2026-08-04 real-world test (the first attempt to build a new screen from scratch using this system) empirically revealed holes: content icons were split across **167 call sites** using **9 distinct px values** (10, 11, 12, 13, 14, 15, 16, 17 + 24 unspecified), with two surfaces mixing 4 values within the same file (Document Palette: 10/11/12/14; Dependency Picker: 10/11/12/13) — this was drift, not role differentiation. Since consumption channels used **JSX numeric props** (`size={N}`) rather than className, the values fell outside lint's scope (the same bug that fractured framer durations). The tester noted while copying sibling components: *"Nothing told me it had a different value."*

**Steps were chosen based on observed frequency + type pairing.** New value 0 — all are dominant values in today's screens, so adding them moves zero pixels. The source of the type-pairing principle is Carbon (verified 2026-08-04, [Icons usage](https://carbondesignsystem.com/elements/icons/usage/)): *"16px and 20px icons are optimized to feel balanced when paired with 14px and 16px IBM Plex"* — icon steps stand not as independent scales but **paired with type sizes**, and *"Be sure icon size is consistent throughout your product."* The lower bound source is Fluent 2 (verified, [Iconography](https://fluent2.microsoft.design/iconography)): *"Smaller icons can give information or reinforce an idea, but should not be used for interaction"* (12px is the lower bound for informational use). Material 3 · Apple HIG (SF Symbols) · Polaris · Primer have body text intended only for JS rendering, making source verification impossible — per precedent #0 in "Rules for Expanding the System" (M3/Spectrum 2026-08-03), no sentences citing these four as grounds are included.

**Scope — content icons only.** Chrome and rail icons remain owned by their respective surface contracts: `--topology-chrome-icon-size` (12) · `--chrome-icon` (16) · `--app-nav-rail-icon-size` (20, logo only 26 — fixed scale contract). Overlapping values represent the same answer for the same type pair, but Chrome density decisions must move independently, so they are not bundled.

**The gate is a ratchet, not lint** (`tests/contract/icon-size-ramp.contract.test.ts`): ① CSS ↔ JS mirror consistency ② Per-file ledger for sizes outside the ramp (`size={N}` prop + `size-N`/`h-N w-N` classes) — **new files start at 0 on day one**, existing debt of 64 cases/17 files can only decrease ③ Ratchet for unspecified (default 24px render): 3 cases/2 files ④ Composite probe + dead-code prevention denominator. The reason it's not lint: replacing the 64-case debt implies ±1–2px render changes, requiring design judgment at each site (the founding judgment of the ratchet), and an icon-specific exception block would replace ramp selectors for those files due to flat config multi-block pitfalls.

**Debt repayment is a design pass with before→after tables per site.** Whether 10·11 (44 sites) target sm (12) — and whether micro steps (10 or 11) are separately needed — is judged after screen measurement (queued alongside mono command tag tracking confirmation). Until then, this ramp guarantees only one thing: **newly used icons do not expand the set from 9 to 10.**

#### 2026-08-05 — This ramp had **zero consumers**, and the gate missed 73%

The above paragraphs were correct but unaware of two things. Upon review in the audit:

1. **The production consumers of `ICON_SIZE` and `--icon-*` were exactly 0.** 216 sites had hardcoded numeric `12`/`14`/`16` values, which happened to match by chance. Defining ramp tokens without anyone referencing them makes them not a spec but **incorrect information** (the same judgment used when this document removed two margin tokens). Now, **313 sites reference `ICON_SIZE`** — moving the value moves the screen.

The descriptions below regarding "camera reservation width" are records from that era.

**Aligning only the left still causes visual bias.** Even after Verdict ③ placed these six elements at the same x, the column stops at `--page-max`, causing all remaining width to accumulate on the right — measured 1920: left 64 · right 256 (ratio 4.0), 2560: left 96 · right 864 (ratio 9.0). These six elements were **one set** even then. While adhering to alignment principles, symmetry can break; thus, they are specified and measured separately.

**Do not fix with `mx-auto`.** Not because centering is bad, but **because it creates two origins** — the wrapper centers itself based on the viewport, while camera reservation insets are fixed values, causing a 96px offset at 1920 and 416px at 2560. Elevating the origin to a single token means both the six elements and the camera consume **the same value**, making this thought structurally impossible.
Symmetry comes from having origins on both left and right padding, with the column filling the remaining width exactly.

**It is the only gateway token registered via `@property <length>`.** Registration ensures computed values solidify into used lengths like `160px`, enabling: ① CSS to recalculate automatically when the viewport changes, and ② JS to read the same value via `parseFloat` and derive camera reservation width (`origin + plate width + gap`). The three atomic values manually set by humans are **not registered** — registration would cause silent drift where natural inputs like `30rem` silently revert to initial-value without error. Only derived values are registered.

**⚠️ If the origin becomes a function of viewport, JS derivation must subscribe to resize.** CSS follows for free, but camera reservation width does not — setting it once on mount means the plate moves to the new origin while the camera continues using the old value. Updates require full invalidation or `refreshIndexDependentTokens` (replacing only that token).

Gateway: `tests/e2e/download-gateway-grid.spec.ts` — 8-column × (six elements x identical · `clientWidth − band.right === origin` · GNB right edge · reservation width = origin + plate width + gap) + resize round-trip. The reference for symmetry is `clientWidth`, not `innerWidth` (`100vw` includes the scrollbar, while `getBoundingClientRect` does not).

**To create a width «ramp»**, that is when ramp listing requires "system" convening + approval. Falsification
observation: if three or more surface width tokens of the same value repeat **without derivation** (evidence of scale demand), this decision is reconsidered.

### Form Fields — `fieldClass()` · `fieldLabel()` (Design Council, 2026-08-06)

**Pressing and receiving values are different parts.** The eight shapes of `controlClass()` emerged from a full census of **419** production `<button>` elements, while fields belong to a **different population** (63 forms). Hence, the ninth shape is not a variant but a **second cva** — for detailed rationale and rejected alternatives: `docs/DECISIONS.md` 2026-08-06.

#### `fieldClass({ frame, size, multiline })`

| Axis | Options | What differs |
|---|---|---|
| `frame` | `boxed` · `bare` | **Who provides the box** |
| `size` | `xs` · `sm` · `md` · `lg` | Height — **1:1** with `--control-h-*` |
| `multiline` | `false` · `true` | Hard `h-*` vs `min-h-*` |

| `size` | Height | Token | Radius | Inset | Type |
|---|---:|---|---|---|---|
| `xs` | 28 | (same as `sm`) | `micro` 4 | `px-2` | `text-body` 12.5 |
| `sm` | 28 | `--control-h-sm` | `chip` 6 | `px-2` | `text-body` 12.5 |
| `md` | 32 | `--control-h-md` | `chip` 6 | `px-2.5` | `text-body-lg` 14 |
| `lg` | 40 | `--control-h-lg` | `chip` 6 | `px-3` | `text-body-lg` 14 |

**`xs` is not a height tier** — it is a tier that lowers only the radius, using the same syntax as chips' `xs`.

**The reason types pair with sizes is because the screen dictated it.** Initially, we used only `text-body` (12.5), but reviewing `/project/new` revealed that **the values users input are roughly the same magnitude as the labels the app uses (11px)**. In forms, what must be most readable is the value entered by the user. The tight spacing of 12.5 exists because putting 14px text into a 28px box eliminates vertical breathing room.

##### `boxed` vs `bare` — Why they cannot be merged

The "Hierarchy" column opened the reality and split forms into three:

| Dialect | Function | **Winning choice** | `frame` |
|---|---|---|---|
| **Record** | Value persists to disk | **Input** | `boxed` |
| **Query** | Reaches existing data fastest | **Result** — not input | `bare` |
| **Stage** | Renders text for cards in situ | 23px name | **Out of spec** |

Making records transparent causes forms to disappear; making queries heavy causes **input to overpower results**.

`bare` **does not provide any dimensions, borders, radius, horizontal insets, or touch bottom** — the parent already provides the box; providing it again here would **push inward from within that box**.

**List Stage (workshop name 23px · subtitle 9.5px) out of spec.** Its size is not a form type but the **type of card being created**, meaning its size carries information (Mackinlay expressiveness). The moment it enters a box, that information is erased. We document it here so **the next person does not have to rediscover it**.

#### `fieldLabel({ row })`

Labels split into three branches, but **only two have specifications**:

| Branch | Spec | Why |
|---|---|---|
| **Name text** | `text-label`(11) · `secondary` | Name must be larger than its footnote |
| **Entire row is clickable** (`row: true`) | Touch floor + `min-h-6`(24) + row layout | Clicking the label toggles → **label is the target** (WCAG 2.5.8) |
| **Layout-only wrapper** (`block` · `flex flex-col`) | **None** | Adding type/color competes with the inner name text and spec |

**The reason ink is `secondary` is empirical measurement.** The label on `/project/new` was 9.5px · quaternary, while **the footnote directly below it was 11px** — the field's name was one step smaller than its own footnote, causing users to read the 14px placeholder before the label. This is the **same issue** as caught in the 2026-08-02 settings sheet (promoting dimensions from subordinate positions to primary roles).

### link floor 24 · Prose link contract (2026-08-04)

**The `link` floor is 24 (`min-h-6`), not 44.** The previous value layer cited WCAG 2.5.8 (AA, 24×24) but included the value 44 (`min-h-11`) from 2.5.5 (AAA)/HIG. This incorrect floor created an `inline` escape hatch, allowing five misconfigurations (16–18px hit areas) to survive without triggering any static checks. The three parts of the redefinition:

- **Fine pointer = 24.** The value layer `link` base carries `min-h-6`. Gate:
  `tests/contract/control-class.contract.test.ts` "link floor is 24" +
  `tests/e2e/touch-target-contract.spec.ts` fine-pointer audit (24×24 ∨ inline
  exemption ∨ 24px spacing exception — exactly as per WCAG 2.5.8).
- **Coarse pointer = 44 — two prescriptions, neighbor spacing determines which**
  (revised 2026-08-05). 44 comes only from `--touch-target-min` (single source for coarse).

  | Prescription | Where | Why this one |
  |---|---|---|
  | **Actual height** — `.atlas-touch-floor` (`min-height`) | Value layer `chip`, `row`, `pill` | As the control grows, it **pushes neighbors away**, preventing overlap |
  | **Hit expansion** — `.touch-hit-expand` (coarse-only pseudo-element, 0 layout shift) | Value layer `icon`, hand-drawn controls | A square surface contract; `min-h` alone cannot shape this area |

  **Hit expansion attachment requires ≥12px neighbor target clearance** — blindly attaching to dense rows causes the `::after` of a later DOM element to steal the tab of the preceding one. This is exactly why we use actual height for the value layer: among 38 cases under 44px, **21 had <12px spacing with neighbors** (EN/KO toggle 1px · tab pair 2px). The cost is density (~50px vertical space in the mobile `/docs` header), documented in the ledger (2026-08-05).

  ⚠️ **The floor rule lives outside cascade layers.** If placed inside `@layer base`,
  `min-h-8` from `@layer utilities` wins — **layer order dictates specificity**,
  so stacking classes cannot override it. We experienced this: the rule was in the
  build, but the screen remained 32px. Gate:
  `tests/contract/touch-floor-layer.contract.test.ts`.
- **The `inline` axis is deleted.** "Is it inside a sentence?" cannot be determined statically (sibling text origin, used display, reflow all open outside the tag), so runtime handles it.

**Prose links are not controls.** Links within markdown body flow (Document Viewer 5 ·
Gateway Reader 1) have siblings that are text, and the line box is owned by the parent `--leading-prose` — none of the eight value layer shapes can theoretically occupy this space (inline-flex kills wrapping at 320px — measured rect 1 vs. control 2). The target is
the single set **`.prose-link`** in `app/globals.css`: it owns only underline geometry (offset 2px) and default decoration color; it does not impose ① display, ② line-height/font-size, or ③ focus (preserving UA defaults). Gate: `tests/contract/prose-link.contract.test.ts`. In the control ledger,
`prose` is listed as a claim (`control-adoption-ratchet`).

### Which shapes does this ladder apply to? (2026-08-03 — scope explicit)

The previous sentence (*"Heights outside this table are deviations"*) omitted the scope, leaving
**areas where deviation or compliance cannot be determined**: NavRail items render at **62px** across all routes (measured 1440×900), but that 62 is not a unified value — it is the **sum** of `py-1.5` (12) + tile 32 + `gap-1` (4) + label line box 14. This is not in this table, nor is it a defect — it was a gap caused by the rule not stating its scope.

| Category | What the ladder captures | Example |
|---|---|---|
| **Single-line horizontal controls** — content is one line, height defines the axis | **The outer height itself.** All variants must explicitly declare `min-h-*`, and that value must be in this table | `chip` · `pill` · `segment` · `row` · `card` |
| **Square icon controls** | **The side length itself.** `h-*` or size tokens must be in this table | `icon` · `ChromeTile` · `DocsHeaderTile` |
| **Vertically stacked controls** — e.g., icon above, label below, two+ lines | **The inner square tile, not the outer height.** The outside is the sum of content, so the ladder does not define it | `tile` · NavRail item (`--app-nav-rail-tile-height` = 32 = `--control-h-md`) |
| **Inline text links** | Exempt. Applying `min-h` pushes the line box up (measured 21.3 → 44) | `link` (inline). Non-inline `link` is 44 |

**In short**: The ladder captures «height of single-line boxes» and «side of squares». For vertically
stacked items, it captures **the tile inside**, not the outer sum — trying to do so would let label character count dictate specs, causing the ladder to violate its own rule 1 (*"padding must not define height"*).
**Scope — this table applies to «single-line horizontal» controls (2026-08-03 system log).**
Applicable targets are only single-line shapes (`chip`·`pill`·`segment`·`row`·`card`) and squares
(`icon`). **Vertical 2-axis surfaces are not in this table** — `tile` shapes, and controls stacked like NavRail items (icon above, label below) have their height defined by content and chrome geometry tokens (`--app-nav-rail-tile-*`). A NavRail item rendering at 62px is not a ladder deviation but **out of scope** (sum of tile 32px + label + spacing). As the rule audit noted, the phrase "outside this table is deviation" was undeterminable without specifying which shapes it applied to — this paragraph is that scope declaration. Underline tabs (`tab-bar`) are also out of scope as they are baseline-aligned surfaces, not boxes; however, the note that their height (measured 29px) is outside the lexicon remains unresolved (see "Next" below).

**`xs` (micro tier) is not a height step (2026-08-03).** The value layer's `size: 'xs'`
keeps the 24 floor (`min-h-6`) and only lowers **inset, type, and radius** to the micro tier (chip: `px-1.5 py-0.5`/caption/`rounded-micro`. Outside chips, it is an alias for `sm` — no consumers invent values). The reason for not creating a step below 24 is the first line of the table above: below WCAG 2.5.8 floor is not a "small step" but non-compliance. Evidence is the three-round continuous record in the ratchet ledger: "no step below sm" (full sweep 14 · 9 files).

**Three disciplines:**

1. **Height is defined by the ladder; padding is determined within it.** Reversing this (letting padding define height) quietly births values not in the lexicon — that is how 30/34/22/20 were created.
2. **Hard `h-*` is forbidden; use `min-h-*`.** Hard heights clip wrapped controls, hiding content. `min-h` establishes single lines on the ladder and allows overflow to grow.
3. **If you need a height not here, fix this table — do not add axes.** This is what Rules 0 (check if it exists first) and 1 (components over axes) of "Rules for extending the system" require here. The `fixedHeight` axis from 2026-08-03 did exactly the opposite.

### Rules for extending the system (2026-08-03 owner directive)

`/design-build` is **how to use** the system. This section is **how to extend** it —
we paid a real price for not doing so.

> Spectrum (`spectrum.adobe.com`) render their body content via JS, so the original text
> doesn't download properly

I also verified that Fluent 2's token documentation **lacks a section on "When to create new tokens."**

#### Rule 0 — **Look for existing values before creating new ones**

**This rule is first because we didn't follow it on 2026-08-03.**

This app already had a single source of truth for control heights —
`--control-h-{sm,md,lg}` = **28 / 32 / 40px** (`app/globals.css`, established in
"Design Overhaul #13" on 2026-07-25, consumed by 7 files). But while building the control value layers,
we failed to find it and instead **invented new values of 24 / 30 / 34** as a byproduct of padding + line-height.
**30 and 34 are values that do not exist in this app's height vocabulary (24·28·32·36·40·44).**

Then it got worse. When the new values clashed with the contract (32px), **instead of fixing the value, we added an exception axis
(`fixedHeight`).** System stone verdict: *"That axis is a **symptom** that the value is wrong,
not a necessary axis — fix the value and the axis dies."*

The result appeared on screen: we reduced chip sizes from 50 types to 3, but **there were
8–9 types of control heights on a single screen**. Even if Rules 1–6 were followed, this one violation caused it.

**Procedure** — If you feel you need new dimensions, colors, or spacing, stop right there and:

1. Find the token for that role in `app/globals.css` (`--control-h-*` ·
   `--chrome-*` · `--text-*` · `--leading-*` · `--radius-*` · `--motion-*`).
2. Read this document's **「Control Height Ladder」** and ramp sections.
3. Run `git log --oneline -- app/globals.css | head -20` to see why those values
   were set — there is usually a reason, and that reason is likely still valid.
4. If they still don't exist, **only then** proceed to Rule 4 (count how many are blocked).

> **Values created without looking are not part of the system; they are a second system.**

**Industry publication** — [Carbon Contribution Review](https://carbondesignsystem.com/contributing/product-development-lifecycle/) actually has this question as a review item:

> *"Does it replicate anything in the system already, or is there truly a gap?"*
> *"If the proposal does replicate an existing asset, is there evidence to show that
> the proposed solution is better?"*

[W3C Design Tokens Draft](https://www.designtokens.org/tr/drafts/format/) defines the purpose itself
as a single source of truth — *"Maintaining a 'single source of truth' for design tokens"* ·
*"Eliminating repetition of values in token files."*

The second quote is the exact reflection of our thinking: **if you must recreate something that already exists, you must provide evidence that the new version is better.** We invented 24/30/34 while having `--control-h-*`, without providing that
evidence.

#### Rule 1 — Look at slots before adding axes

**The basis of this clause is arithmetic, and the tool called slots exists in the industry.** To avoid mixing them in speech, their sources are listed separately.

**Our rationale (math)**: With 3 axes, there are 8 combinations; with 4 axes, 16. **Axes multiply, components add.** We added axes one by one from `active` → `inline` → `fixedHeight`, and the results appeared on screen — reducing chip sizes from 50 types to 3 types, yet **the control height has 8–9 types** on a single screen.

**Industry tool**: [tailwind-variants slots](https://www.tailwind-variants.org/docs/slots)
defines them as *"Slots allows you to separate a component into multiple parts."*
⚠️ **That document does not call slots 'the solution to variant explosion'** — it introduces them merely as a part separation
feature. Using them as an alternative to axis explosion is **our judgment**, and the basis is the arithmetic above. (Original text verification on 2026-08-03. Initially I wrote "the document explicitly states" based only on search summaries, but that sentence was not in the original text — always verify quotes by opening the original source.)

⚠️ **No industry publication basis.** No text in Carbon · Fluent · Polaris · W3C discusses "variant axis
combination explosion vs. part decomposition" (verified against original texts on 2026-08-03). This clause stands on **our arithmetic and measurements alone**. tailwind-variants is cited for tool usage, not as an industry principle basis;
the moment you erase that distinction, this clause gains fabricated authority.

Judgment: When a new variant is needed, first ask "**which part** of this control changes?"
If only the shell changes, use an axis; if text/icon/badge changes, use **parts**.

#### Rule 2 — Do not create two tags with the same appearance

**Our basis**: If buttons and links look the same, one must inevitably become outdated. Measurement — this
repository had byte-identical `<button>`/`<Link>` twins with no guardrails.

**Industry publication — why twins arise**: Because semantics diverge from purpose.
[Carbon Button usage](https://carbondesignsystem.com/components/button/usage/):
*"Do not use buttons as navigational elements. Instead, use links when the desired
action is to take the user to a new page."*
[Polaris Button](https://polaris-react.shopify.com/components/actions/button):
*"Buttons are used primarily for actions… Links are used primarily for navigation."*

**And the industry's answer is also 'one component, replace only the underlying element'** — same Polaris document:
*"If navigation is required for the button component, use the `url` prop."* Our
`asChild` escape hatch follows the same structure; Polaris releases it as a **first-class API**.

**Industry tool**: [Radix's `asChild`](https://www.radix-ui.com/primitives/docs/guides/composition)
is *"When `asChild` is set to `true`, Radix will not render a default DOM element,
instead cloning the part's child and passing it the props and behavior required to
make it functional."*

⚠️ **However, Radix itself does not recommend this common path.** From the same document:
*"In the majority of cases you shouldn't need to modify the element type as Radix
has been designed to provide the most appropriate defaults."* And there are three conditions —
your child must **spread all props** (`If your component doesn't support those
props, it will break.`), **accept a ref** (`If your component doesn't accept a
ref, then it will break.`), and *"it is your responsibility to ensure it remains
accessible and functional."*

**So our rule is this**: It is an **escape hatch** used only where duplicates would arise, not a default
pattern. When using it, pin those three conditions as contract tests. If you can't bear that burden,
don't create the duplicate — **eliminate one side**. That is the title of this clause.

```tsx
<RowButton asChild><Link href="…">Open Document</Link></RowButton>
```

### There are two layers — values and behavior

`controlClass()` does **not replace** components. The industry standard is clearly components
(Carbon · Fluent · Material · Polaris · shadcn), and this repository also produces components.
The distinction is **what is separated**:

| Layer | Form | Carries | Why |
|---|---|---|---|
| Value | `controlClass()` | Appearance · Size · Color · Disabled | A string is sufficient; contract tests prevent the lamp from emitting out-of-contract values. |
| Action | `Chip`/`IconButton`/`RowButton` | Default `type="button"`, mandatory accessible name, button semantics | **Strings cannot fundamentally represent me** |

Specifically, three things strings cannot do: ① Inside a form, the default for `<button>` is `submit`, so
a single chip could submit the form ② Icon controls have no readable text, requiring an accessible name,
which is an attribute ③ List rows are wide, tempting one to make them `div+onClick`, but then keyboard navigation fails. `IconButton`'s `label` is a **required prop**, so the type blocks it at the moment of use — lint and contract tests tell you "you missed it" later, but types block it right there.

Height was not put in the lamp. Of 143 chips, only 38 (30%) have an explicit height; putting it in would change
the key for the remaining 70% at the moment of transition. Squares (`icon`) are the exception —
there, height is shape.

### Disabled State — One Value (2026-08-06)

The visual treatment for unclickable controls is **the single set `CONTROL_DISABLED_CLASS` in `control-class.ts`**: blurred `disabled:opacity-55`, cursor `not-allowed`, removed shadow, and disabled hover. These four form one set — taking only the blur leaves a half-state where the control appears disabled but hover still works. `controlClass()`/`fieldClass()` already load this as base; hand controls combine this constant (they do not copy the value).

- **Why 55**: The value from the 2026-08-03 layer decision (owner feedback: «pressing recent changes yields no response»), verified on `/project/new` where both filled indigo and outline buttons read as «present» and «not clickable». The nine places split across 60, 50, and 45 were unified to 55 on 2026-08-06 — WCAG 1.4.3 exempts disabled components from contrast requirements, but this exemption does not permit «any value».
- **Elements that cannot receive `disabled:` variants** (inactive representations of `<Link>`/`<span>`) use `opacity-55` directly at the same level — currently one place (`TopologyV2ContextMenu`), outside lint.
- **Gate**: `eslint.config.mjs` `disabledAffordanceSelectors` (global ban on values other than 55, zero exempt files) + `tests/contract/disabled-affordance.contract.test.ts` (does the constant handle all four treatments? · do values not diverge per path? · is the value layer consistent with lint allowed values?).

#### List Growth and Upper Bound (`select-growth.ts`, 2026-08-02)

The old upper bound was a single literal `max-h-[264px]`, and that value **answered nothing**: how many items are fully visible? · when does scrolling start? · what happens if it opens at the bottom of the screen? All three were wrong. The upper bound is **two values, and the smaller one wins.**

| Upper Bound | Value | Rationale |
|---|---|---|
| Row upper bound `LISTBOX_MAX_ROWS` | **8 rows** | ① Measured runner had model **7 items** — if common cases scroll, «more available» becomes a lie ② 8 rows with mixed description lines ≈ 320px, which is less than half the settings sheet (672px) where this list appears. Growing beyond that turns it from a «selection control» into a «covering surface», requiring search rather than a larger dropdown |
| Space upper bound | Remaining viewport relative to anchor | Using row upper bound directly on bottom-triggered triggers causes the window to go off-screen |

Three rules:

1. **Row height is measured, not assumed.** Rows with «embedding-only» descriptions are two lines and thus taller. Multiplying line count by fixed height causes half-rows near the upper bound. `ResizeObserver` follows late-loading web fonts.
2. **The upper bound when nothing is constrained is not «measured content height».** Doing so means the box scrolls its own content the moment a row grows 1px due to subpixels or late fonts — verified in practice (all 7 items visible but `scrollHeight > clientHeight` so affordance falsely enabled). If unconstrained, the upper bound is **remaining space**.
3. **Affordance only appears when actually clipped by the upper bound.** `listboxTopIsHidden` / `listboxBottomIsHidden` — same judgment as composer's `composerTopIsHidden`, syntax intentionally matched (if two surfaces solve the same problem differently, the next person won't know which to copy). If upper bound is not reached, there is no scrollbar at all due to `overflow: hidden`.

| `--settings-content-measure` | 658px | Maximum row width on **any face** of the settings sheet |

  button occupy the upper-right 45° zone, so **80% (513px²)** of the badge was covered by the button,
  and `elementFromPoint` returned the button, meaning the **badge was never clicked**; the default
  bar also had its lower-right corner 80px² covered. The single source for position calculation is
  `render/cluster-chips.ts` (`clusterBarRect` · `clusterBadgeRect` ·
  `orbitButtonRect`), and zero full overlap across radii 7–42 × zoom 0.85–1.5 is
  locked by `expand-settings.contract.test.ts`.
- **Fan spacing is 34, not 26** (2026-08-02) — child radii grow up to 1.4x via
  `magnitudeScale` (capability 11 → 15.4), requiring 30.8 for two to stand side-by-side,
  yet the spiral disk's 26 was used as-is. `relaxCollisions` only sees the
  **base radius** and pushes, failing to correct this excess (actual measurement: parent expansion from three
  marks overlap 26 pairs → 0 pairs, named marks 31% → 34%). The final layer does not stretch across the entire wedge width but is **center-aligned** — leaving the other two to fly to the fan's ends, eliminating the spot where they stood alone farthest from the parent (read as crumbs and first touching the sibling domain). Columns (`column`) also use 34 for the same reason.
- **The bar has no preceding glyph zone like the pill** (2026-08-02) — the pill places
  `＋` in that 14px, but the bar aligns and draws the sign and number in the center of the plate. Inheriting the zone as-is made the plate wider than the node it describes (actual measurement: 58.8 vs domain node diameter 48). A control larger than data is ink inversion (Tufte) — removing it yields 44.
- **Name boxes reserve an additional 3px left and right** (`LABEL_SIDE_GAP`) — AABB overlap determination does not count "touching" as overlap, so two names stood side-by-side with a 0.7px gap, reading as one word (actual measurement 2026-08-02: "Kakao Alert Talk" + "Accumulated Points Ledger"). This matches the design's reserved box value `measurement width + 6`.
- **Three numbers** — count opened at once (4–24, default 24) · count to attempt naming (3–40,
  default 8) · parents to expand simultaneously (1–6, default 3). All three are **constants already in the code**
  (`EGO_NEIGHBOR_LIMIT` · `DISC_LABEL_TOP_K` · `MAX_EXPANDED_PARENTS`), and now
  these constants derive their defaults from this setting (preventing values being written in two places).
- **Hierarchy of settings sections** — do not weigh all six items equally. There are two decisions
  ("Expand indicator" · "Expansion structure"), and the three numbers are collapsed under "Number matching" —
  following the same syntax as its immediate neighbor "Footprints" (presets first · "Manual adjustment" later).
