# Build the app and the website with Vite and remove Next.js

**In one minute.** Next.js builds every Atlas screen today, yet Atlas uses none of its server: the
build writes plain files. That costs a 31 s build peaking at 3.3 GB and 13 s from `pnpm dev` to the
map. On 2026-11-27 the owner decided to move the installed app's screens and the public website to
Vite, one toolchain, with Next.js removed. This spec decides how:

- **Addresses in the app stay exactly as they are** (`/<language>/<screen>/?…`). They are how
  screens keep a selection, how the install link lands and how 466 test navigations enter; changing
  them in the same move would make a red test run unreadable.
- **Every public page stays a real HTML file at the same address**, written at build time by a
  step Atlas owns. Its whole `<head>`, its words, the sitemap and `llms.txt` do not change.
- **Nothing a person reads on a screen changes.** No message catalogue is edited. The app's first
  frames keep today's loading picture in the person's language.
- **It starts after the removal of the browser workbench has merged, whole.** Then: Vite builds
  the app beside Next and runs the whole suite; Vite builds the website beside Next and must match
  it page by page and beat it on three measured numbers; the shipping build switches and one beta
  ships; only after that beta is seen is Next deleted.

Words used below: the *app folder* is the files the installed app embeds; the *site folder* is the
files the website host serves; to *prerender* is to write a page's HTML at build time; a *shim* is
a small stand-in file that answers an import of `next/…` while both builds exist. "The removal
spec" is "Remove the browser workbench" (branch `docs/remove-browser-workbench`), whose terms this
spec uses: the *faked app runtime* (the test helper answering the app's native calls), the
*app-only page* (what a plain browser sees at an app address), and the two *faces* an app address's
HTML carries, chosen before paint by the boot script's `data-shell="desktop"` on `<html>`.

## Person and moment

1. **The owner and the coding agents that build Atlas.** They start `pnpm dev` or a build, often in
   several worktrees at once, and wait. Owner, 2026-11-27, translated: "Let's switch to Vite! If
   it's fine to do, do all of it." "Can't the intro site also be Vite only?" "Instead of keeping
   the URL format, if there's a different way, you can do that — there will be no web browser
   anyway." Standing instruction, 2026-11-19 (the owner's words, not in the repository): memory
   use is held to the highest standard.
2. **A person using the installed app.** They launch it, move between screens, switch language,
   follow an install link from an agent. They must notice nothing.
3. **A visitor or a search engine** opening `https://ontologyatlas.com/ko/guide/relations/`. The
   address, the words and the page's head must be what they were.

Not observed: the owner waiting on a dev server or a build (no capture; criterion 1 takes the
measurement), and any visitor. Someone who uses Atlas without agents sees no difference.

## Patterns that already worked

| Pattern and source | Why it worked | How it fails | What Atlas borrows | What is new here |
|---|---|---|---|---|
| Replace a system beside the running one, behind an unchanged interface, then delete the old ([Strangler Fig](https://martinfowler.com/bliki/StranglerFigApplication.html)) | The old system stays the reference, so every difference is visible before anyone depends on the new one | Both run forever and cost double | Old and new builds judged by the same specs and a page-by-page diff, with a named moment for deletion | The diff compares two bundlers' HTML: whole heads, links, visible text, bytes |
| A desktop shell fed a static folder by Vite ([Tauri's Vite guide](https://v2.tauri.app/start/frontend/vite/); fallback read in Tauri's source, above) | The shell needs files and a fixed dev port, which is Vite's native output | A one-document app breaks on reload where the host has no fallback | The pairing, and history addresses instead of hash addresses | The same bundle also feeds a prerendered website |
| Client-only products leaving Next for Vite and a route table ([Plane](https://plane.so/blog/why-did-we-migrate-plane-from-nextjs-to-react-router-vite), [Railway](https://dev.to/sarah-railway/moving-railways-frontend-off-nextjs-2hg5); search summaries only, not read in full) | Page logic was lifted out of route files first, so routes could be regenerated from a table | Metadata regresses unseen; a long branch rots | The order: table first, switch, delete | Atlas's route files are already thin, so the lift is done |
| Build-time prerender with the framework's static renderer ([Vite's SSR guide](https://vite.dev/guide/ssr), React's `prerender`; summaries only) | One client bundle plus a script that renders each route to a file needs no framework | The page and its hydrating script disagree; the page list drifts from the router | A script over one route table | Per-language pages with a message subset each |

## Problem and alternatives

The slow build is the symptom. The cause: Atlas pays for a server framework to get static files,
then maintains six corrections to its output (Today, third bullet), and agents arrive with Next
habits the repository must talk them out of (`AGENTS.md:173-177`).

**Ranked.** 1. The app on Vite: the daily wait and the peak memory of every parallel session come
back, and it proves the swap under the whole suite. 2. The website on Vite: no visible gain, but
Next cannot go without it, and it carries the search risk. 3. A different address format in the
app: no person can see it; it costs 466 test navigations, two Rust scripts and the scripts that
verify the installed app. First is 1, next is 2, and 3 waits under Later.

| Way | Value | Usability | Feasibility | Local-first fit | Verdict |
|---|---|---|---|---|---|
| Keep Next (status quo) | None gained | Familiar; agents' habits fit | Free | `next/font/google` fetches a font at build (Next's documented behaviour, not re-observed); telemetry must be switched off (`next.config.ts:16`) | Lost: the cost recurs on every build |
| Vite for the app, Next for the website | Most of the dev gain | Two toolchains, two translation set-ups | Smaller move | Same | Lost: every correction script stays, and the owner asked for one toolchain |
| Keep the Next API on Vite through a compatibility layer (vinext; not evaluated beyond a search summary) | Build gain | `app/` and Next habits stay | Young; depends on a re-implemented framework | Unknown | Lost: keeps a framework surface Atlas uses only to write files |
| **Vite, an Atlas-owned router and prerender script** | Build, dev loop, memory; six correction scripts deleted | One command set; one route table | Six slices | Build needs no network | Chosen |

**Address format in the app.**

| Option | What breaks | Verdict |
|---|---|---|
| Keep `/<language>/<screen>/?query#hash` on the History API | Nothing: Tauri's fallback serves the one document for every path | **Chosen** |
| Drop the language from the path, read it from the stored setting | 466 navigations, both Rust scripts, `deploy-macos-app-local.mjs:17`; app and site would speak two grammars through one `Link` | Later 1 |
| Hash addresses | 39 files reading `location.search` and `pathname`; the hash is taken by heading anchors | Lost |
| No address (memory only) | Reload loses the screen; no test can open a screen; the install link and verifier scripts stop working | Lost |

**Decisions.**

1. **Router.** Atlas owns a small router over the History API, exported from `@/i18n/navigation`:
   `Link`, `useRouter` (`push`, `replace`, `back`), `usePathname`, `useSearchParams`, `notFound`,
   and one route table in `src/app/routes`. No router package: the surface in use is four hooks,
   one component and three calls, and 67 test files already mock that module. Its contract:
   - (a) A path change is a transition. The address changes in the same commit as the screen, so
     a screen still rendering reads its own address from `window.location`.
   - (b) There is one history writer. The six direct writers move onto `guardedHistoryWrite`,
     which keeps the entry's state when the caller asks and tells the router, so
     `useSearchParams` and `usePathname` readers update; lint rejects `history.pushState` or
     `replaceState` anywhere else.
   - (c) `replace` takes a path that already holds a language without adding another; the
     language switch uses it, so `/en/x` becomes `/ko/x`, never `/ko/ko/x`.
   - (d) Inside the app, a same-origin link is a router navigation. After each, `document.title`
     is the new screen's title and a polite live region announces it; `#<heading>` on arrival
     scrolls that heading into view; Back and Forward restore scroll as Next does at slice 1's
     base, which the contract spec records first. In a plain browser, `Link` is an ordinary
     anchor: moving between public pages is a page load (decided by lead 2026-11-27).
2. **One bundle, two folders.** `pnpm build` writes the app folder (`src-tauri/target/desktop-frontend`)
   and the site folder (`out/`). The app folder holds one `index.html` and what the bundle
   references, nothing else (criterion 7 replaces the exclusion list). That `index.html` carries
   the loading picture's `mapEntry.mapComing` and `mapEntry.loadingDetail` in all four languages;
   its inline boot script sets `lang` from the path, else the stored choice, else the system list
   (`src/i18n/detect-locale.ts:13-24`), and `data-shell`, before first paint; CSS shows the
   matching language (decided by lead 2026-11-27). A reload of a non-map screen therefore shows
   the map's loading picture, not that screen's neutral frame. The site folder holds the same
   bundle plus one prerendered file for every route and language Next exports after the removal,
   `404.html`, `sitemap.xml`, `robots.txt`, `llms.txt` and `llms-full.txt`.
3. **Prerender.** An Atlas script renders each public route of the table with React's `prerender`,
   which waits for every suspended part, so a `lazy` part on a public page arrives whole; today
   no public page holds one. For an app address it does not render the screen: it writes the two
   faces the removal spec defines, the app-only page and the loading picture, so the map never
   runs in Node. A page's head comes from `buildPageMetadata`'s facts plus the root head
   (Today), its `<html lang>` from `LOCALE_META`, its data from a non-executing JSON block.
   Social cards stay the PNGs `pnpm og:build` writes. No new dependency.
4. **Translation.** `use-intl` replaces `next-intl`: same hooks, no Next peer. Loading stays as it
   is: one catalogue chunk per language in the app, the listed subset inlined per public page.
5. **Fonts, images, lazy parts, CSS, variables, policy.** Fonts become plain `@font-face` rules;
   JetBrains Mono, kept, ships from `@fontsource-variable/jetbrains-mono` (OFL-1.1), so the build
   fetches nothing, and slice 1 adds its license to `NOTICE.md`, which already ships it without
   one. `next/image` becomes `<img>` with the same attributes. `next/dynamic` with `ssr: false`
   becomes React `lazy`. Tailwind runs through `@tailwindcss/vite`, and `app/globals.css` lists
   every `@import` before `@source`. The app's `index.html` holds no `<style>` element and no
   `style` attribute, and the bundle creates no `<style>` at run time: CSS arrives as files, because
   the WebView's nonce disables `'unsafe-inline'`. The boot script stays the document's one
   inline script. `NEXT_PUBLIC_*` becomes `ATLAS_PUBLIC_*` in slice 4a, in one commit across
   `src`, `scripts`, `.github/workflows` and `.env.example`; until then Vite defines the old names.
   `NEXT_DEV_ALLOWED_ORIGINS` becomes `ATLAS_DEV_ALLOWED_HOSTS`; `NEXT_TELEMETRY_DISABLED` and
   `NEXT_PUBLIC_OATLAS_FIRST_RELEASE_PENDING` (`.env.example:15`, read by no product file) go.
6. **New dependencies, three, each replacing one.** `@tailwindcss/vite` for `@tailwindcss/postcss`;
   `use-intl` (MIT, read), made direct, for `next-intl`; `@fontsource-variable/jetbrains-mono`
   for the build-time download. The first's license was not read; `pnpm licenses:check` on the
   slice-1 branch decides (`docs/engineering/third-party-code.md`, rule 5).
7. **Commands.** `pnpm dev` is `vite --host 127.0.0.1 --port 3000 --strictPort`; Playwright passes
   `--port`. `pnpm build` is type check, bundle, prerender, reports; `pnpm typecheck` is
   `tsc --noEmit`; `ATLAS_BUILD_SKIP_TYPECHECK=1` and `pnpm build:static`'s reuse stamp keep their
   meaning. Browser specs keep both modes; in static mode a spec that opens a public page is
   served the site folder and every other spec the app folder, on two ports.

## Flow

1. When a contributor or agent runs `pnpm dev`, Atlas serves one document on `127.0.0.1:3000` for
   every path; a second server on the same port exits naming the port. A plain browser sees the
   public pages and the app-only page; the map opens under `pnpm desktop:dev` or the faked app
   runtime.
2. When they run `pnpm build`, Atlas writes the app folder and the site folder and prints first-load
   sizes for the app's map and the site's download page.
3. When a person launches the installed app, the window loads one document whose first frame is
   the loading picture in the stored or system language, then the map or first run.
4. When they press a destination or select a concept, the address changes, the title updates, and
   no document loads.
5. When they switch language, the first path segment changes in place; query and hash are kept
   byte for byte and the open folder stays open.
6. When an agent's install link arrives, the app opens `/<language>/mcp/?tab=connectors&install=…`
   and shows the pre-filled form, as today.
7. When a visitor opens a public address, the host returns its prerendered HTML in that language;
   the words are readable before any script runs. A link to another public page loads that page.
8. When a visitor opens an address no route has, the host returns `404.html`; an app address
   returns the app-only page the removal spec defines.
9. When an agent, from habit, writes `import Link from 'next/link'`, adds `app/…/page.tsx` or types
   `'use client'`, lint fails with the sentence under Copy. The agent is wrong and is told where
   the route table is.
10. When the measurement in criterion 1 does not meet its margin, the move stops after slice 2 and
    both slices' files are deleted. The evidence was missing, so nothing else is built on it.

## Edge cases

- **Zero.** A language without its own changelog still gets the page, canonical to the default
  language's (`src/shared/lib/public-pages/page-metadata.ts:31-35`).
- **One.** A fork with one folder under `messages/` builds one language's pages; the list is
  derived, never written twice.
- **Largest measured count.** 160 HTML files before the removal, 52 of them the 13 guide pages in
  four languages. The count must equal Next's at the same commit (criterion 3); it comes from the
  route table and is not pinned.
- **First run.** No stored language: the boot script and the app agree on the system list.
- **Hangul input.** `?p=` and `?slug=` values with Hangul survive a language switch and a reload
  byte for byte (`LocaleSwitch.tsx:17`). React stays 19.3.1, so composition handling does not change.
- **Moved, renamed or unreadable folder.** Unchanged: the bridges own it, not the bundler.
- **Two at once.** Two worktrees build into their own folders; peak memory per build is the number
  that decides how many fit (criterion 1).
- **Offline.** After `pnpm install` a build needs no network. The app embeds every chunk.
- **Fork under a sub-path.** With `ATLAS_PUBLIC_BASE_PATH` set, the site bundle is built a second
  time with that base; the app folder is always built for `/`.
- **Updating from a Next-built app.** The origin does not change, so the stored language
  (`ontology-atlas:locale`), text size and remembered folder persist.
- **Windows.** The build writes both folders with `/`-separated paths on every platform, as
  `stage-desktop-frontend.mjs:49-51` did.
- **The updater feed.** `out/update/latest.json` (`package.json:60`) stays at its address.

## Out of scope

- A different address format in the app, a bundle without website-only code, and a stricter
  website script policy: each is a slice under Later with its reason.
- Moving `app/styles/**` and `app/globals.css`: 118 files name those paths; after slice 4 `app/`
  holds only them and the move is its own rename.
- Any change to what the website shows or which routes exist: the removal spec owns that.
- The addresses MCP hands out (`traversal-analysis.mjs:536`): a public MCP contract.
- Server rendering at request time: forbidden (`forbidden.md:32-33`).

## Slices

Before slice 1 branches, the removal spec has merged to `main` whole, its test-host slice first and
alone. While it is open, only criterion 1's tooling and a Next baseline on today's `main` may be

## Risks

1. **Search visibility drops because a public page changed unseen.** Answer: criterion 3 compares
   whole heads, links and text while both builds exist and is a merge condition on the switch; the
   first Vite deploy stops unless IndexNow reports zero changed pages; `seo:check` and
   `verify-hosted` stay as gates.
2. **The installed app fails where Chromium specs cannot see**: the nonce that disables inline
   styles, frozen prototypes in strict-mode modules, module loading from the app's own origin,
   WebView2 on Windows. Answer: the style rule and its planted probe; criterion 2 freezes
   `Object.prototype`; criterion 5 runs a local installed app before slice 2 exists; the Windows job
   runs the verifier.
3. **Slice 4a collides with every open UI branch, or agents keep writing Next.** Answer: 4a is a
   script, run again after each merge of `main`; it starts when no other UI branch is open, which
   the owner's finish-before-starting rule already asks; the lint sentence names the right place.

**Rollback.** Before slice 3: delete slices 1 and 2's files. The website switches at slice 3's
merge with no beta of its own; until 4a, reverting slice 3's merge restores the Next build, the
website included. Slice 4a is the point of no return. It starts only after: the updater moved the
last Next-built stable to the Vite beta, keeping folder and language; criterion 5 passed on that
beta; the Windows verifier passed on its commit; and the Vite site has been live 7 days with
`verify-hosted` green. The beta carries no change to the MCP server's language: the MCP server's

then 3's; a Next-built patch release can follow a Vite-built one because the app's origin and
