# Read project planning documents in place

## Person and moment

The owner develops with a coding agent in a CLI and wants Atlas to be the place they inspect the surrounding work without opening an IDE: planning documents, downloaded design images, code changes and evidence. They ask Atlas to make repository Markdown and downloaded Figma images easy to inspect and automatically keep track of them, with a separate navigation destination. They delegated the choice of approach and implementation. These are the owner's reported workflow and request; no observation yet shows how another person discovers or understands the resulting screen.

The owner prioritizes PC use and the installed macOS app. The web layout must also work across viewport widths, including narrow screens, with usable navigation, reading and recovery. A separate mobile product or mobile-only agent runtime is not part of this slice. Browser folder access remains conditional on the safety proof below; an unsupported environment must still display its explanation accessibly at any width.

The first acceptance walk therefore starts with the actual Atlas repository and an independent temporary project containing a planning question, Markdown, downloaded-design image, observable code history and an explicitly recorded ontology concept. The person finds the plan and checks its image, selects a period containing a known commit and a file touched during that period, inspects the commit record and the period's repository-wide endpoint comparison as distinct evidence, and returns to the same plan; they then inspect the chosen concept and return again. They can also find a subsequent document change without manually importing a copy. A screen that only displays a file list, or a green test without an installed-app walk, does not prove this recovery. The walk records which question was answerable and which evidence remained unavailable; it does not claim measured productivity from a single trial.

## Today

- Library groups raw originals, Wiki pages, ontology documents and check history in one destination. Its raw-source import copies picked files to the open vault's `sources/` (`src/features/library/lib/sources/add-sources.ts:8`; `docs/ARCHITECTURE.md:416`). Library remains the home for its existing copied sources, reviewed Wiki and ontology work.
- Native document discovery returns metadata, not document bytes; its extension list excludes Markdown and image formats (`src-tauri/src/library.rs:37`, `src-tauri/src/library.rs:532`). Its depth limit and unsuccessful nested reads can stop a walk without marking the whole report incomplete (`src-tauri/src/library.rs:85`, `src-tauri/src/library.rs:470`). It is not a complete live index of a project's planning files.
- The existing source picker adds to the shared source registry, and the vault picker grants vault operations (`src-tauri/src/source_access.rs:3`, `src-tauri/src/vault_grants.rs:26`, `src-tauri/src/vault_grants.rs:143`). Neither picker establishes an isolated Planning-only read grant. The existing vault watcher starts from a granted vault root (`src-tauri/src/vault/watch.rs:32`); this does not establish change notifications for an independently chosen planning folder.
- The first recorded 2026-11-01 repository scan found 833 Markdown paths under Atlas's `docs/` using `rg --files docs -g '*.md'`. That is an inventory of this checkout at that time, not a performance result, semantic assessment or assertion about another project.
- The current web CSP permits local blob images and does not permit remote image origins (`src/shared/config/web-content-security-policy.ts:1`). The source-folder picker is a native bridge; the browser has no native absolute source path (`.claude/rules/surfaces.md:35`). Native and browser support for the new task have not been measured.
- A temporary macOS Python `openat` experiment accepted ordinary Markdown and an in-root parent-relative image while refusing planted parent, leaf and root symlink replacements. Separate temporary fixtures showed that a selected-folder hardlink can share bytes with a path outside the folder, and a transient second link can exist even when the observed link count is one before and after the read. On this Mac `/tmp` is a legitimate alias of `/private/tmp`, so rejecting every alias in an absolute picker path also rejects a normal selection. These are local syscall observations, not Rust, native-picker or Tauri IPC proof.
- The existing Briefing reads current-branch first-parent commit history; it explicitly excludes uncommitted work (`docs/features/change-briefing.md:14`). Commit messages and a chosen file's code comparison are distinct: the latter compares repository-wide endpoints for the selected period, not one selected commit, and can include intervening out-of-period changes (`docs/features/change-briefing.md:48`). The Git workbench's current changes concern the open vault, not an arbitrary selected project source (`docs/features/git.md:31`). Neither is evidence that a CLI agent's uncommitted project edits have been inspected. Briefing retains its selected period and source in session memory (`src/views/change-briefing/ui/ChangeBriefingPage.tsx:38`).
- Library's source, Wiki and ontology boundaries stand under [c5472b7d](../records/decisions/2026-09-14-library-ontology-workspace-c5472b7d-bb5f-475d-b31a-523bd09fdc89.md). The fully read `capabilities/library-workspace` and `elements/vault-source-import` describe gathering originals, not automatic acceptance of meaning. Their review state was not confirmed during this pass.

## Problem and alternatives

Ranked by user value: (1) carry the person's planning-to-evidence review across Markdown, design images and an explicitly selected existing code-history or ontology view, then return to the same place; (2) discover additions and external edits without re-importing copies; (3) make this work understandable and reachable without an IDE. A current uncommitted source-diff view is the highest-value follow-on because existing history excludes it. Editing, model-generated organization and inferred semantic links follow only after the read/review journey is demonstrated. The request names a distinct work moment; it does not establish that a separate destination is inherently easier for new users.

| Option | Value and usability | Cost, feasibility and local-first fit | Decision |
|---|---|---|---|
| A: use current Library import | Existing originals and citation work remain familiar | Copies must be imported, and project Markdown and images are not automatically read in place; no new source grant | Retain for its existing job; does not meet this request |
| B: add project originals inside Library | One Library destination; fewer rail entries | Readers must distinguish a live project folder from copied originals and Wiki pages in an already multi-purpose space; requires the same read boundary | Defer; revisit if a separate destination confuses readers |
| C: a Planning destination for one selected folder | Direct access to a project's observed files; reader and image share one context | Adds navigation and a narrowly scoped native-to-renderer read; requires new coverage and permission handling | Choose, as explicitly requested and delegated |

Direction C has a folder-and-file index and one reader, not a second Wiki or a second ontology. Explicit navigation to existing source history and the map, and a return to the same document, complete this slice's review loop. The person selects the repository, dates and concept; Atlas does not infer that a file, commit, image or concept is related merely because it was opened from Planning. Existing Library links, imported originals, drafts, citations and meaning review remain intact. The prior combined-Library decision is retained for those jobs; the lead records the separate project's read-only surface and its dissent before implementation. Reconsider C if a fresh reader cannot distinguish Planning from Library or if it requires broader access than the chosen folder. Product value remains a hypothesis until the installed walk and a later independent task show that the material helped the developer (`docs/PRODUCT-DIRECTION.md:24`).

Product routing: `po:route` with `evidence=observed`, `outcome=orient`, `change=surface-inventory`, `truth=unchanged`, `transfer=affected`, `agent-write=unchanged`, and `human-correction=unchanged` returned `review`, `risk=meaning`, `record=yes`, and `moment,evidence,boundaries,smallest-slice` lenses. Transfer is affected because selected project bytes cross the native-to-renderer trust boundary; no network or model transfer is authorized. Route additions and the new read boundary require a decision fragment and an independent spec review.

Independent spec review returned **prove first / revise**: neither a dedicated grant nor confined browser reads exist as an established capability. Before selecting a native or browser implementation, probe the grant, traversal, initial picker-to-descriptor handoff, legitimate canonical aliases, root replacement and actual rendering boundaries in the acceptance criteria below. The temporary Python experiment does not complete these probes. This spec states required behavior, not evidence that those probes have passed.

A subsequent independent review of the picker experiments recommends a narrower native boundary: the protected identity begins when the selection callback successfully opens the root directory descriptor, not when the person first sees or selects its path. A replacement before that open cannot be ruled out by the picker evidence and could expose unintended document bytes to the renderer; neither external hardlink aliases nor secrets in document content can be ruled out. The interface must describe those limits without suggesting otherwise. This is a technical boundary decision, not semantic acceptance or proof that the implementation passes.

## Flow

1. When the person opens Planning, Atlas explains that this view reads a selected local folder and leaves its originals in place. If a connected project has an accessible `docs/` directory, Atlas may present it as a candidate, but only the person's folder selection creates a Planning-only, read-only grant for the current session. This grant is not placed in the existing source or vault registries and cannot enable their commands. It is scoped to the selected identity and session, retained across the explicit review-and-return journey, and revoked on replacement or session end. A separately granted vault or source keeps its independently established authority; it is never attributed to the Planning selection. Otherwise the picker starts from the normal platform choice. Cancel keeps the previous selection, if any.
2. When a folder is selected, Atlas lists readable Markdown and supported local images by folder and relative path. A file observed to have multiple hardlinks is skipped and counted, as are other excluded categories; excluded secret names are never displayed. The folder path and scope checked against the opened descriptor, actual scan coverage and last successful observation time remain visible. The path helps the person recognize the opened scope but does not authenticate the inode originally seen or detect an attack. The view explains that files may change before Atlas detects the change. A file-name/path search narrows the last observed inventory; it does not claim to search file contents or excluded material.
3. When the person selects a Markdown file, Atlas opens text read from it in a readable pane with its relative path and observation time. Safe relative image references open within the same selected folder, including a `../` that resolves inside that root. A selected supported standalone image opens in the same reader. Local originals are not copied or moved into the vault.
4. When the person wants to compare the plan with code evidence, Atlas offers **Open source history**, says that it contains current-branch, first-parent committed history only and excludes uncommitted changes, and opens the existing Briefing for a repository and dates the person chooses. The person selects a period containing a known commit and a file touched during that period, then inspects the commit record and the period's repository-wide endpoint comparison separately. The comparison names its revisions and scope; it is not attributed to that individual commit and may include intervening changes outside the chosen dates. When they choose **Open ontology map**, they select and judge the concept there. Either action retains the source planning document's session context for an explicit **Back to planning** return. No automatic association or change verdict is asserted. If there is no suitable repository, history, ontology or evidence, the respective screen states that gap and the person can still return to the plan.
5. When the person returns, Atlas restores the same selected relative file, reading position and navigation focus only after its folder grant and file identity are rechecked. If the file or folder changed or disappeared, Atlas presents a newly dated re-read or the applicable unavailable state and does not silently restore another file. The original reader's selection and return remain usable without an agent.
6. When an agent or person adds, changes, renames or removes a file while this screen is active, an observed event or scheduled recheck marks the last observation unconfirmed immediately and starts a bounded reread. Successful reread updates its observation time; failure keeps the unconfirmed or unavailable state and recovery action. Changes can happen before an event or the next scheduled reread, so no observation claims uninterrupted real-time completeness. The current file and selection do not jump to a different file when another item changes. Manual refresh remains available.
7. When the folder, grant or current file is moved, replaced, inaccessible or cannot be completely scanned, Atlas marks the previous observation unavailable or partial, says what can be recovered, and offers retry or folder selection. An earlier folder's delayed read must not replace the new selection. A failed or incomplete scan cannot appear as a complete empty folder.
8. When a document points outside the chosen folder, to a remote image, or to a missing, unsupported or unsafe image, Atlas keeps the document readable and identifies the unavailable image. It does not silently fetch another origin or show the image as evidence that the document's claims are true.
9. When a person changes projects, Atlas revalidates the chosen folder's actual access. After an app or browser restart, the person selects the Planning folder again; a remembered label, path or separate source grant alone is not Planning authority. No AI request, file edit, accepted ontology meaning, source binding change, or Library import is triggered by reading or refreshing.

## Edge cases

- Empty, one-file and the recorded 833-Markdown-path folder must be distinguishable from partial enumeration. Large or deep folders use bounded listing and explicitly report omissions; no particular capacity or latency is promised before measurement.
- Unicode and Hangul input, encoded spaces, mixed case, duplicate file names and literal relative paths retain the exact selected file. In-root `../` image links work; traversals leaving the selected root do not. Absolute paths, `file:` URLs and remote images in documents are not followed. After the selected root has been established, symlink components inside it are never followed; a legitimate canonical alias encountered while establishing the selected root is a separate, identity-checked case described below.
- First selection, cancelled selection, folder rename or replacement, missing permission, unreadable descendants and app restart retain a recovery action. Browser and app grants are independent. The app must not offer its own download from inside the installed app.
- A content change, including an equal-size and equal-timestamp replacement, can occur before an event or scheduled recheck notices it; the UI always describes a dated observation, not continuous certainty. On a received event, screen resume, watch failure or scheduled recheck, mark the last observation unconfirmed immediately and re-read the selected file and bounded listing. Debouncing may delay reread but not the unconfirmed label. Keep that label after failure, stop or loss of visibility until a successful recheck; manual refresh is available. Completion from an older folder, scan or file cannot replace a newer selection. Tests measure actual detection delay and failure recovery without treating a measured duration as an always-current guarantee.
- A plan, image, source history and ontology concept may concern different work. Destination links identify only where they lead; the person picks the repository or concept and compares the evidence. Missing commits, uncommitted source edits, empty ontologies and unsupported histories remain gaps rather than negative findings.
- Offline use reads local files and needs neither an account nor a model. External links and images are inert unless a separately authorized existing action handles them. Untrusted Markdown and image bytes must be tested through the real display path, not only a sanitizer or URL helper. Render Markdown without executing HTML or scripts. Read supported images under explicit byte and decoding bounds; unsafe SVG must be rejected or sanitized with tested external-resource and script blocking before display.
- Never scan secret-named files, dotfiles or system/build directories. Report exclusion categories and counts without exposing excluded secret names in the UI, error details, logs or navigation. A filename rule does not detect secrets embedded in otherwise permitted document or image content; the UI must not claim it does. Nothing read here is automatically transmitted to an agent or model.
- Native traversal must be anchored to the actually opened selected-root directory and use no-follow descriptor-relative operations for every parent and leaf. The guarantee concerns opening entries beneath that selected directory without following symlinks outside it; it is not a guarantee that their bytes have no other name, hardlink or open file descriptor outside the folder. Where inspection identifies multiple hardlinks, skip the file and report the category/count. Rechecking link count and identity before and after reading is conservative: link count one at both moments still cannot prove that no external reference existed between them. Do not claim that this is a content-provenance or secret-detection guarantee.
- Open the root descriptor during the native selection callback, before the picker returns. Compare both `validateURL` and the picker's final successful result with the last candidate descriptor and refuse the grant itself on mismatch. Bind the session grant to that opened identity only after successful selection. Verify that identity before publishing a result and again on recheck; replacement or loss after the descriptor opens makes the observation unavailable rather than silently adopting a new root. A changed selection discards the previous candidate; cancellation or a missing, stale or inconsistent callback must not create a grant. A legitimate `/tmp`-to-`/private/tmp` canonical alias should work where it identifies the opened directory. Allowing this alias during root establishment does not allow following symlinks in entries beneath the established root. The interval before descriptor acquisition is outside this guarantee and must be exercised and reported rather than represented as protected. The implementation and proof are pending. On web, support requires a real target-browser/OS probe of parent and leaf replacement, prevention of reads outside the selected handle, and the ability to observe and omit a file with multiple hardlinks. If the browser cannot prove the last ability, it is unsupported; a directory picker, handle or API presence alone does not pass these probes.
- A fresh Planning-only session grants no existing vault read/write or source inspection command access to the chosen folder or its parent. Calls to those existing commands must be rejected in a fixture without independent grants. A pre-existing independently granted vault or source may retain its previous capabilities, but selecting it in Planning must not create, widen or prolong those capabilities or change project binding.

## Out of scope

- Editing, creating, moving, deleting, converting or copying project originals: reading and change visibility do not require mutation.
- Agent tagging, automatic summaries, semantic classification, Wiki creation, ontology relations or accepted meaning: none follows merely from a file or image being present.
- A live uncommitted project-code diff, a new per-commit diff and an embedded coding-agent runtime: the current Briefing covers committed history and period endpoint comparisons only. A separate future review must add those abilities rather than labelling existing vault Git or commit history as the agent's current work.
- Sending any content to a remote service or model, connecting a Figma account, fetching remote Figma files, or background transfers: the request concerns files already downloaded to the person's disk.
- PDF and arbitrary binary previews: leave unsupported files explicit until their safe rendering and scope are separately reviewed. SVG is supported only if the safe handling in Edge cases is proven; a failed safety check is an explicit unsupported state, not a raw render.
- A shared, canonical catalog of project documents or a promise of browser/native permission persistence: files remain authoritative and this slice's derived list can be rebuilt.
- A separate mobile product or mobile-only agent runtime: the owner prioritizes the PC workbench. The same web surface still requires complete responsive behavior and an accessible unsupported-permission fallback at narrow widths.

## Acceptance criteria

1. Given the real Atlas `docs/` folder and a temporary project with a concrete planning question, a Markdown plan and a downloaded-design image, when the person uses the freshly built installed app, then an actual-window walk captures entry, text and image and their relative paths. Record the answer and unresolved evidence; do not claim improvement without a fair comparison. Capture the first failure and compare original bytes before and after. Both onward-and-return paths in criterion 6 are separately mandatory.
2. Given no folder, picker cancellation, an empty folder, one file, an unreadable child and the recorded large corpus, when scanning in the installed app and each browser/OS combination whose safety probe passed, then focused integration tests and the installed walk distinguish complete, partial and unavailable states. Failed or untested browser/OS combinations explicitly show unsupported. The 833-path baseline must not silently become a complete 500-item listing; coverage and limit counts must agree with the observed scan without exposing excluded secret names.
3. Given nested Markdown linking to a valid in-root `../images/` file and a standalone Figma-exported image, when opened through the actual installed reader and each supported browser reader, then tests prove the correct image bytes appear beside the exact source path. Untrusted Markdown, absolute paths, encoded traversal, remote URLs, missing files, malformed images, size limits and unsafe SVG are blocked or disclosed through that same render path; planted script and network probes do not execute or send traffic.
4. Given a fresh isolated session with a Planning-only grant, parent and leaf symlink substitution, ungranted root, secret-named files and selected root replacement, when exercising inventory and open through actual Rust commands and Tauri IPC, then descriptor-relative confinement proves symlink traversal cannot open entries outside the selected directory and excluded secret names do not leak; root loss leads to recovery. A prior Python syscall experiment is not Rust IPC proof. Exercise an outside-origin hardlink and a temporary-link race: a known multi-link file is skipped and counted, but neither a one-link observation nor a passing race test is described as proof that no external name or open descriptor shares the bytes. Through the real native picker, verify a legitimate `/tmp`-to-`/private/tmp` alias, cancellation, changed and repeated selection, a missing callback, and replacement after root-FD acquisition; stale or inconsistent identity must refuse and offer reselection. Exercise replacement before FD acquisition separately and preserve the limitation rather than claiming it is detected. Symlink entries inside the established root remain disallowed. Invoke existing vault read/write and source inspection commands against the Planning-only folder and parent and assert refusal. Repeat with an independently pre-granted source or vault and prove its prior authority remains separate and is not widened. For each supported browser/OS, test real handle parent/leaf replacement, outside-grant reads, and actual detection and omission of a multi-link fixture; inability to observe or omit the fixture, or missing proof, means unsupported.
5. Given external create, same-size/same-time edit, rename and deletion while the screen is active, when an event or scheduled recheck is observed, then the installed-app walk and focused tests mark the earlier observation unconfirmed before rereading and display a new timestamp only after successful verification. Test detection delays, event loss, sleep/resume, watcher failure, permission failure and reversed asynchronous project reads; never assert that an event detects every change immediately.
6. Given a plan opened from one folder, prove both paths independently in the installed walk and focused tests: (a) open Briefing, choose a period containing the known first-parent commit and a file touched during that period, inspect the commit record and separately inspect the period's repository-wide endpoint comparison with revisions and scope visible, then return; (b) open the ontology map, deliberately select the known concept, inspect its declared meaning/evidence and return. The comparison must not be described as that commit's individual diff. Both paths restore the correct document, reading position and focus after revalidation. If the source changed, grant is gone, a project was switched or the app restarted, show the correct rechecked/recovery state instead. Missing history or ontology stays visible; history is never labelled as uncommitted work, and no association or verdict is invented.
7. Given first entry, long Hangul names, image failure, partial results, unsupported-browser fallback and the large corpus, when the routed design audit, full responsive width matrix and user walkthrough run, then controls, reading, navigation and recovery remain usable at narrow and wide widths, text and paths remain readable, and navigation distinguishes Planning from Library. Supported layout at a width does not establish filesystem permission on that device. Fresh computer-use captures cover baseline, material checkpoint and final state, led by the installed app.
8. Given the reviewed implementation, when changed checks and every recommendation pass and the app is rebuilt, reinstalled and launched, then a local offline walk verifies no model request, network fetch, source write, Wiki import or ontology change was caused by viewing or refresh. Structural or test success alone does not establish developer productivity or semantic correctness.

## Risks

1. A reused path or renderer-asserted root reads outside the person's folder. Probe parent and leaf replacement, ungranted root and secret-name fixtures through the real native command, not only a path-normalization unit test.
2. A missed event, partial traversal or stale async response presents old or incomplete material as current. Probe deliberate watcher failure, same-metadata edits, omitted descendants and reversed project requests; refuse a current/complete claim until rechecked.
3. A second destination is hard to discover or confused with Library copies. Walk a fresh reader from a real task to a project original and back, with both destinations visible; revise the navigation if the reader cannot explain the distinction.

## Later

1. Add a reviewable uncommitted project-code view after the first journey exposes the existing committed-history gap; retain exact source identity and never claim the vault Git view covers project changes.
2. Propose organization or links only after a real task establishes that the reader helps; show exact source and a reviewable diff before any authorized write.
3. Consider a deliberate Figma connection, additional formats or an in-app agent runtime only after their separate user need, transfer, permissions and recovery boundaries are reviewed.
4. Consider persistent folder selection only after a grant can be restored and revoked safely on each surface; a remembered path is not sufficient.

## Owner question

None. The owner requested a distinct navigation entry and delegated the implementation choice. The selected read-only scope can be revised after the independent spec review or the installed-app walk.
