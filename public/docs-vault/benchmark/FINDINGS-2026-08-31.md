# Paired lifecycle findings — 2026-08-31

## The decision this run can inform

Atlas should earn its long-term place by improving a person's or an agent's
business-to-code decision: where work belongs, what boundary it crosses, what
impact is actually recorded, what evidence supports the claim, and what the
next verification action is. It should not claim that every source lookup gets
faster, or that more nodes automatically mean more value.

The first paired run is a **feasibility pilot**, not general product proof. It
tests consumption of a prepared ontology. Bootstrap and maintenance cost remain
separate because a vault that helps after preparation can still be a poor
long-term trade if it is too expensive to construct or keep current.

## Protocol

- Subject 1 (`greenfield`): the small feature-sliced `commerce-fsd` fixture.
- Subject 2 (`brownfield`): the multi-package `collaboration-monorepo` fixture.
- Each subject was copied to a fresh temporary workspace for every cell.
- `off` had source/product documents only; it had no Atlas folder, MCP server,
  or golden answer file.
- `on` had the identical source plus a validated prepared Atlas folder and the
  read-only Atlas MCP server.
- The same `gpt-5.6-sol` Codex CLI and fixed task prompts ran in three fresh
  repeats per cell.
- The runner required MCP traffic in `on`, rejected MCP traffic in `off`,
  removed `golden.json` from every subject, and wrote raw transcripts with a
  caller-supplied run id.
- Machine coverage counts required slugs, paths, and an explicit bounded
  unknown signal in the final structured answer. It does not judge meaning,
  unsupported rationale, citation truth, or user usefulness.

The exact runner is [`scripts/benchmark-lifecycle.mjs`](../../scripts/benchmark-lifecycle.mjs),
and the complete raw matrix is [`results/2026-08-31-gb-r3-summary.md`](results/2026-08-31-gb-r3-summary.md).

## Result

| Subject | OFF coverage | ON coverage | Delta | Content passes OFF → ON | ON median time delta | Arm integrity |
|---|---:|---:|---:|---:|---:|---:|
| Greenfield-shaped fixture | 0.25 | 0.875 | **+0.625** | 0/6 → 4/6 | +17.2 s | 12/12 |
| Brownfield-shaped fixture | 0.2834 | 0.7389 | **+0.4555** | 0/6 → 2/6 | +33.2 s | 12/12 |

Across the 24 cells, every process completed and every arm had the expected
Atlas exposure. The `on` arm used a median of 4 MCP calls per greenfield cell
and 4.5 per brownfield cell; `off` used zero. The raw transcripts are the
primary evidence for any human semantic grade.

## What the pilot suggests

1. **Boundary and handoff work is the strongest current wedge.** Greenfield G2
   and brownfield B2 gained the most: the prepared vault supplied explicit
   exclusions, ownership, rationale-bearing relations, and a next read path
   that the source did not state as one connected record.
2. **Atlas is not a speed claim.** It was slower in both subjects in this run.
   That is acceptable only if the extra time buys fewer wrong decisions or a
   more trustworthy handoff; token and tool-call savings are diagnostics, not
   the product goal.
3. **Impact is not automatically solved by a graph edge.** Brownfield B1 had
   an on median of 0.4 and an off median of 0.4. The source snapshot contains
   package manifests rather than runtime implementations, so a declared
   product dependency correctly remains weaker than proven runtime impact.
   This is an improvement target, not a reason to widen the claim.
4. **The greenfield result is still conditional.** The prepared vault gave the
   new-project-shaped subject a larger lift, but this run did not charge the
   cost of creating that vault. A real greenfield onboarding run must measure
   time from first Atlas connection through a reviewed usable handoff.

## What this does not prove

- These are internal fixture proxies, not unfamiliar customer repositories or
  a user cohort.
- A required-token coverage score is not a correctness or semantic-quality
  score. Human blind grading still needs to inspect factual claims, citations,
  unsupported rationale, and usefulness.
- This is not a source-hidden field trial. Existing field-trial baseline rows
  measure construction, citation, and vault-only handoff quality separately;
  they do not provide this run's no-Atlas counterfactual.
- Three repeats of two small subjects cannot establish a universal effect or a
  long-term return on maintenance. The next run should use real unfamiliar
  snapshots and preserve the same control protections.

## Improvement backlog from this run

- Replace or supplement the tiny fixtures with one real unfamiliar greenfield
  snapshot and one real unfamiliar brownfield snapshot, while keeping the
  chosen repository outside this repository's files and commit messages.
- Add a human grading record for the 24 final answers: correctness,
  unsupported rationale, path citation accuracy, boundary fidelity, and
  handoff usefulness. Keep it separate from machine coverage.
- Add a deliberate stale-vault arm for brownfield maintenance. Measure whether
  Atlas detects or worsens a changed source boundary before trusting its advice.
- Improve the agent-facing compact handoff so MCP consumers preserve canonical
  slugs and exact relation provenance in their final answer. The G1 and B1
  transcripts still sometimes summarized the concept without returning the
  typed slug set.
- Charge construction and maintenance time before turning this pilot's positive
  deltas into an investment or marketing claim.

## Current long-term goal

> Make a repository's reviewed product meaning a durable, local, queryable
> handoff that compounds across changes: ownership, boundaries, evidence,
> bounded impact, and the next verification path remain inspectable by both a
> person and an AI agent. Earn that claim with paired outcomes after
> construction and maintenance cost; do not earn it with node count or prose
> volume.
