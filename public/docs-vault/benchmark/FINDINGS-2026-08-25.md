# Does the ontology help? — 2026-08-25

> Read this before running the benchmark again. It explains what the numbers can
> and cannot tell you, and why the first three attempts produced numbers that
> looked fine and meant nothing.

## The conclusion, in three sentences

1. **An ontology is worth its cost only where it holds something nothing else
   holds.** When the vault was deleted outright, a coding agent still answered a
   vault question correctly — from `README.md`, `AGENTS.md`, the product docs,
   the generated copies, and git history.
2. **Half of this vault was not that.** 37.5% of it was decisions that exist
   nowhere else; 35.9% was description any agent could re-derive by reading the
   code. Re-sectioning four files, without editing a sentence, moved the first
   number to 51.4%.
3. **The question cannot be answered on this repository.** Not because the
   ontology is worthless, but because this repository documents itself so
   thoroughly in prose that no control group can withhold the answer. Note what
   did *not* substitute for the vault: code comments, not once in nine cells.

The rest of this document is the evidence for those three claims and the rule
they produce.

## The rule

> **If it would disappear along with the source, do not put it in the vault.**

This is now written into `docs/ontology/README.md` and half-enforced by
`tests/contract/vault-section-shape.contract.test.ts`.

Three kinds of knowledge survive that test, and nothing else does:

| Survives | Why code and comments cannot hold it |
|---|---|
| **Membership across files** | Which capability belongs to which domain is not a property of any one file, so no comment can own it. This is also what makes the vault findable at all: `path:` on 75 nodes hands an agent an entry point it had no way to guess |
| **What is *not* there** | You cannot write a comment on code that was deliberately never written. `## Inclusions / Exclusions` is the only home for a decision to *not* build something |
| **Knowing when it has gone stale** | A comment lies quietly when the code moves. Frontmatter carries `uid`, `mtime`, `graphHash`, and `source_changed` |

Everything else — what a module does, how a flow proceeds, which constant is set
where — is a second copy that will drift.

## Claim 1: the vault added nothing here, and we know why

D1 asked a question whose answer is written in the vault and, we believed,
nowhere else: *is code symbol search inside or outside the `mcp-server`
capability?* The vault says outside, in as many words:

```
capabilities/mcp-server.md · ## Inclusions / Exclusions
  Excluded: AST/source search engine, embedding store, model selection/agent
  loop, backend/accounts, auto-saving creation proposals without human approval.
```

Three modes, three runs each, graded against a key pinned to that text:

| Mode | What was on disk | Boundary /3 | Provenance /2 |
|---|---|---|---|
| **none** | vault, generated copies and answer key all removed | 3, 3, 3 | 2, 2, 2 |
| **off** | vault markdown present, MCP server unregistered | 3, 3, 3 | 1, 2, 2 |
| **on** | vault plus the MCP tools | 3, 3, 3 | 1, 2, 2 |

`none` really had no vault — the transcript shows
`rg: docs/ontology: No such file or directory`. It scored full marks anyway, and
said where it had looked:

> "Atlas is not a code index …" — cites `README.md`
> "the exhaustive symbol graph is recorded as being left to deterministic
> code-intelligence tools" — cites `AGENT-MEMORY-POSITIONING.md`
> "`docs/ontology` is deleted in the current working tree, so I read the record
> from git HEAD"

(The agent answered in Korean; the three lines above are translated. The
originals are in `results/2026-08-25-codex-D1-none-r2.txt`.)

The same meaning is written in several places, but **they are not equivalent**,
and the difference decides what the vault is actually for.

| Where | Did it substitute for the vault? |
|---|---|
| `README.md`, `AGENTS.md` | **Yes.** Coding agents read both by default, and `AGENTS.md:14` and `README.md:479` state the D1 boundary directly |
| `PRODUCT-DIRECTION.md`, `AGENT-MEMORY-POSITIONING.md`, `DECISIONS.md` | **Yes.** Reached by an obvious grep on the terms in the question |
| Generated copies | **Yes**, but they are copies *of* the vault. `public/docs-vault/`, `src/entities/docs-vault/data/content.json` |
| Git history | **Yes.** The vault is committed, so `git show HEAD:` recovers a deleted vault. **A vault cannot be withheld from an agent by moving files** |
| Code comments | **No. Not once in nine cells.** |

That last row is the one worth stopping on, because the first read of this
evidence got it wrong.

`dome-view.ts` is 2,057 lines of which 1,080 are comments, and all four academic
citations the vault quotes (Everts, Sun & Perona, van Wijk, Ware & Franck) are
already in the source. It is tempting to conclude that the vault is a second copy
of the comments. **It is not, and the nine `none` cells prove it:** every answer
cited Markdown documents, and not one cited a source file.

The reason is that comments duplicate *content* without duplicating
*reachability*. A comment is only readable by someone already inside that file,
and there is no way to enumerate the comments in a repository — grep only works
if you already guessed the right word. The vault carries `path:` on 75 nodes, so
an agent that knows only *"I need to change how the map rotates"* is handed the
entry point. Nothing in the source can do that, because the answer is not a
property of any one file.

So the two compose rather than compete: **comments hold depth, the vault holds
reach.** What genuinely substituted for the vault here was prose documentation
that agents load anyway — `README.md` and `AGENTS.md` above all.

That is a property of a heavily self-documented repository, not a defect in the
vault. It does mean the promise *"Atlas preserves the meaning that is not in the
code"* is imprecise. The accurate promise is narrower and stronger: **Atlas makes
that meaning reachable without knowing where to look.**

## Claim 2: half the vault was description, and the fix was renaming

All 84 nodes, 151 KB, classified by section:

| | Before | After |
|---|---:|---:|
| Decisions (membership, boundary, exclusion, relation reasons) | 37.5% | **51.4%** |
| Description (re-derivable from the source) | 35.9% | **22.1%** |
| Evidence citations | 13.8% | 13.7% |
| Metadata (`uid`, `slug`, `kind`, `title`, confidence) | 12.9% | 12.8% |

Broken out by kind, the problem was in one place:

| kind | files | decisions before | decisions after |
|---|---:|---:|---:|
| project | 1 | 92% | 92% |
| domain | 7 | 57% | 57% |
| **capability** | **28** | **29%** | **50%** |
| element | 47 | 26% | 26% |

Capabilities are 63% of the vault by size and the part an agent reads most.

**The failure was not length. It was a decision wearing a descriptive heading.**
`capabilities/mcp-server.md` carried one `## Core Flow` of 12,865 bytes: five
lines of actual flow, then twenty-two paragraphs of hard limits, fail-closed
rules and per-language scan boundaries. Every rule was real and unrecoverable
from the source, and an agent had to read 12 KB of prose named "Core Flow" to
reach any of them.

Splitting that one file into `Core Flow` plus six `Constraints: …` sections —
**moving text, editing none** — took the whole vault from 37.5% to 45.7%. Three
more files took it to 51.4%.

Two numbers worth keeping: the top five files held 61% of all descriptive text,
and **57 of the 84 files needed no work at all.**

`tests/contract/vault-section-shape.contract.test.ts` now caps a single section
at 6,600 bytes so the next one gets named instead of buried. When it fails, the
fix is always to name the second idea, never to delete the text.

## Claim 3: the outside evidence agrees on the shape

| Finding | Source |
|---|---|
| Repository context files do **not** generally improve task success, and raise inference cost by over 20%. Instructions are followed; **repository overviews are not helpful** | [arXiv:2602.11988](https://arxiv.org/abs/2602.11988) |
| A **queryable structural index** improves localization and resolve rate at no extra cost per task | [arXiv:2606.22417](https://arxiv.org/abs/2606.22417) |
| Contexts treated as an incrementally updated playbook beat monolithic rewriting; the named failures are *brevity bias* and *context collapse* | [arXiv:2510.04618](https://arxiv.org/abs/2510.04618) |
| A memory layer is itself a source of error: information loss and retrieval misalignment | [arXiv:2605.28732](https://arxiv.org/abs/2605.28732) |
| Frontier agents reach 25% on long-horizon multi-file evolution against 72.80% on single-issue SWE-bench | [arXiv:2512.18470](https://arxiv.org/abs/2512.18470) |

Read together, the deciding factor is not graph versus prose. It is **unique and
queried on demand** versus **restated and loaded in bulk**. Atlas is built as the
former and, on this repository, its content is largely the latter.

## What to do next

1. **Measure somewhere else.** `.claude/skills/ontology-field-trial/` already
   exists for exactly this: build a vault on a repository nobody here knows, then
   hand that vault — *without the source* — to a second agent. It is the only
   design where the control group can genuinely withhold the answer.
2. **Run D2 and D3** on the isolated harness. D2 is the best remaining candidate,
   because its answer lives in a `relation_notes` frontmatter field rather than in
   prose, and frontmatter is the one place the five duplication sites do not reach.
3. **Measure staleness as a failure mode.** Plant a deliberately outdated vault
   and check whether the agent gets *worse*. Until that is measured, "it helps as
   long as it is maintained" is unfalsifiable.
4. **Do not score on cost.** See `rubric.md`. Tool calls and tokens are recorded
   as diagnostics and decide nothing.

## Appendix: why the first three attempts measured nothing

Each was found only after fixing the one before it. All three passed silently,
and all three biased the result in the flattering direction.

**1. The control arm held the treatment.** `codex mcp remove` edits the global
config, but this repository commits `mcp_servers.ontology-atlas` in
`.codex/config.toml`, and Codex merges both. "MCP off" cells logged 8 and 10
ontology-atlas calls. Fixed by moving the project config aside for the duration.

**2. The prompt tripped our own product gate.** D1 originally asked whether a
feature *should* be built. `AGENTS.md` instructs any connected agent to run the
product owner gate before a product decision, so Codex opened
`docs/PRODUCT-OWNER-OPERATING-SYSTEM.md` and spent fourteen minutes per cell
running a PO pass. That measured our process documents. D prompts now ask what
the boundary **is**, never what it should be. This is a dogfooding artifact: a
user's repository has no PO operating system to trip.

**3. The answer key was inside the repository under measurement.** The graded
answers were written into `docs/benchmark/tasks.md`, which the agent searches.
All nine D1 cells read it; one read it 51 times. The key is now withheld in every
mode — this is a cheating problem, not a control problem. The same pass found the
vault duplicated into `public/docs-vault/` and `content.json`, and found that
renaming the vault folder in place left `docs/ontology.benchmark-parked/`, which
the agent read 19 times.

A fourth defect surfaced while fixing these: a killed run stranded the parked
`.codex/config.toml`, because `process.on("exit")` never sees `SIGKILL`. A
stranded config silently removes the MCP server from every Codex session in the
checkout. Every run now repairs what it finds on the way in.

**One correction worth recording.** B1 was called a failure because the agent
used 47 shell calls and 2 MCP calls. Reading the answer showed it had named the
boundary and its reasons correctly. Counting tools produced a verdict opposite to
the truth, which is why `rubric.md` now scores no cell on cost.
