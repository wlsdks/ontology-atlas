# 코드 그래프·위키·노트 앱·CLAUDE.md와 Atlas 비교

Ontology Atlas는 코드베이스가 무엇을 위해 있고 왜 그렇게 만들었는지를, 사람이
검토한 마크다운으로 저장소 안에 기록해요. 나와 코딩 에이전트가 같은 기록을
읽어요. 코드 그래프 도구는 코드가 어떻게 짜여 있는지를 계산해요. 위키와 노트
앱에 담긴 글은 코드가 바뀌어도 그 사실을 몰라요. `CLAUDE.md`와 `AGENTS.md`에는
에이전트가 따를 규칙이 담겨요. 이 글에서는 Atlas를 이 도구들, 그리고 지식 그래프
데이터베이스와 하나씩 비교하고, 어떤 경우에 다른 도구가 더 나은지도 짚어요.

## 한눈에 보기

| 도구 | 잘하는 것 | 담지 못하는 것 | Atlas와 함께 쓰기 |
|---|---|---|---|
| 코드 그래프, 코드 검색 | 정확한 구조: 정의, 호출, import | 각 부분이 무엇을 위한 것인지, 왜 그런지 | 개념이 코드 경로를 가리키고, 에이전트는 둘 다 써요 |
| 저장소 위키, 문서 사이트 | 독자를 위한 긴 설명 | 유형이 있는 관계, 코드가 바뀌었다는 신호 | 폴더 안의 위키 문서가 해시로 원본을 인용해요 |
| Obsidian, Notion | 글쓰기, 빠른 메모, 협업 | 저장소나 Git 기록과의 연결 | Obsidian으로 같은 폴더를 열 수 있어요 |
| `CLAUDE.md`, `AGENTS.md` | 에이전트가 세션마다 읽는 규칙 | 시스템 전체의 지도 | Atlas가 읽고, 섹션을 개념으로 바꿀 수 있어요 |
| 그래프 데이터베이스, RDF와 OWL | 대용량 데이터, 쿼리 언어, 추론 | Git 리뷰 안에서의 자리 | Atlas는 추론하지 않고, 데이터베이스도 아니에요 |

## 코드 그래프와 코드 인텔리전스

언어 서버, 코드 검색, 코드 그래프 인덱스는 소스에서 계산해 낸 결과예요. "이
함수를 어디서 호출하지?", "이 파일을 누가 import하지?" 같은 질문에 정확히 답하고,
코드에서 다시 만들어지기 때문에 늘 최신이에요. 이런 질문이라면 이 도구들이 더
알맞고, Atlas보다 빨라요.

하지만 각 부분이 무엇을 위한 것인지, 어느 제품 경계에 속하는지, 왜 두 모듈을
함께 바꿔야 하는지, 아직 아무도 확인하지 않은 게 무엇인지는 말해 주지 못해요.
Atlas는 이런 내용을 사람이 쓰거나 받아들인 개념과 관계로 기록해요. 개념은
`path`에 자기 코드를 적어 두고, 데스크톱 앱에서는 그 코드가 개념보다 나중에
바뀌면 지도가 그 개념을 오래됨으로 표시해요. Atlas의 `infer_imports` 도구도
정적 import를 읽지만, 결과는 검토할 후보일 뿐 받아들인 관계로 저장하지 않아요.

## 저장소 위키와 문서 사이트

긴 설명, 온보딩, 코드 밖의 독자를 위한 문서라면 위키나 문서 사이트가 제자리예요.
저장소에서 자동으로 만든 위키에는 팀이 정한 내용이 아니라 프로그램이 추측한
내용이 담겨요.

위키 문서는 자기가 설명하는 코드나 문서가 바뀌어도 알지 못하고, 그 링크에는
프로그램이 따라갈 수 있는 유형이 없어요. Atlas에서는 **자료실**이 원본 문서를
`sources/`에, 위키 문서를 `wiki/`에 둬요. 위키 문서는 원본마다 그 내용의 해시를
붙여 인용하기 때문에, 원본이 바뀌면 문서를 열기 전에 표시가 붙어요. `document`
개념은 `describes`로 글과 그 글이 설명하는 개념을 이을 수 있어요.

## 노트 앱: Obsidian과 Notion

Obsidian은 로컬 마크다운으로 빠르게 쓰고 잇는 데 강하고, 플러그인과 모바일 앱도
있어요. Notion은 팀이 함께 쓰는 워크스페이스와 데이터베이스에 강해요. 데일리
노트, 휴대폰으로 빠르게 적기, 실시간 협업이 필요하다면 이 도구들을 쓰세요.

둘 다 내 저장소와 그 Git 기록을 모르기 때문에, 노트가 설명하는 코드가 바뀌어도
노트에는 아무 표시가 나타나지 않아요. 온톨로지 폴더는 YAML frontmatter가 붙은
평범한 마크다운이라서 Obsidian으로 같은 폴더를 열고 거기서 글을 써도 돼요.
Atlas는 이름이 점으로 시작하는 폴더를 건너뛰기 때문에 Obsidian의 `.obsidian/`
설정은 읽지 않아요. 한계가 두 가지 있어요. Atlas는 `[[...]]` 링크를 Obsidian처럼
노트 이름으로 찾지 않고 폴더 루트 기준 경로로 찾기 때문에, Obsidian 링크 가운데
일부는 Atlas에서 연결되지 않아요. 그리고 Atlas의 편집은 일반 텍스트 편집이에요.

Atlas는 Notion과 동기화하지 않아요. 데스크톱 앱의 **자료실**에서 **외부에서
가져오기**를 쓰면, 연결된 에이전트가 Notion 페이지를 원본 문서로
`sources/notion/`에 복사해요.

## 에이전트 지침 파일: CLAUDE.md와 AGENTS.md

에이전트는 세션을 시작할 때마다 `CLAUDE.md`와 `AGENTS.md`를 읽어요. 빌드 명령,
코드 규칙, 에이전트가 하면 안 되는 일을 적기에 알맞은 자리예요. 매번 읽히는
파일이라 짧게 유지해야 하고, 그래서 시스템 전체의 지도, 어떤 코드가 어떤 역량을
구현하는지, 그게 언제 바뀌었는지까지 담을 수는 없어요.

Atlas는 이 파일들과 세 가지 방식으로 함께 일해요. Atlas가 만든 온톨로지 폴더에는
자체 `AGENTS.md`와 그것을 가져오는 `CLAUDE.md`가 들어 있어서, 에이전트에게 파일을
훑기 전에 Atlas MCP 서버에 먼저 물어보라고 알려 줘요. 에이전트의 `absorb_document`
도구는 기존 파일의 섹션을 개념으로 바꿔요([내 코드로 첫 지도 만들기](/guide/from-your-repo)).
그리고 앱의 **하네스** 탭은 이 파일들을 고치지 않고 읽기만 하면서 문제를 짚어
줘요. 예를 들어 `AGENTS.md`를 가져오지 않는 `CLAUDE.md`나, Codex의 기본 한도인
32 KiB를 넘는 `AGENTS.md`예요.

규칙은 지침 파일에, 의미는 온톨로지 폴더에 두세요.

## 지식 그래프 데이터베이스, RDF와 OWL

Neo4j 같은 그래프 데이터베이스는 큰 그래프를 저장하고, 여러 사용자와 서비스가
동시에 보내는 임의의 질의에 쿼리 언어로 답해요. RDF와 OWL은 조직 사이에
데이터를 주고받고, 추론기로 새 사실을 이끌어 내기 위한 표준이에요. 사실이 수백만
건에 이르거나 형식 추론이 필요하다면 이쪽을 쓰세요.

Atlas는 데이터베이스가 아니에요. Atlas의 그래프는 폴더 안의 파일이고, 코드와
함께 Git에서 리뷰돼요. 쿼리 언어도 없어요. MCP 도구 `query_ontology`는 `path`,
`impact`, `blast_radius`처럼 정해진 질문에만 답해요. Atlas는 아무도 적지 않은
관계를 추론하지 않고, RDF나 OWL 준수를 내세우지 않으며, 두 형식으로 내보내지도
않아요. frontmatter는 평범한 YAML이라서 스크립트로 읽을 수 있어요.
