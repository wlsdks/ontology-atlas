# コードの変更に合わせてマップを最新に保つ

この章では、あなたとコーディングエージェントがコードを変え続ける間も、コードベースのオントロジーを正しく保つ方法を説明します。変更後のマップの同期、安全な名前の変更、重複した概念の防止、根拠が古くなった概念の発見、そして変更内容のレビューとコミットです。

## コードを変更したら同期する

変更のあと、その変更を行ったエージェントに、同じセッションの中でマップを更新するよう頼みます。判断の基準は次のとおりです。

- **同期する**: ドメイン、ケイパビリティ、要素、またはそれらの間の関係を追加、削除、名前変更したとき。
- **スキップする**: 誤字、コメント、1行のスタイル変更、lintの設定、意味を変えないテストフィクスチャ。

エージェントは、影響を受ける概念を`get_concept`で読み、`patch_concept`、`add_concepts`、`add_relations`で変更し、`validate_vault`を実行します。コードの名前を変えても、概念の名前まで変える必要はありません。意味が変わったのか、ファイルが変わっただけなのかを判断してください。ファイルが移動しただけなら、概念の`path`を更新します。

`init`は、Claude CodeとCodex向けに3つのスタータースキルをインストールします。`atlas-review`は壊れているものやつながっていないものを報告し、`atlas-grow`は次に追加するものを提案し、`atlas-absorb`はメモや仕様書から概念を抜き出します。どれも、あなたが選ぶまでは書き込みません。

## 古くなったものを見つける

デスクトップアプリでは、根拠が古くなっているかもしれない概念がマップ上で示されます。概念が**古い**とされるのは、その概念が参照しているファイルが、その概念自身の文書が最後に変更されたあとにコミットされた場合です。どのマップビューでも、古い概念は琥珀色または金色で示され、凡例にその印の名前が表示されます。これにはフォルダのGit履歴が必要なので、Webサイトや、Gitのないフォルダでは古い印は表示されません。

ターミナルからは、`health`がすべてのチェックを実行します。概念が参照しているソースパスがまだ存在するかどうかも確認します。

```bash
node ~/tools/ontology-atlas/cli/src/index.mjs health ./atlas
```

`validate`がチェックするのはMarkdownとその参照だけで、コードは見ません。参照されているファイルを削除するリファクタリングは、`validate`を通っても`health`では失敗することがあります。

アプリの**変更**画面は、あなたが選んだコードリポジトリのGit履歴を読みます。ある期間にマージされた内容を要約し、変更ごとに、そのコードパスに触れた**影響を受ける概念**を一覧表示します。忙しい1週間のあとに見るのはここです。

コミットする前に、`preflight --staged`がステージしたファイルと、それらを参照している概念を照らし合わせ、影響するものを出力します。コミットをブロックすることはなく、該当する概念がなければ何も出力しません。

## 重複を避ける

マップが劣化するいちばんよくある原因は、同じ概念が2つの名前で二重に書かれることです。追加する前に確認しましょう。

```bash
node ~/tools/ontology-atlas/cli/src/index.mjs similar "order acceptance" ./atlas
```

スコアが高ければ、既存の概念を更新してください。エージェントも同じ保護を受けます。似たタイトルの概念がすでにあると、`add_concept`が警告を返します。すでに2つの概念に分かれてしまっている場合は、マージします。マージすると、すべての参照が残す側の概念に移ります。

```bash
node ~/tools/ontology-atlas/cli/src/index.mjs merge capabilities/checkout capabilities/order-acceptance --vault ./atlas
```

## 参照を壊さずに名前を変える

概念の名前を手で変えると、参照を取りこぼします。`rename`はファイルを移動し、その概念を指しているすべての概念を、関係のメモも含めて書き換えます。

```bash
node ~/tools/ontology-atlas/cli/src/index.mjs backlinks capabilities/checkout --vault ./atlas
node ~/tools/ontology-atlas/cli/src/index.mjs rename capabilities/checkout capabilities/order-acceptance --vault ./atlas
```

スラッグは変わりますが、概念の`uid`は変わらないので、エージェントやエクスポートは引き続き同じ概念として認識します。`rename`、`merge`、`delete`は、デフォルトではプレビューだけを行います。適用するには`--confirm`を付けます。`delete`は、ほかの概念がまだ削除対象を指している間は実行を拒否します。エージェントは対応するMCPツール`rename_concept`、`merge_concepts`、`delete_concept`を使い、これらも同じように最初にプレビューします。

## マップ上で指摘をレビューする

アプリで概念を選び、**オントロジーのレビュー**を開きます。**AIにレビューを依頼**を押すとエージェントにマップのチェックを頼み、その答えが**レビュー結果**の下に、指摘1件につき1行で表示されます。マップは、指摘の対象となっている概念に印を付けます。指摘ごとに、**修正を依頼**、**後で見る**、**却下**のいずれかを選びます。指摘はエージェントの推測です。レビューが自分でマップを編集することはありません。

## 同時に編集されたとき

あなたと、チームメイトと、エージェントが同じファイルを編集することがあります。Atlasの書き込みが黙って上書きすることはありません。

- MCPの書き込みツールは、書き込む前にディスクからファイルを読み、エージェントが読んだあとに変更されたファイルは上書きを拒否します。エージェントは読み直してから再試行する必要があります。
- アプリが提案された変更を、直前に変更された文書に適用しようとした場合は、何も書き込まず、そのことを伝えます。

## 変更をコミットする

オントロジーフォルダはGitで管理される普通のファイルなので、概念の変更はコードと同じプルリクエストでレビューできます。アプリでは、**Git**画面に未コミットの変更が文書ごとに一覧表示され、変更された行に印が付きます。変更の数を表示する**コミット**ボタンで、それらを記録します。そこから、1つの文書を以前のバージョンに戻すこともできます。ターミナルからは、`snapshot`がオントロジーフォルダだけを、変更内容の要約とともにコミットします。

```bash
node ~/tools/ontology-atlas/cli/src/index.mjs snapshot ./atlas --dry-run
```

ここで使ったコマンドはすべて[CLIの章](/guide/cli)に一覧があります。概念と関係の形については[概念どうしの関係](/guide/relations)で説明しています。
