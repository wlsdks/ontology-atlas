# Atlasとコードグラフ・Wiki・ノートアプリ・CLAUDE.mdの比較

Ontology Atlasは、コードベースが何のためにあり、なぜそう作られているのかを、人がレビューしたMarkdownとしてリポジトリの中に記録します。あなたとコーディングエージェントは同じ記録を読みます。コードグラフのツールは、コードがどう組み立てられているかを計算します。Wikiやノートアプリに書かれた文章は、コードが変わってもそれを知りません。`CLAUDE.md`と`AGENTS.md`には、エージェントが従うルールが書かれます。この章では、Atlasをこれらのツールと、さらにナレッジグラフのデータベースと比べ、ほかのツールのほうが適している場面も説明します。

## 一覧で比べる

| ツール | 得意なこと | 持っていないもの | Atlasとの併用 |
|---|---|---|---|
| コードグラフ、コード検索 | 正確な構造：定義、呼び出し、import | 各部分が何のためにあるのか、なぜそうなのか | 概念がコードのパスを指し、エージェントは両方を使う |
| リポジトリのWiki、ドキュメントサイト | 読み手のための長い説明 | 型付きの関係、コードが変わったことを示すしるし | フォルダ内のWikiページがハッシュ付きでソースを引用する |
| Obsidian、Notion | 執筆、すばやいメモ、共同作業 | リポジトリやそのGit履歴とのつながり | Obsidianで同じフォルダを開ける |
| `CLAUDE.md`、`AGENTS.md` | エージェントがセッションごとに読むルール | システム全体のマップ | Atlasが読み込み、セクションを概念に変換できる |
| グラフデータベース、RDFとOWL | 大量のデータ、クエリ言語、推論 | Gitのレビューの中での居場所 | Atlasは推論せず、データベースでもない |

## コードグラフとコードインテリジェンス

言語サーバ、コード検索、コードグラフのインデックスは、ソースから計算されたものです。「この関数はどこで呼ばれているか」「このファイルを誰がimportしているか」に正確に答え、コードから作り直されるので常に最新です。こうした問いには、これらのツールのほうが適しており、Atlasより速く答えます。

一方で、各部分が何のためにあるのか、どのプロダクトの境界に属するのか、なぜ2つのモジュールを一緒に変えなければならないのか、まだ誰も確かめていないことは何か、には答えられません。Atlasはそれらを、人が書いた、または受け入れた概念と関係として記録します。概念は`path`に自分のコードを書き、デスクトップアプリでは、そのコードが概念より後に変更されると、マップがその概念を古いものとして示します。Atlasの`infer_imports`ツールも静的なimportを読みますが、その結果はレビュー候補として返すだけで、受け入れた関係にはしません。

## リポジトリのWikiとドキュメントサイト

長い説明、オンボーディング、コードの外にいる読み手のためのページを置くなら、Wikiやドキュメントサイトが適しています。リポジトリから自動生成されたWikiに入っているのは、チームが決めたことではなく、プログラムが推測したことです。

Wikiページは、自分が説明しているコードや文書が変わってもそれを知りません。また、そのリンクにはプログラムがたどれる型がありません。Atlasでは、**資料室**がソース文書を`sources/`に、Wikiページを`wiki/`に置きます。Wikiページは各ソースをその内容のハッシュ付きで引用するので、ソースが変わると、開く前にそのページに印が付きます。`document`の概念は、`describes`を使って文章とそれが説明する概念を結び付けられます。

## ノートアプリ：ObsidianとNotion

Obsidianは、ローカルのMarkdownですばやく書いてリンクすることが得意で、プラグインやモバイルアプリもあります。Notionは、チームで共有するワークスペースとデータベースが得意です。デイリーノート、スマートフォンでのすばやいメモ、リアルタイムの共同作業には、これらを使ってください。

どちらもあなたのリポジトリやそのGit履歴を知らないため、ノートが説明しているコードが変わっても、ノートには何も表示されません。オントロジーフォルダはYAMLのフロントマターが付いた普通のMarkdownなので、Obsidianで同じフォルダを開き、そこで書くこともできます。Atlasは名前がドットで始まるフォルダを読み飛ばすので、Obsidianの`.obsidian/`の設定は読みません。制限が2つあります。Atlasは`[[...]]`リンクを、Obsidianのようにノート名ではなく、フォルダのルートからのパスで解決します。そのため、Obsidianのリンクの一部はAtlasではつながりません。また、Atlasでの編集はプレーンテキストです。

AtlasはNotionと同期しません。デスクトップアプリの**資料室**にある**サービスから取り込む**を使うと、接続したエージェントがNotionのページをソース文書として`sources/notion/`にコピーします。

## エージェント向けの指示ファイル：CLAUDE.mdとAGENTS.md

エージェントは、セッションを始めるたびに`CLAUDE.md`と`AGENTS.md`を読み込みます。ビルドコマンド、規約、エージェントがしてはいけないことを書くのに適した場所です。毎回読まれるので短く保つ必要があり、そのためシステム全体のマップや、どのコードがどのケイパビリティを実装しているか、それがいつ変わったかまでは書けません。

Atlasはこれらのファイルと3つの方法で連携します。Atlasが作るオントロジーフォルダには、独自の`AGENTS.md`と、それを取り込む`CLAUDE.md`が入っており、ファイルを走査する前にまずAtlasのMCPサーバに問い合わせるよう、エージェントに伝えます。CLIの`absorb`コマンドは、既存のファイルのセクションを概念に変換します（[コードから最初のマップを作る](/guide/from-your-repo)）。そしてアプリの**ハーネス**タブは、下のコマンドと同じように、これらのファイルを変更せずに読み、問題を指摘します。たとえば、`AGENTS.md`を取り込んでいない`CLAUDE.md`や、Codexのデフォルトの上限である32 KiBを超える`AGENTS.md`です。

```bash
node ~/tools/ontology-atlas/cli/src/index.mjs agent-files --root .
```

ルールは指示ファイルに、意味はオントロジーフォルダに置いてください。

## ナレッジグラフのデータベース、RDFとOWL

Neo4jのようなグラフデータベースは、大きなグラフを保存し、多くのユーザやサービスから同時に届くアドホックな問い合わせにクエリ言語で答えます。RDFとOWLは、組織をまたいでデータを共有したり、推論器で新しい事実を導いたりするための標準です。数百万件の事実や形式的な推論が必要なら、こちらを使ってください。

Atlasはデータベースではありません。Atlasのグラフはフォルダ内のファイルであり、コードと一緒にGitでレビューされます。クエリ言語もありません。MCPツールの`query_ontology`が答えるのは、`path`、`impact`、`blast_radius`のような決まった問いだけです。Atlasは誰も書いていない関係を推論せず、RDFやOWLへの準拠もうたわず、どちらの形式へのエクスポートもしません。フロントマターは普通のYAMLなので、スクリプトで読めます。
