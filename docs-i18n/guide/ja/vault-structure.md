# オントロジーフォルダ：Markdownファイルと先頭の情報ブロック

Atlasのオントロジーは、普通のMarkdownファイルが入ったフォルダです。コードベースのナレッジグラフの概念1つが`.md`ファイル1つにあたり、ファイル先頭の情報ブロック（YAMLフロントマター）に、その概念が何で、ほかの概念とどうつながっているかを書きます。この章では、そのファイル形式、Atlasが読むフィールド、ファイルの置き場所を説明します。裏にデータベースはありません。ファイルそのものがオントロジーです。

## 概念1つにファイル1つ

```markdown
---
uid: 7ec556ec-768d-40c3-8147-19db4287a338
slug: capabilities/token-issue
kind: capability
title: Token issuance
display_en: Token issuance
domain: domains/auth
elements: [elements/jwt-signer]
path: src/auth/issue-token.ts
dependencies: [capabilities/session-store]
relation_notes: { capabilities/session-store: "セッションが書き込まれたあとでのみ、トークンが発行される。" }
---

サインインに成功したあと、失効させられるセッショントークンを発行する。

## Includes
- トークンに署名して返すこと。

## Excludes
- パスワードの確認。これは資格情報の検証に属する。
```

フロントマターがグラフそのものです。種類、名前、親、関係が入ります。本文には、人やエージェントが読む意味を書きます。定義、その概念が含むものと含まないもの、根拠、そしてまだ不確かなことです。

## フィールド

| フィールド | 入るもの |
|---|---|
| `uid` | 概念の永続的な識別子（小文字のUUIDv4）です。変わることはありません。 |
| `slug` | 読みやすい現在のアドレスです。たとえば`capabilities/token-issue`。関係はスラッグを指します。あとから変更できます。 |
| `kind` | `project`、`domain`、`capability`、`element`、`document`のいずれかです。[概念の選び方](/guide/what-becomes-a-node)を参照してください。 |
| `title` | 正式な名前です。検索や照合では、どの言語でもこれを使います。 |
| `display_<locale>` | その言語の画面に表示する名前です。たとえば`display_en`、`display_ko`。 |
| `display` | `title`が長いときに、ラベル用に使う短い名前です。省略できます。 |
| `description` | 1行の要約です。省略できます。 |
| `domain` | ケイパビリティや要素の親ドメインです。基本的に書きます。ないと警告になります。 |
| `path` | ケイパビリティや要素について、初めて読む人が最初に開くべきファイルまたはフォルダ1つです。 |
| 関係のキー | `domains`、`capabilities`、`elements`、`dependencies`、`relates`、`broader`、`contains`、`describes`。[関係](/guide/relations)を参照してください。 |
| `relation_notes` | 関係ごとに、それが成り立つ理由を1文で書きます。キーは相手のスラッグです。 |
| `created_by` | ファイルを作成した人またはエージェントです。`human`、または`agent:`のあとにエージェントの名前を続けます。 |
| `review_state` | 省略できます。`human_decides`は、人だけが判断を下せる概念の印です。`confirmed`は、人が意味を確認したことを記録します。 |

`uid`、`slug`、`kind`、`title`は、すべての概念で必須です。ケイパビリティや要素に`domain`がないのはエラーではなく警告なので、作りかけのフォルダでも開けます。

### 識別子：uidとslug

`uid`は、概念を作成するツール（アプリかMCPサーバ）が一度だけ発行します。自分で決めるものではありません。概念の名前を変えると、その`slug`が変わり、その概念を指しているすべての関係が書き換えられますが、`uid`はそのまま残ります。2つの概念をマージすると、残る側の`uid`が保たれ、取り込まれた側は`merged_uids`に記録されるので、古い`uid`からでも正しい概念にたどり着けます。`merged_uids`を手で書かないでください。

関係やリンクを書くときはスラッグを使います。ファイルの中で人が読むのはスラッグだからです。名前が変わったあとでも同じ概念を指し続けなければならないツールや引き継ぎでは、`uid`を使います。

### 複数の言語での名前

マップ、一覧、パネルは、画面の言語の`display_<locale>`があればそれを表示し、なければ正式な名前を表示します。`title`はどの言語でも同じなので、検索や照合は翻訳に左右されません。チームが2つの言語でマップを読むなら、両方の名前を書いておきましょう。片方がなければ、もう一方の言語の名前が代わりに表示されます。

## ファイルの置き場所

オントロジーフォルダは、それが記述するリポジトリの中に置いてください。そうすれば、コードの変更と、それに対応する意味の変更を同じプルリクエストでレビューできます。Ontology Atlasのリポジトリ自身も、オントロジーを`docs/ontology/`に置いています。

```text
your-repo/
├── src/
└── docs/ontology/
    ├── project.md          プロジェクト（kind: project）
    ├── domains/            ドメインごとに1ファイル
    ├── capabilities/       ケイパビリティごとに1ファイル
    ├── elements/           要素ごとに1ファイル
    ├── sources/            元の資料ファイル。概念にはならない
    └── .ontology-atlas/    アプリがオントロジーの横に置くファイル
```

プロジェクトと文書はフォルダのルートに置き、ドメイン、ケイパビリティ、要素はそれぞれのフォルダに置きます。慣例としてファイルのパスはスラッグに合わせますが、Atlasが信頼するアドレスはフロントマターの`slug:`です。種類ごとのフォルダの下では、スラッグに階層を作れません。`elements/jwt-signer`は正しく、`elements/src/auth/jwt-signer`は誤りです。コードの場所は`path`に書きます。

`sources/`の下のファイルは、Wikiページが引用する文書のような元の資料で、概念として読まれることはありません。`.ontology-atlas/`には、レビュー結果やコードフォルダへのリンクなど、アプリがオントロジーの横に書き込むファイルが入ります。Atlasが初めてそのリンクを書き込むとき、このフォルダがGitの対象外になるよう、そこに`.gitignore`も追加します。

エージェントの`validate_vault`は、壊れた参照、不明な種類、不正な形式の識別子を報告します。ほとんどの指摘は作業を止めない警告ですが、`uid`の重複はエラーです。

## ファイルが正本

Atlasは、毎回ファイルからオントロジーを読みます。エディタ、アプリ、エージェントのどれでファイルを編集しても、マップは数秒以内にその変更を反映します。同期ボタンも、隠れた状態もありません。エージェントによるものを含め、すべての変更は`git diff`の1行になり、レビューしたり、残したり、元に戻したりできます。
