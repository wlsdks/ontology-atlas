# 概念の選び方：ドメイン、ケイパビリティ、要素

コードベースのオントロジーを作るとは、何を概念にし、それにどの種類を与えるかを決めることです。この章では、Atlasが種類ごとに使う判定基準と、ソースファイル1つが概念1つにならない理由を説明し、子の多い親のための「1文テスト」を紹介します。コーディングエージェント（Claude Code、Codex、Cursor）は書き込む前にMCPサーバを通じて同じルールを読むので、人が作った概念もエージェントが作った概念も同じ形になります。

## 役割で種類を選ぶ

種類は、その概念の大きさ、フォルダ、担当者ではなく、モデルの中で果たす役割で選びます。

| 種類 | 問い | 例 | これは違う |
|---|---|---|---|
| `project` | 「このシステムは〜のためにある」という文を完成させ、ほかのすべての範囲を決めるか | 「プロダクトの意味を人とエージェントの間で共有しておくための、ローカルのワークベンチ。」 | 「TypeScriptのモノレポ。」 |
| `domain` | ケイパビリティをまとめる、長く続く責務や問題の境界で、コードを書き直しても残るか | 「ID管理は、サインインとアカウントへのアクセスのポリシーを受け持つ。」 | 「`src/auth`フォルダ」や「認証チーム」。 |
| `capability` | システムができることを、それを行うモジュールの名前を出さずに、外から観察できる形で述べているか | 「サインイン後に、失効させられるセッショントークンを発行する。」 | 「トークンコントローラ」や「ログインのワークフロー」。 |
| `element` | ケイパビリティを担う、区別できる実装上の役割を名指しし、誰かが開ける根拠があるか | `path: src/auth/jwt-signer.ts`を持つ「JWT署名器」。 | 名前としての`src/auth/jwt-signer.ts`。 |
| `document` | それ自体が文章で、別の概念について説明したり決定したりすることに価値があるか | 「ADR：ローカルファーストの永続化」。 | READMEがあるからという理由で文書として登録されたサービス。 |

表は上から下へ読みます。何を届けるのか、責務がどこで分かれるのか、システムに何ができるのか、それをどう実現するのか、という順です。

フォルダ、パッケージ、チーム、ルート、クラス名、READMEの見出しは手がかりであって、概念ではありません。それがドメインやケイパビリティになるのは、循環していない定義を書け、何を含み何を含まないかを言えるときだけです。名前に動詞が入っていてもケイパビリティになるわけではなく、名詞だからといって要素になるわけでもありません。

種類ごとに何を含み何を含まないかを含めた完全な判定基準は、[Atlasの仕様](https://github.com/wlsdks/ontology-atlas/blob/main/docs/ONTOLOGY-ATLAS-SPEC.md#2-the-five-authorable-node-kinds-and-reserved-reader-kind)にあります。

## ファイル1つは概念1つではない

いちばんよくある間違いは、ディレクトリを開いてファイルごとに要素を1つ作ることです。結果はオントロジーのように見えますが、実際にはディレクトリの一覧をグラフに写しただけです。Atlas自身のリポジトリにも以前、要素が92個あるケイパビリティがあり、その中身は1つのフォルダを`ls`した結果とそっくり同じでした。

パスは概念の根拠であって、概念そのものではありません。

- 要素には、`jwt-signer`や`session-store`のように役割を表す名前を付けます。
- 場所は`path:`に書きます。
- タイトルが`src/lib/auth/jwt.ts`のように見えるか、ソースの拡張子で終わっているなら、それは根拠です。MCPサーバは、そうしたタイトルを見つけると警告します。
- 種類ごとのフォルダの下では、スラッグに階層を作りません。`elements/jwt-signer`とし、`elements/src/lib/auth/jwt`とはしません。パスの形をしたスラッグは、概念を書き込むときに拒否されます。同じ名前の2つのファイルが、知らないうちに1つの概念になってしまうからです。

複数のファイルが1つの役割を共有することもあります。2つのファイルの役割の違いを1文で言えないなら、それは1つの要素です。あるいは要素ですらなく、ケイパビリティの`path`にすぎません。

## 子が多いことは欠陥ではない

概念が持てる子の数に上限はありません。どの子にもそこにいる理由があるなら、幅の広い親は正しい形です。上限は、中身を理解しないままでも簡単に満たせてしまいます。ひと山を「グループA」と「グループB」に分ければ数字は整いますが、何も分かりやすくなっていません。

数は、問いを立てるきっかけにすぎません。フォルダがまだ育っていないうちは、ドメインの下にケイパビリティが約8個、ケイパビリティの下に要素が約6個が目安です。ある種類の親が10個以上になると、Atlasは代わりにあなたのフォルダ自身の分布と比較します。

### 1文テスト

親がその目安を超えたら、子ごとに1つの問いを立てます。

> この子が兄弟と入れ替えられない理由を、循環しない1文で書けるか？

- 書けるなら、兄弟が30個あってもそのままにします。
- 書けないなら、新しい概念を追加しないでください。代わりに、既存の兄弟の本文を改善します。

名前の先頭が共通していることは、どこを見るべきかのヒントであって、テストではありません。

### 3つ以上の子がテストに通らないとき

3つ以上の子がテストに通らないなら、階層が1つ欠けています。親とそれらの子の間に概念を1つ追加します。ただし、次のすべてを満たすときに限ります。

1. 子が共有する振る舞いにちなんだ名前が付いている。「その他」や「パート2」は名前ではありません。
2. その振る舞いを1文で述べられる。
3. それ自身の兄弟に対して、1文テストに通る。
4. 実際に子をその下に移す。空のグループ化概念は、削除の対象として報告されます。

どれか1つでも満たさないなら、何も作りません。

## すべてのケイパビリティに根拠を付ける

ケイパビリティを作るときは、同時に、開いて確かめられるものを付けます。`path:`に実装の入口を1つ書くか、`elements:`に少なくとも1つの要素を書きます。どちらもないケイパビリティは、誰も確かめられない主張です。それでも書き込まれはしますが、何かを指すようになるまでは`capability_without_evidence`として整理キューに残ります。このキューは`query_ontology`の`maintenance_plan`で確認できます。

```markdown
---
uid: 9f6805c6-7f22-4ca8-8252-c0c2d06f3fad
kind: capability
slug: capabilities/token-issue
title: Token issuance
domain: domains/auth
path: src/auth/issue-token.ts
elements: [elements/jwt-signer]
---
```

`elements:`に入れるのは、実在する要素の概念のスラッグだけです。ファイルのパスは決して入れません。

## ルールは報告するが、ブロックはしない

これらのチェックは書き込みを拒否しません。チェックを満たさない概念も保存され、応答に警告が付くか、整理キューに1行が加わります。ブロックすると、エージェントがツールを回避するやり方を覚えてしまうからです。唯一の例外が、パスの形をしたスラッグです。これは意味ではなく識別子を壊すもので、概念を作る時点で直すのがいちばん手間がかかりません。
