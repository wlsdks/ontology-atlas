# オントロジーとは

オントロジーとは、ある分野にどんなものがあり、それらがどう関係しているかを、皆で共有できる形で書き表したものです。どんな概念があるか、それぞれがどの種類に属するか、概念どうしをどんな関係で結べるか、そしてそれぞれの言葉が何を意味するかを定めます。この章では、まず一般的な考え方を説明し、タクソノミー、スキーマ、ナレッジグラフとの違いを整理したうえで、Ontology Atlasがコードベースを記述するのに使うオントロジーを紹介します。

## 一般的な考え方

どのチームにも、すでにオントロジーがあります。たいていは明文化されていないだけです。「注文」「決済」「返金」と言うとき、人は同じ意味を前提にしていて、返金は注文に属し、購入確定は決済に依存していることも知っています。問題が起きるのは、二人が同じ言葉で別のものを指したときや、2つの部分がなぜつながっているのかを誰も覚えていないときです。

オントロジーを書き表すと、そうした取り決めがはっきりします。オントロジーは4つの部分からなります。

- **概念**: 名前を付けて呼ぶもの。たとえば「注文」や「カートの購入を確定する」です。
- **種類**: 各概念の型です。種類は、それがどういうものか、どんな問いに答えるべきかを示します。
- **関係**: 概念どうしを結ぶ型付きのリンクです。「〜に属する」「〜に依存する」「〜を説明する」などがあります。関係には向きと意味があるので、「AはBに依存する」は「AはBと関連がある」とは別のことを言っています。
- **合意された意味**: 各概念と各関係の短い定義です。これがあることで、人もプログラムも同じ意味で読めます。

## 似た用語との違い

これらの言葉は意味が重なり、ゆるく使われがちです。このガイドでは次の意味で使います。

- **タクソノミー**（分類体系）は、カテゴリの階層です。各項目はより広いカテゴリの下に置かれます。関係は基本的に「〜の一種である」の1つだけです。オントロジーはタクソノミーを含むこともありますが、依存のようなほかの関係も持ちます。
- **スキーマ**は、データの形、つまりレコードがどんなフィールドを持ち、各フィールドがどの型かを定めます。データをどう保存するかは示しても、それが自分たちのドメインで何を意味するかは示しません。Atlasにも各ファイルのフィールドについてのスキーマがありますが、スキーマはオントロジーではありません。
- **ナレッジグラフ**は、具体的なものを関係で結んだ集まりです。ナレッジグラフが使う語彙（種類と関係の型）は、通常オントロジーが与えます。Atlasでは種類と関係の型がその語彙で、フォルダ内のファイルがその語彙で組み立てたグラフです。

OWLやRDFのような形式的なオントロジー言語は、プログラムが新しい事実を推論するための論理を加えます。Atlasはそれをしません。人やエージェントが書いたものだけを保存し、誰も書いていない関係を推論することはありません。

## コードベースにオントロジーが必要な理由

コードは、ものがどう作られているかを示します。しかし、各部分が何のためにあるのか、どのルールが重要なのか、なぜ2つのモジュールを一緒に変えなければならないのかは、めったに示しません。そうした知識は、たいてい人の頭の中や古い文書にあります。

コーディングエージェントは、この溝をさらに広げます。エージェントは数分で数十のファイルを変更でき、人が読むペースでは追いつかないからです。システムについて共有された記述がなければ、エージェントのセッションは毎回ゼロから始まり、レビューは毎回、変更されたファイルの一覧から始まります。コードベースのオントロジーは、エージェントと人の両方に同じ出発点を与えます。エージェントは作業の前に、タスクがどの概念に関わるかを読みます。人は作業が終わったあとに、変更がどの概念に影響するかを確かめます。

## Atlasが使うオントロジー

Atlasはオントロジーを、Markdownファイルからなるオントロジーフォルダとして保存します。通常はリポジトリ内の`atlas/`フォルダです。概念1つがファイル1つです。ファイル先頭のフロントマター（YAMLで書く情報ブロック）には識別情報、種類、関係が入り、その下の本文には平易な文章で説明を書きます。

種類は5つあります。

| 種類 | 何を表すか | 例 |
|---|---|---|
| `project` | フォルダが記述するプロダクトやシステム | 「小規模な小売店向けのWebショップ」 |
| `domain` | 書き直しても残る、長く続く責務の領域 | 注文、ID管理、請求 |
| `capability` | システムができること。コードの名前は出さずに書く | カートの購入を確定する |
| `element` | ソースパスを持つ具体的な実装部品 | 購入確定サービス、`src/orders/checkout.ts` |
| `document` | 他の概念について説明したり決定したりする文章 | アーキテクチャ決定記録 |

関係はフロントマターのキーとして書きます。

- `domains`、`capabilities`、`elements`は、プロジェクト、ドメイン、ケイパビリティが何を含むかを列挙します。`domain`は、ケイパビリティや要素が属するドメインを示します。
- `dependencies`は、ある概念が別の概念を必要とすることを表します（マップ上では**依存先**）。向きのある関係です。逆向きは相手側から読み取るので、両側に二重に書くことはしません。
- `relates`は、向きも因果関係も含意しない、ゆるい関連です。
- `describes`は、文書を、それが説明する概念に結びつけます。
- `broader`は、ある概念が、同じ種類の別の概念に含まれる、より狭いケースであることを表します。マップ上では、その線に**上位概念**というラベルが付きます。
- `relation_notes`には、関係ごとに、それが成り立つ理由を1文で書きます。

すべての概念には、一度決まったら変わらない識別子である`uid`と、現在の読みやすいアドレスである`slug`もあります。`slug`は名前を変えると変わることがあります。

## ファイルの例

オンラインストアのケイパビリティファイルを、フォルダに置かれているそのままの形で示します。

```markdown
---
uid: 3f6c2a9e-8b41-4d7a-9c25-6e0f1b7d4a12
slug: capabilities/checkout
kind: capability
title: カートの購入を確定する
description: 決済が1回承認されたあとで、カートを注文に変える。
domain: domains/orders
elements: [elements/checkout-service]
path: src/orders/checkout.ts
dependencies: [capabilities/payment-authorization]
relation_notes: { capabilities/payment-authorization: "決済事業者が金額を承認したあとでのみ、注文が作成される。" }
---

# カートの購入を確定する

現在のカートを注文に変える。返金は扱わない。
```

マップ上では、このファイルは注文ドメインの中の1つの概念になります。それを実装する購入確定サービスへの線と、依存している決済の承認への線が引かれます。その線をクリックすると、`relation_notes`に書かれた理由が小さなパネルに表示されます。

## Atlasのオントロジーが主張しないこと

フォルダ内の関係は宣言された主張であって、証明ではありません。それが示すのは、誰かが「購入確定は決済の承認に依存する」と書いたということであって、プログラムを実行時に追跡した結果ではありません。関係が書かれていないことは「つながりがない」ではなく「不明」を意味します。だからマップは正直でいられます。書き留められたものと、まだ誰も何も書いていない場所を、ありのまま示すからです。
