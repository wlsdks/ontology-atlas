# 概念どうしの関係

関係とは、オントロジーのナレッジグラフで概念どうしを結ぶ、型付きのエッジです。「このケイパビリティはあのケイパビリティに依存する」「この要素はあのケイパビリティに属する」といったものです。Atlasでは、関係の1つ1つが、概念のフロントマターの1項目になります。この章では、関係の型を一覧にし、その書き方を示し、マップと、コーディングエージェントが呼び出すMCPツール（`query_ontology`や`find_backlinks`など）がそれをどう読むかを説明します。

## 構造と意味

関係は2つのグループに分かれます。

- **構造**は、何が何を含むかを表します。プロジェクトはドメインを持ち、ドメインはケイパビリティを持ち、ケイパビリティは要素を持ちます。構造だけならツリーになります。
- **意味**は、概念どうしがどう依存し、どう関連するかを、階層をまたいで表します。あるドメインのケイパビリティが別のドメインのケイパビリティに依存することもあれば、2つのドメインが直接関連することもあります。そうした関係が1つあるだけで、ツリーはグラフになります。

## 関係の型

| 意味 | フロントマターのキー | どこから → どこへ | マップ上の表示 |
|---|---|---|---|
| プロジェクトのドメイン | `domains: [...]` | プロジェクト → ドメイン | プロジェクトのまわりのドメイン |
| 含まれるケイパビリティ | `capabilities: [...]` | プロジェクトまたはドメイン → ケイパビリティ | ドメインのまわりの円 |
| 含まれる要素 | `elements: [...]` | プロジェクト、ドメイン、ケイパビリティ → 要素 | ケイパビリティのまわりの点 |
| ドメインへの所属 | `domain: <slug>` | ケイパビリティまたは要素 → ドメイン | そのドメインの中に置く |
| 汎用の包含 | `contains: [...]` | 任意の概念 → 任意の概念（上のどのキーも合わないとき） | |
| 依存 | `dependencies: [...]` | 任意の概念 → それが必要とする概念 | 必要とされる側に向かう先細りの線 |
| 関連 | `relates: [...]` | 任意の概念 ↔ 任意の概念 | 点線の細い線 |
| 上位概念 | `broader: [...]` | ドメイン → ドメイン、ケイパビリティ → ケイパビリティ、要素 → 要素 | 二重の細い線。`is_a`として表示 |
| 説明 | `describes: [...]` | 文書 → それが説明する概念 | 文書のパネルに一覧表示 |

Atlasは読み込むときに`depends_on:`も`dependencies:`の別表記として受け付けますが、書き出すときは常に`dependencies:`を使います。向きと推論のルールを含めた完全な表は、[Atlasの仕様の第5節](https://github.com/wlsdks/ontology-atlas/blob/main/docs/ONTOLOGY-ATLAS-SPEC.md#5-relation-types-and-their-semantics)にあります。

`broader`は、同じ種類の2つの概念の間で、本当に「〜の一種である」と言えるときだけ使います。狭い側の定義に当てはまるものは、すべて広い側の定義にも当てはまらなければなりません。同じドメインにある、名前が似ている、フォルダが入れ子になっている、といったことだけでは足りません。

## 関係の書き方

関係は、元になる概念の側に一度だけ書きます。相手の側で触れる必要はありません。

```markdown
---
uid: 94cf0cde-1e74-497d-ac41-00cdf3a42f0b
slug: capabilities/vault-live-updates
kind: capability
title: Vault live updates
domain: domains/local-vault
dependencies: [capabilities/map-render]
relates: [capabilities/conflict-guard]
relation_notes: { capabilities/map-render: "検出したファイルの変更を見せるには、マップを描き直す必要がある。" }
---
```

`relation_notes`には、関係ごとに、それが成り立つ理由を1文で書きます。キーは相手のスラッグです。MCPサーバやマップのエディタで新しく書く`depends_on`には、この1文が必須です。ほかの関係も、理由が分かっているなら書いておきましょう。概念パネルでは、理由のない関係に**理由なし**の印が付きます。

値はスラッグなので、人はファイルを見てグラフを読めます。`capabilities/map-render`に対する`map-render`のように、一意に決まる短い形も使えます。Atlasを通じて概念の名前を変えると、その概念を指しているすべての関係が書き換えられます。

Atlasは関係のリストを書き込むときに、前後の空白を除き、重複を取り除き、並べ替えます。そのため順序に意味はありません。また、逆向きの関係や推移的な関係を勝手に追加することもありません。片側に書いた`relates`がもう片側にコピーされることはなく、AがBに依存し、BがCに依存していても、AがCに依存するとは書き込まれません。関係が書かれていないことは「関係がない」ではなく「記録されていない」を意味します。

## マップでの関係の使われ方

- 何も選んでいないときは、ドメインの間の薄い弧が、両ドメインの概念どうしにある`depends_on`関係を向きごとに数えて示します。
- 概念にポインタを合わせたり選んだりすると、その概念自身が記述している関係だけが、相手の概念1つにつき1本の線で描かれます。**依存先**と**依存元**は先細りの線、**関連**は点線、**上位概念**は二重線です。
- 概念パネルの**依存先**と**依存元**は、`depends_on`だけから一覧を作ります。関連と上位概念のリンクは**その他の関係**に数えられます。

線の凡例の全体は、[マップの読み方](/guide/reading-the-map)を参照してください。

## エージェントでの関係の使われ方

MCPサーバは同じフロントマターからグラフについての問いに答えるので、エージェントはすべてのファイルを読む必要がありません。

- `find_backlinks`は、関係のキーや本文中のリンクを通じて、あるスラッグを指しているすべての概念を一覧にします。名前の変更や削除の前に呼び出してください。
- `path`を指定した`query_ontology`は、2つの概念の間の最短経路を返します。各ステップには、それをつないでいるキー（`via`）と、記録されていれば理由（`rationale`）が付きます。
- `neighbors`を指定した`query_ontology`は、ある概念のまわり1ステップ分を、向きと型で絞り込んで返します。
- `impact`または`blast_radius`を指定した`query_ontology`は、「これを変えると何に影響するか」に答えます。たどるのは宣言された`depends_on`関係だけです。構造は影響ではありません。
- `project_map`を指定した`query_ontology`は、プロジェクトのドメインとドメイン間の関係を一覧します。

書き込むには、`add_relations`に関係のリストを渡し、関係ごとに`from`、`to`、`type`（`depends_on`、`relates`、`contains`、`describes`、`domains`、`capabilities`、`elements`、`domain`のいずれか）、そして`why`を指定します。`remove_relation`は、デフォルトではプレビューだけを行い、`confirm: true`のときにだけ書き込みます。`replaceWith`を一緒に渡すと、関係を別の関係へ1回の書き込みで置き換えます。`broader`はまだ`add_relations`の型に含まれていません。エージェントは`patch_concept`に新しいリスト全体とファイルの`mtime`を渡して変更し、そのあと`validate_vault`を実行します。

マップでは、**関係を編集**で、MCPツールと同じチェックを通して関係を1つずつ書き込めます。[概念と関係を編集する](/guide/studio)を参照してください。

## ファイルが正本であり続ける

関係を追加すると、1つのファイルの1行が変わり、その変更はほかの変更と同じように`git diff`に表示されます。エージェントが書いた関係もあなたが書いた関係と同じ見た目なので、1回のレビューで両方を確認できます。
