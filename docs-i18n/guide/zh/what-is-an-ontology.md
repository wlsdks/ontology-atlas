# 什么是本体（Ontology）？

本体（ontology）是对某个领域的一份共享的书面描述：其中有哪些概念，每个概念属于什么类型，概念之间可以用哪些关系连接，以及这些词各自是什么意思。本章先讲本体的一般含义，再把它和分类体系、模式（schema）、知识图谱做比较，最后介绍 Ontology Atlas 用来描述代码库的本体。

## 一般意义上的本体

每个团队其实都已经有一个本体，只是通常没有写下来。大家说到“订单”“支付”“退款”时，默认指的是同一个意思，也都知道退款属于某个订单、结算依赖支付。问题往往出在两个人用同一个词指不同的东西，或者已经没人记得两个部分为什么连在一起。

把本体写下来，就是把这些约定说清楚。它由四部分组成：

- **概念**：有名字的事物，例如“订单”或“结算购物车”。
- **类型**：每个概念的类别。类型告诉你它是哪一类事物，以及它应当回答哪些问题。
- **关系**：概念之间带类型的连接，例如“属于”“依赖”或“描述”。关系有方向，也有含义，所以“A 依赖 B”和“A 与 B 有关”说的不是一回事。
- **约定的含义**：简短的定义，让人和程序以同样的方式理解每个概念和每条关系。

## 与相近术语的区别

这几个词的含义互有重叠，平时也常有人混用。本指南中，它们分别指：

- **分类体系**（taxonomy）是一个类别层级，每一项都挂在一个更宽泛的类别下面。它基本上只有一种关系：“是一种”。本体可以包含分类体系，但除此之外还有别的关系，例如依赖。
- **模式**（schema）定义数据的形状：一条记录有哪些字段，每个字段是什么类型。它说明数据怎样存储，而不是这个事物在你的业务里是什么意思。Atlas 也有模式，规定每个文件里有哪些字段，但模式并不是本体。
- **知识图谱** 是一组由关系连起来的具体事物。本体通常为知识图谱提供词汇，也就是有哪些类型、有哪些关系类型。简单地说，本体规定“可以有哪些种类的事物，它们之间可以有哪些关系”；知识图谱则是用这套词汇写下的具体事物和连接。在 Atlas 中，类型和关系类型就是这套词汇，你文件夹里的文件就是用它构建出来的图谱。

OWL、RDF 等形式化本体语言还加入了一套逻辑，程序可以据此推导出新的事实。Atlas 不做这种推理：它只保存人或智能体写下的内容，不会推断出没人写过的关系。

## 为什么代码库需要本体

代码能说明东西是怎么做出来的，却很少说明各个部分是干什么用的、哪些规则重要、为什么两个模块必须一起改。这些知识通常只存在于人的脑子里和过时的文档里。

编码智能体让这个缺口变得更大。智能体几分钟就能改动几十个文件，比人读得还快。如果没有一份大家共用的系统描述，每次智能体会话都得从零开始，每次审查也只能从一串改动文件的列表看起。代码库的本体给了双方同一个起点：智能体动手之前，先读取任务涉及哪些概念；人在改动完成之后，再核对这次改动影响了哪些概念。

## Atlas 使用的本体

Atlas 把本体保存在一个由 Markdown 文件组成的文件夹里，我们称之为本体文件夹，通常是你仓库中的 `atlas/`。一个概念就是一个文件。文件顶部的信息块（frontmatter）保存它的身份、类型和关系；下面的正文用平实的文字解释它。

共有五种类型：

| 类型 | 是什么 | 示例 |
|---|---|---|
| `project` | 这个文件夹所描述的产品或系统 | “面向小型零售商的网店” |
| `domain` | 长期存在的职责范围，即使重写代码也依然成立 | 订单、身份、计费 |
| `capability` | 系统能做的一件事，描述时不提具体代码 | 结算购物车 |
| `element` | 带有源码路径的具体实现部分 | 结算服务，`src/orders/checkout.ts` |
| `document` | 对其他概念作出解释或决定的文本 | 一份架构决策记录 |

关系写成 frontmatter 中的键：

- `domains`、`capabilities` 和 `elements` 列出项目、领域或能力包含的内容；`domain` 指明能力或元素所属的领域。
- `dependencies` 表示一个概念需要另一个概念（地图上显示为 **依赖**）。它有方向：反方向可以从另一端读出来，不必写两遍。
- `relates` 是一种松散的关联，没有方向，也不暗示因果。
- `describes` 把文档与它所解释的概念连接起来。
- `broader` 表示一个概念是另一个同类型概念下更具体的一种。地图上这条线标为 **上位概念**。
- `relation_notes` 为每条关系保存一句话，说明这条关系为什么成立。

每个概念还有一个 `uid` 和一个 `slug`：`uid` 是永不改变的永久标识符；`slug` 是它当前的可读地址，重命名时可能会变。

## 示例文件

下面是网店里的一个能力文件，在文件夹里就是这个样子：

```markdown
---
uid: 3f6c2a9e-8b41-4d7a-9c25-6e0f1b7d4a12
slug: capabilities/checkout
kind: capability
title: 结算购物车
description: 在一次支付授权之后，把购物车变成订单。
domain: domains/orders
elements: [elements/checkout-service]
path: src/orders/checkout.ts
dependencies: [capabilities/payment-authorization]
relation_notes: { capabilities/payment-authorization: "只有在支付服务商授权该金额之后，才会创建订单。" }
---

# 结算购物车

把当前购物车变成订单。不处理退款。
```

在地图上，这个文件会成为“订单”领域里的一个概念：一条线连到实现它的结算服务，另一条线连到它所依赖的支付授权。点击后一条线，会弹出一个小面板，显示写在 `relation_notes` 里的理由。

## Atlas 本体说明不了什么

文件夹里的一条关系只是一个声明，而不是证据。它表示有人写下了“结算依赖支付授权”，并不代表有人在运行时追踪过程序。缺少某条关系意味着“未知”，而不是“没有联系”。这样地图才是诚实的：它展示已经写下的内容，也让你看出哪里还没人写过。
