# Atlas 与代码图谱、Wiki、笔记应用和 CLAUDE.md 的比较

Ontology Atlas 把代码库的各个部分用来做什么、为什么这样设计，以经过人审阅的 Markdown 记录在仓库里，你和你的编码智能体读的是同一份记录。代码图谱类工具计算的是代码怎样搭建起来。Wiki 和笔记应用里的文字不知道代码什么时候变了。`CLAUDE.md` 和 `AGENTS.md` 写的是智能体要遵守的规则。本章把 Atlas 与这些工具逐一比较，也与知识图谱数据库比较，并说明什么时候其他工具才是更好的选择。

## 一览

| 工具 | 擅长 | 不包含 | 与 Atlas 配合 |
|---|---|---|---|
| 代码图谱、代码搜索 | 精确的结构：定义、调用、import | 某个部分用来做什么，以及为什么 | 概念引用代码路径；智能体两者都用 |
| 仓库 Wiki、文档站点 | 面向读者的长篇说明 | 带类型的关系；代码已变化的任何迹象 | 文件夹里的 Wiki 页面用哈希引用源文档 |
| Obsidian、Notion | 写作、随手记录、协作 | 与仓库或其 Git 历史的任何关联 | Obsidian 可以打开同一个文件夹 |
| `CLAUDE.md`、`AGENTS.md` | 智能体每次会话都会读取的规则 | 整个系统的地图 | Atlas 会读取它们，并能把其中的章节转成概念 |
| 图数据库、RDF 与 OWL | 海量数据、查询语言、推理 | 在 Git 审阅流程中的位置 | Atlas 不做推理，也不是数据库 |

## 代码图谱与代码智能工具

语言服务器、代码搜索和代码图谱索引都是从源码计算出来的。它们能精确回答“这个函数在哪里被调用”“哪些文件 import 了这个文件”，而且因为是根据代码重新生成的，所以始终是最新的。遇到这类问题，它们是更合适的工具，也比 Atlas 更快。

但它们说不出某个部分用来做什么、属于哪个产品边界、为什么两个模块必须一起改，或者哪些地方还没有人核实过。Atlas 把这些内容记录为由人写下或认可的概念和关系。概念在 `path` 中写明实现它的代码；在桌面应用中，如果这段代码在概念之后又被修改，地图就会把这个概念标为过时。Atlas 的 `infer_imports` 工具也会读取静态 import，但只把结果作为待审阅的候选返回，从不当作已认可的关系。

## 仓库 Wiki 与文档站点

长篇说明、新人上手资料，以及给代码之外的读者看的页面，适合放在 Wiki 或文档站点里。从仓库自动生成的 Wiki，内容是程序推断出来的，而不是团队定下来的。

Wiki 页面不知道它所描述的代码或文档什么时候变了，页面上的链接也没有可供程序沿着走的类型。在 Atlas 中，**资料库** 把源文档放在 `sources/`，把 Wiki 页面放在 `wiki/`。Wiki 页面引用每份源文档时都附上其内容的哈希，所以源文档一旦变化，你还没打开页面，它就已经被标记出来。`document` 概念可以用 `describes` 把一篇文字和它所解释的概念连起来。

## 笔记应用：Obsidian 与 Notion

Obsidian 擅长在本地 Markdown 中快速写作和建立链接，还有插件和移动应用。Notion 擅长团队共享的工作区和数据库。写每日笔记、在手机上随手记录或实时协作，请用它们。

两者都不了解你的仓库及其 Git 历史，所以笔记所描述的代码变了，笔记上也不会有任何提示。本体（ontology）文件夹是带 YAML frontmatter 的普通 Markdown，因此 Obsidian 可以打开同一个文件夹，你也可以在那里继续写。Atlas 会跳过名称以点开头的文件夹，所以从不读取 Obsidian 的 `.obsidian/` 设置。有两点限制：Atlas 按相对于文件夹根目录的路径解析 `[[...]]` 链接，而不像 Obsidian 那样按笔记名称解析，所以部分 Obsidian 链接在 Atlas 中无法解析；另外，Atlas 中的编辑是纯文本编辑。

Atlas 不与 Notion 同步。在桌面应用的 **资料库** 中使用 **从服务导入**，已连接的智能体会把 Notion 页面作为源文档复制到 `sources/notion/`。

## 智能体指令文件：CLAUDE.md 与 AGENTS.md

智能体每次开始会话时都会读取 `CLAUDE.md` 和 `AGENTS.md`。它们适合写构建命令、编码约定，以及智能体不能做的事。正因为每次都要读取，它们必须保持简短，所以装不下整个系统的地图，也记录不了哪段代码实现了哪项能力、这些又是什么时候变化的。

Atlas 通过三种方式与这些文件配合。由 Atlas 创建的本体文件夹自带一份 `AGENTS.md`，以及导入它的 `CLAUDE.md`，告诉智能体在扫描文件之前先询问 Atlas MCP 服务器。CLI 命令 `absorb` 会把你现有文件中的章节转成概念（[从代码构建第一张地图](/guide/from-your-repo)）。应用中的 **Harness** 标签页和下面的命令一样，只读取这些文件而不修改它们，并指出其中的问题，例如没有导入 `AGENTS.md` 的 `CLAUDE.md`，或超过 Codex 默认 32 KiB 上限的 `AGENTS.md`：

```bash
node ~/tools/ontology-atlas/cli/src/index.mjs agent-files --root .
```

把规则留在指令文件里，把含义放在本体文件夹中。

## 知识图谱数据库、RDF 与 OWL

Neo4j 这样的图数据库能存储大规模的图，并用查询语言回答许多用户和服务同时发来的临时查询。RDF 和 OWL 是用于跨组织共享数据、并借助推理机推导出新事实的标准。如果你有数以百万计的事实，或需要形式化推理，请用它们。

Atlas 不是数据库。它的图就是你文件夹里的文件，与代码一起在 Git 中审阅。它也没有查询语言：MCP 工具 `query_ontology` 只回答一组固定的问题，例如 `path`、`impact` 和 `blast_radius`。Atlas 不会推断出没有人写下的关系，不声称符合 RDF 或 OWL 规范，也不导出为这两种格式。frontmatter 是普通的 YAML，脚本可以直接读取。
