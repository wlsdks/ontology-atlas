# 选择概念：领域、能力与元素

构建代码库本体，就是决定什么该成为概念、它属于哪种类型。本章给出 Atlas 对每种类型使用的判断标准，解释为什么一个源文件不等于一个概念，并介绍上级概念的子项很多时该用的“一句话测试”。你的编码智能体（Claude Code、Codex、Cursor）在写入之前，也会通过 MCP 服务器读取同样的规则，因此人和智能体创建的概念遵循同样的形态。

## 按职责选择类型

选择类型要看这个概念在模型中承担什么职责，而不是看它的大小、所在文件夹或负责人。

| 类型 | 问问自己 | 示例 | 不是这样 |
|---|---|---|---|
| `project` | 它能否补全“这个系统之所以存在，是为了……”这句话，并为其余一切划定范围？ | “一个本地工作台，让产品的含义在人与智能体之间保持共享。” | “一个 TypeScript monorepo。” |
| `domain` | 它是否是一个长期存在的职责或问题边界，能把多项能力归为一组，并且即使重写代码也依然成立？ | “身份领域负责登录和账号访问策略。” | “`src/auth` 文件夹”或“认证团队”。 |
| `capability` | 它是否描述了系统能做的一件事，从外部可以观察到，而且不提是哪个模块在做？ | “登录后签发一个可撤销的会话令牌。” | “令牌控制器”或“登录工作流”。 |
| `element` | 它是否指出了一个承载某项能力的独立实现角色，并带有别人可以打开查看的依据？ | “JWT 签名器”，带 `path: src/auth/jwt-signer.ts`。 | 把 `src/auth/jwt-signer.ts` 当作名称。 |
| `document` | 它本身是不是一段文本，价值在于对另一个概念作出解释或决定？ | “ADR：本地优先的持久化。” | 一个因为有 README 就被归为文档的服务。 |

从上往下读这张表：交付的是什么，职责在哪里划分，系统能做什么，以及它是怎么做的。

文件夹、包、团队、路由、类名或 README 标题都只是线索，而不是概念。只有当你能为它写出一个不循环的定义，并说清它包含和不包含什么时，它才能成为领域或能力。名称里有动词不代表它就是能力，有名词也不代表它就是元素。

完整的判断标准，以及每种类型包含和不包含的内容，见 [Atlas 规范](https://github.com/wlsdks/ontology-atlas/blob/main/docs/ONTOLOGY-ATLAS-SPEC.md#2-the-five-authorable-node-kinds-and-reserved-reader-kind)。

## 一个文件不等于一个概念

最常见的错误，是打开一个目录，然后每个文件建一个元素。结果看上去像本体，实际上只是把目录列表复制进了图谱。Atlas 自己的仓库就曾经有一项能力挂了 92 个元素，和某个文件夹的 `ls` 结果一模一样。

路径是概念的依据，而不是概念本身。

- 按角色为元素命名：`jwt-signer`、`session-store`。
- 把位置写进 `path:`。
- 如果一个标题看起来像 `src/lib/auth/jwt.ts`，或者以源文件扩展名结尾，那它就是依据。MCP 服务器看到这种标题时会发出警告。
- 在类型文件夹下保持 slug 扁平：写 `elements/jwt-signer`，而不是 `elements/src/lib/auth/jwt`。写入概念时，路径形态的 slug 会直接被拒绝，否则两个同名文件可能悄无声息地变成同一个概念。

多个文件可以共用一个角色。如果你无法用一句话说清两个文件在角色上有什么不同，它们就是同一个元素；或者根本不是元素，只是某项能力的 `path`。

## 子项多并不是缺陷

一个概念可以有多少个子项，并没有上限。一个很宽的上级概念，只要每个子项都名副其实，就是正确的。而上限很容易被机械地满足：把一堆子项拆成“A 组”和“B 组”，数字是好看了，但什么都没有变得更清楚。

数量只是一个该问一问的信号。文件夹还在早期时，参考值大约是一个领域下 8 项能力、一项能力下 6 个元素。某种类型的上级概念达到十个或更多之后，Atlas 会改为和你文件夹自身的分布比较。

### 一句话测试

当一个上级概念的子项超过这个参考值时，对每个子项问一个问题：

> 你能否写出一句不循环的话，说明为什么这个子项不能与它的同级项互换？

- 如果能，就保持原样，哪怕它有三十个同级项。
- 如果不能，不要新增概念，而是去完善已有同级项的正文。

名称前缀相同只是提示你该往哪里看，并不是测试本身。

### 当三个或更多子项未通过时

如果有三个或更多子项未通过测试，说明缺了一个层级。在上级概念和这些子项之间添加一个概念，但必须同时满足以下全部条件：

1. 它以这些子项共有的某种行为命名。“其他”或“第 2 部分”不算名称。
2. 你能用一句话说明这种行为。
3. 它与自己的同级项相比，能通过一句话测试。
4. 你确实把这些子项移到了它下面。空的分组概念会被列为待删除。

只要有任何一条不满足，就什么都不要创建。

## 为每项能力提供依据

创建一项能力时，要在同一步里给它一个可以打开查看的东西：在 `path:` 中写一个实现入口，或者在 `elements:` 中至少写一个元素。两者都没有的能力，是一个无人能核实的说法。它仍然会写入，但会一直以 `capability_without_evidence` 的形式留在清理队列中，直到它指向某个东西为止。可以用 `query_ontology` 的 `maintenance_plan`，或 `node cli/src/index.mjs maintenance` 查看这个队列。

```markdown
---
uid: 9f6805c6-7f22-4ca8-8252-c0c2d06f3fad
kind: capability
slug: capabilities/token-issue
title: Token issuance
domain: domains/auth
path: src/auth/issue-token.ts
elements: [elements/jwt-signer]
---
```

`elements:` 只存放真实元素概念的 slug，从不存放文件路径。

## 规则只报告，不阻止

这些检查不会拒绝写入。不符合规则的概念依然会保存，只是响应里会带一条警告，或者清理队列里多出一行。如果一律阻止，只会教会智能体绕开工具。唯一的例外是路径形态的 slug：它破坏的是身份而不是含义，而且在创建概念时修正成本最低。
