# 从代码构建第一张地图

本章为你的仓库构建第一个代码库本体：你的代码所实现的领域、能力和元素，以及它们之间的关系。Claude Code 或 Codex 等编码智能体通过 MCP 读取代码并提出地图草案。由你来审查，只有你批准的内容才会被写入。

## 谁负责什么

Atlas 不会自己把代码变成含义。智能体读取代码，带着依据提出概念和关系，再把你接受的那些以 Markdown 形式写进本体文件夹。你的代码只会被读取，从不会被修改。

对仓库的扫描结果是依据，而不是答案。`analyze_repo_structure`、`index_project` 和 `infer_imports` 不写入任何内容。文件夹名或一行 import 只是智能体观察到的现象，还算不上领域、能力或依赖。

## 从应用开始

桌面应用提供三种开始方式。

**根据代码构建本体。** 开始卡片上的这个按钮会请你选择代码文件夹。Atlas 会显示它将在该代码文件夹内创建的 `atlas` 文件夹的路径（如果已有就复用），并等你按下 **创建**。随后它会与你的编码智能体开启一段对话，智能体读取代码，一次性写出第一张地图。每次写入都会征求你的批准。即使开启了 **自动批准**，智能体在绑定代码文件夹之前和完成地图之前仍会询问你。

**开始使用。** 当你打开一个还没有地图的文件夹时，地图上会出现一张卡片，带你完成几个步骤。在代码文件夹中，第一步是 **让智能体根据代码起草地图**。如果应用中已有可用的编码智能体，**交给智能体** 会把这条请求放进地图旁的智能体对话中，由你自己按下 **发送**。否则，**复制提示词** 会复制同样的请求，供你在终端里运行的智能体使用。后面的步骤会连接智能体，然后创建起步文档，或者让你手动开始。

**用本地模型从代码构建。** 在 macOS 应用中，地图旁的智能体面板里有 **从代码创建**。它需要在 **智能体**、**模型** 中设置一个本地模型，例如 Ollama、LM Studio 或 llama.cpp。选择一个代码文件夹后，预览会列出代码文件夹、审查后的改动将保存到哪里、所用的模型、模型地址，以及有多少文件符合条件。**运行** 只会把代码片段发送到那个本地地址。结果是一份拟议的文档改动列表。选中你想要的那些并应用即可。

## 从终端开始

有了 Atlas 的源码检出目录（见 [CLI](/guide/cli)）之后，在你自己的仓库中运行：

```bash
cd /path/to/your/repo
node ~/tools/ontology-atlas/cli/src/index.mjs init ./atlas
node ~/tools/ontology-atlas/cli/src/index.mjs bootstrap . --vault ./atlas
```

`init` 会创建 `atlas` 文件夹，其中包含五个起步文件、智能体配置 `.mcp.json` 和 `.codex/config.toml`，以及三个供 Claude Code 和 Codex 使用的起步技能：`atlas-review`、`atlas-grow` 和 `atlas-absorb`。起步文件只是格式示例，并不是对你产品的分析。

`bootstrap` 会扫描仓库并打印一份审查计划。它不写入任何内容，并以退出码 3 结束，表示仍需批准。在该仓库中重启你的智能体，然后在智能体里继续。

## 向智能体提什么要求

第一张地图要小。挑一个你想弄明白的行为，只就这一个行为提出要求。例如：

```text
为这个仓库构建第一张 Atlas 地图，聚焦于[一个行为，
例如接收订单]。

先调用 connection_info，确认本体文件夹和代码
仓库。读取 list_kinds 和已有的概念，避免
添加重复项。把起步文件当作示例，而不是事实。

阅读入口、它的条件和它的失败路径。写入之前先提出
一小批提议。对每个概念，给出一句定义、它包含和
不包含什么、实现它的文件，以及你未能核实的内容。
对每条关系，说明它为什么成立。

停下来，让我修正或批准这一批。然后只写入我
批准的内容，并运行 validate_vault。
```

第一轮有几个概念就够了。需要回答别的问题时再继续添加。

## 保存之前先审查

好的提议能让你针对某一条具体的说法提出异议。逐一检查每个概念和每条关系：

- **名称说明它做什么。** 只有文件夹名或库名，同事能获得的信息太少。
- **正文各部分齐全。** 一句定义、`## Includes`、`## Excludes` 和 `## Uncertainty`。缺少其中任何一项时，`validate` 会发出警告。
- **依据指向一个文件。** 能力或元素带有指向代码的 `path`。路径存在并不能证明解释正确，所以要去读一读。
- **关系成立。** 问问自己：把目标移除之后，这项能力是否仍然能工作。仅凭一条 import 并不能证明存在依赖。

批准你真正读过的那一批，再要求下一批。地图的形态稳定下来之后，智能体可以用 `connect_project_source` 把项目绑定到代码文件夹，并用 `finalize_project_meaning` 记录结果。写入成功仍然不等于含义被接受：提交之前请先阅读 diff。

## 复用 CLAUDE.md 和 AGENTS.md

你的智能体指令文件往往已经描述了这个代码库。`absorb` 会把它们转成概念：

```bash
node ~/tools/ontology-atlas/cli/src/index.mjs absorb CLAUDE.md AGENTS.md --vault ./atlas
```

默认情况下它只打印计划。加上 `--write` 后，它会把策略和规则部分保存为 `document` 概念，把原文件备份为 `.pre-absorb.bak`，并把原文件改写成一个简短的指引，保留它没有吸收的部分。架构部分只会被提议，从不会自动写入。智能体也可以通过 MCP 工具 `absorb_document` 做同样的事。

`init` 还会打印一小段文字，供你粘贴到自己的 `CLAUDE.md` 或 `AGENTS.md` 中。它告诉以后的智能体会话：本体已经存在，以及什么时候该去读它。Atlas 不会替你编辑这些文件。

如果文件夹里已经有不在地图上的 Markdown 文档，**开始使用** 卡片会增加一个步骤：**用我的文档生成地图**。
