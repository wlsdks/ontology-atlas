name: design-directions
description: Sketch 3–4 structurally different ways a UI change could go — in text, before writing any code — and have the owner pick one. Use before implementing any non-trivial visual, layout, interaction, or motion change, and before convening the design council. This is the cheap step that prevents building the wrong shape: the model has a persistent default it returns to unless a concrete spec exists, and generic redirection ("cleaner", "not like that") only swaps one default for another. Skip for value-level edits inside an already-decided shape — a token swap, a copy fix, a spacing nudge.

# /design-directions — 짓기 전에 갈래를 그린다

## 왜 이게 필요한가 — 근거는 두 개다

**① 모델에는 늘 되돌아가는 기본 스타일이 있고, 더 좋은 모델을 써도 사라지지
않는다.** Anthropic 공개 문서가 프론티어 모델의 프론트엔드/디자인 기본값을
명시적으로 기록한다 — 그리고 결정적인 문장은 이것이다:

> 일반적인 지시("크림색 쓰지 마", "깔끔하고 미니멀하게")는 다양성을 만들지
> 못하고 **다른 고정 팔레트로 옮길 뿐이다.**

즉 *"이거 말고"* 는 방향을 바꾸지 않는다. **무엇을 어떻게 하라고 구체적으로
적어 준 것만 바꾼다.** 게다가 출력을 무작위로 흔들던 손잡이(`temperature`)가
프론티어 모델에서 없어져서, 그 문서가 남긴 방법은 하나뿐이다 — **모델이 먼저
여러 방향을 내놓고, 사람이 그중 하나를 고른다.**

**② 학술 근거가 같은 처방을 낸다.** Dow, Glassco, Kass, Schwarz, Schwartz &
Klemmer, *"Parallel Prototyping Leads to Better Design Results, More Divergence,
and Increased Self-Efficacy"* (ACM TOCHI 2010). **여러 개를 한꺼번에 만들어 놓고
피드백을 받는 쪽(parallel)이, 하나씩 만들고 매번 피드백을 받는 쪽(serial)보다
결과 품질 · 갈래의 다양함 · 「내가 할 수 있다」는 자신감 셋 다에서 나았다** —
의견이 아니라 실험으로 보인 것이다.

`/design-council` 은 구조상 serial 이다 — R1 비평 → R2 교차비평 → R3 평결이
전부 **이미 만들어진 하나**를 평가한다. 이 스킬은 그 앞에 붙어서, 심사할 것을
하나로 좁히기 전에 갈래를 여러 개 벌려 놓는 단계다.

**③ 이 저장소에서 실제로 그 비용을 냈다.** 2026-08-03 PO 카운슬은 액션 타일과
생성 컴포저를 두고 다섯 자리가 두 라운드를 돌았다. 나온 결론은 「7칸을 3층으로」와
「중앙 모달을 부모 옆으로」였는데, **그 둘은 처음에 세 줄로 그릴 수 있는
갈래였다.** 카운슬이 비싼 게 아니라 **갈래를 안 그리고 하나를 지어 버린 것**이
비쌌다.

## 누가 갈래를 그리는가 — 짓는 쪽이 아니다

**이 단계의 소유자는 `chief`(카운슬 팀장) 다.** 실제로 코드를 고치는 유일한
자리인 `design-guardian` 이 아니다.

지을 사람이 선택지를 직접 만들면 **선택지가 자기가 짓고 싶은 쪽으로 기운다** —
나머지 셋은 들러리가 되고, 그러면 이 절차는 갈래를 벌리는 게 아니라 이미 정해
놓은 변경을 정당화하는 요식행위가 된다. 이 저장소가 카운슬을 만든 이유와 정확히
같은 실패다(*"자기가 만든 것을 자기가 통과시키면 안 된다"*).

`chief` 가 갈래를 그리고, 사람 소유자가 그중 하나를 고르고, 그다음에 구현자가
짓는다.

## 이 제품에서 「방향」은 팔레트가 아니다

⚠️ **위 Anthropic 문서에 나오는 예시(배경 hex / 강조색 hex / 서체)를 그대로
가져오지 마라.** 이 앱은 색을 이미 정해서 못박아 뒀다(이 저장소는 그렇게 못박아
둔 규칙 묶음을 「헌장」이라고 부른다) — 다크 한 가지 · 무채색 + 인디고
하나(`#5e6ad2`) · 그라디언트/글로우/글래스 금지(`.claude/rules/design.md` ·
`forbidden.md`). 색 조합을 갈래로 물으면 **이미 답이 나와 있는 것을 다시 묻는
것**이고, 넷 중 셋은 반려될 걸 알면서 그리는 셈이다.

여기서 실제로 갈래가 갈리는 지점은 넷이다. 이 문서는 그 지점 하나하나를
**축**이라고 부른다 — 갈래끼리 서로 달라질 수 있는 기준이라는 뜻이다.

| 축 | 갈래가 다르다는 것은 |
|---|---|
| **위계** | 이 화면에서 **무엇이 가장 먼저 눈에 들어오는가**가 다르다 |
| **배치·밀도** | 같은 요소들이 **어떻게 묶이고 몇 줄인가**가 다르다 |
| **상호작용 모델** | 같은 일을 **모달/인라인/팝오버/제자리** 중 어디서 하는가 |
| **모션이 나르는 정보** | 무엇이 움직여서 **무엇을 말하는가**(그냥 예뻐 보이려는 움직임은 갈래가 아니다) |

한 갈래가 다른 갈래와 **이 넷 중 하나 이상에서 달라야** 갈래다. 구조는 같은데
값만 다르면 그건 갈래가 아니라 값 조정이고, 이 스킬이 다룰 일이 아니다.

## 언제 돌리나

**돌린다** — 한눈에 답이 보이지 않는 시각/레이아웃/상호작용/모션 변경 **전에**,
그리고 `/design-council` **전에**. 카운슬은 이미 지어진 것을 심사하는 자리고,
이건 무엇을 지을지 고르는 자리다. 순서가 뒤집히면 카운슬이 갈래 찾기를 대신하게
되고, 그게 오늘 실제로 일어난 일이다.

**안 돌린다** — 이미 정해진 형태 **안에서 값만 바꾸는 편집**: 토큰 교체, 문구
수정, 간격 조정, 오타. 여기에 갈래를 그리는 것은 이 저장소가 경계하는 「절차를
밟는 시늉」(process theater) 이다.

**애매하면 물어라, 그리는 데 5분이다.** 이 스킬의 값어치는 싸다는 데 있다 —
비싸지면 존재 이유가 사라진다.

## 규율 — 이 단계가 싸야 이 단계가 살아남는다

1. **코드를 쓰지 않는다.** 갈래는 **글과 ASCII 스케치**로만 그린다. 빌드도
   스크린샷도 없다. 하나라도 미리 구현해 버리면 그 갈래가 남은 셋을 이긴다 —
   이미 만든 게 아까워서다.
2. **3~4개.** 둘은 이지선다라 갈래가 아니고, 다섯은 고르는 것 자체가 일이 된다.
3. **하나는 「지금 그대로」여야 한다.** 지금 화면이 후보에 없으면 이 절차는
   변경을 정당화하는 요식행위가 된다. 「안 바꾼다」가 이기는 결과도 정상적으로
   나올 수 있어야 한다.
4. **각 갈래에 「무엇이 사실로 드러나면 이 갈래가 틀린 것인가」를 같이 적는다.**
   이게 없으면 그냥 취향 투표다.
5. **금지 규칙을 어기는 갈래는 아예 그리지 않는다.** 꼭 그려야겠으면
   `forbidden.md` 의 금지를 푸는 요청을 따로 올린다 — 갈래 안에 몰래 섞지 않는다.
6. **사람 소유자가 고른 하나만 짓는다.** **둘을 합쳐서 짓지 않는다** — 합치면
   아무도 고르지 않은 셋째 형태가 화면에 나온다(PO 카운슬의 같은 규칙).

## 출력 형식

```md
## 방향 — <무엇을 바꾸려는가>

**지금 이 화면의 일**: <한 문장. 못 쓰면 아직 디자인이 시작 안 된 것이다>
**갈리는 축**: 위계 / 배치·밀도 / 상호작용 모델 / 모션 중 무엇인가

### A. 지금 그대로
<현행을 한 문단. 무엇이 이미 되고 있는지 정직하게>
**이게 이기는 조건**: <…>

### B. <이름 — 형용사가 아니라 구조를 말하는 이름>
```
<ASCII 스케치 — 실제 치수를 알면 적는다>
```
**바뀌는 것**: <위 네 축 중 무엇이 어떻게>
**대가**: <무엇을 잃는가. 없으면 갈래를 잘못 그린 것이다>
**이게 틀렸다면 보일 것**: <…>

### C. … / D. …

**실측이 이미 말하는 것**: <재 본 수치가 있으면. 없으면 "없음">
**내 추천과 이유**: <하나. 고르는 것은 소유자다>
```

## 고른 뒤

1. 고른 갈래를 **한 줄로 요약해 적어 둔다** — 다음 사람이 그것만 읽고도 같은
   것을 짓게.
2. 그 한 줄대로 구현한다. **고르지 않은 갈래는 버리지 말고 기록에 남긴다** —
   나중에 되돌릴 때 처음부터 다시 그리지 않기 위해서다.
3. 되돌리기 어렵거나 비싼 변경이면 그때 `/design-council` 을 부른다. 카운슬은
   **이미 고른 갈래를 심사**하지, 갈래를 대신 고르지 않는다.
4. 구현 뒤 `/design-audit`(재서 확인) · 움직임이 걸리면 `/motion-verify` ·
   화면 폭에 따라 레이아웃이 바뀌는 자리가 걸리면 `/responsive-sweep`.

## 이 스킬이 실패하는 방식

| 실패 | 어떻게 알아채나 |
|---|---|
| 갈래가 사실은 하나다 | 넷이 위 네 축 어디에서도 안 다르다 — 값만 다르다 |
| 지금 화면이 후보에 없다 | 「지금 그대로」 항목이 비었거나 들러리로 적혀 있다 |
| 갈래에 잃는 것이 없다 | 전부 좋기만 하다면 아무것도 안 재 본 것이다 |
| 이미 지어 놓고 그린다 | 코드가 먼저 있으면 이건 사후 정당화다 |
| 합쳐서 짓는다 | 아무도 고르지 않은 형태가 화면에 나온다 |
