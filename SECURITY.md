# Security

## Reporting a vulnerability

Report privately through **[GitHub Security Advisories](https://github.com/wlsdks/ontology-atlas/security/advisories/new)** — not a public issue, not a pull request.

Please include what you did, what you expected, and what happened instead. If a
proof of concept touches a real vault, describe it rather than attaching the
vault — this project's whole premise is that your files stay yours.

There is one maintainer, so expect a first reply in days rather than hours.

## What this project is, in security terms

Ontology Atlas is **local-first**. The app reads and writes Markdown in a folder
you pick, on your own disk. There is no backend, no account, no telemetry, and
nothing is transmitted anywhere unless you explicitly ask for it. Most of the
usual web attack surface does not exist here because the server does not exist.

That shifts the interesting questions to three places.

**The desktop app's native bridge.** The macOS shell (Tauri) is what lets the interface
(a WebView) touch your disk at all. Its window is granted a deliberately short list of
permissions — broad filesystem, shell, HTTP, and opener grants are refused by
`pnpm desktop:check`, and adding one requires naming it in an allowlist with a
reason. If you find a path that reaches beyond the folder you chose, that is a
vulnerability and we want to hear about it.

**The update path.** Updates are signed with a key that is separate from Apple's
certificate: Apple's signature says *who built it*, ours says *this update package
is really ours*. The app verifies our signature before it replaces anything, so an
update that we did not sign is refused even if it arrives from our own release
page. A way to make the app accept an unsigned or substituted package is a
vulnerability.

**Release credentials.** This repository is public and its release workflow holds
Apple signing and notarization credentials. See below.

## How release credentials are protected

Secrets live in GitHub Actions and **cannot be read back by anyone, including the
maintainer** — only replaced. They are never in the repository, so a clone does
not carry them.

The contribution model is what keeps them out of reach:

- **External contributions arrive as pull requests from forks.** GitHub does not
  pass secrets to workflows triggered by a fork, so a pull request that modifies
  CI cannot read them.
- **`pull_request_target` is never used.** That trigger runs a fork's code *with*
  the base repository's secrets, and it is the usual way open-source projects lose
  credentials. `tests/contract/security/workflow-security.contract.test.ts` fails the build
  if it ever appears.
- **Workflows triggered by `pull_request` reference no secrets at all** — enforced
  by the same contract, which also makes every workflow name each secret it reads:
  no `toJSON(secrets)`, no `secrets[...]`, no `secrets: inherit`.
- **Signing credentials are referenced only by the release workflow**, which
  starts only from a manual dispatch on `main`. Its first job holds no secrets: it
  requires the dispatch to come from `main` and the requested tag to point at
  `main`'s current head before any signing job starts.
- **Untrusted strings never reach a shell.** Pull request titles, bodies, and
  branch names are chosen by whoever opened the fork; interpolating them into a
  `run:` block is remote code execution. The contract test blocks the known
  fields and keeps workflow inputs out of scripts. Commit SHAs and numbers are
  generated by GitHub and are safe.
- **Publishing a release waits for a human.** The workflow builds a draft; a
  reviewer installs it on a real Mac and approves before anything becomes public.
- The default `GITHUB_TOKEN` is read-only, force pushes and branch deletion are
  blocked on `main`, and workflows on fork pull requests require maintainer
  approval before they run.

**The remaining risk is write access.** Anyone who can push a branch can change a
workflow that runs on push, and therefore can reach the secrets. This is why
external contributions stay on forks. If maintainers are added later, that
assumption changes and this document should change with it.

## Dependency installs

The root, `mcp/` and `cli/` each have their own `pnpm-workspace.yaml`, so each
folder carries the same three install settings. They need pnpm 10.26 or later;
`packageManager` in each folder's `package.json` pins the same version, and
every CI job activates that version through Corepack.

- **`minimumReleaseAge: 10080`.** pnpm will not resolve a version published
  less than seven days ago, so a compromised release has a week to be found and
  pulled before it can enter a lockfile here. An install from the committed
  lockfile (`pnpm install --frozen-lockfile`) resolves nothing and is not
  affected.
- **`trustPolicy: no-downgrade`.** pnpm refuses a version published with less
  trust evidence (provenance or a trusted publisher) than an earlier version of
  the same package, the usual mark of a release made from a stolen token rather
  than the project's own pipeline.
- **`blockExoticSubdeps: true`.** A transitive dependency must come from the
  registry; one that points at a Git repository or a tarball URL is refused.

pnpm checks a locked version again whenever it resolves, for example on
`pnpm add`, so the root file carries exact excludes for versions that were
already locked when these settings arrived. `mcp/` and `cli/` need none.

| Exclude | Setting | Why | Remove |
|---|---|---|---|
| `icu-minify@4.15.2`, `use-intl@4.15.1` | `minimumReleaseAgeExclude` | Locked before the cool-down; younger than seven days | After 2026-11-19 11:17 UTC |
| `@eloqnt/config@0.1.2`, `@eloqnt/format-json@0.1.1`, `@eloqnt/format-po@0.1.2` | `minimumReleaseAgeExclude` | Locked before the cool-down; younger than seven days | After 2026-11-22 14:13 UTC |
| `eslint-import-resolver-typescript@3.10.1` | `trustPolicyExclude` | A 3.x maintenance release published by the same maintainer account after 4.x had started carrying provenance | When the direct development dependency moves to 4.x |
| `semver@6.3.1` | `trustPolicyExclude` | A 6.x maintenance release published from an npm CLI maintainer's own account, after 7.x releases came with provenance from the npm CLI team's release automation; `@babel/core`, `eslint-plugin-import` and `eslint-plugin-react` require 6.x | When nothing locked requires 6.x |

A trust exclude says this exact version was checked and is accepted; it never
names a whole package.

### An urgent security bump

When the fix for a published advisory is younger than seven days, name that
exact version in `minimumReleaseAgeExclude` in the `pnpm-workspace.yaml` of the
folder whose lockfile takes it. Install, commit the lockfile, and name the
advisory in the same pull request. Remove the entries once the version is seven
days old. Naming the version rather than the package keeps every later release
of that package under the cool-down.

A package published as a family needs every sibling it pins at that exact
version, each listed exactly. A framework package that pins its own `@scope/env`
and eight platform binaries published together fails on the first sibling
when only the framework is listed, and a pattern such as `@scope/*@1.2.3` is
rejected because a name pattern cannot carry a version. Each sibling is a line
of its own, `name@version`, scoped names in quotes.

`npm view <package>@<version> dependencies optionalDependencies` lists the
siblings to name; pnpm names the next missing one if any is left out.

## Supported versions

Only the latest release. This project is pre-1.0 in practice even where the
version number says otherwise; fixes go forward, not backward.
