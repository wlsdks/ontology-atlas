# Security

## Reporting a vulnerability

Report privately through **[GitHub Security Advisories](https://github.com/wlsdks/ontology-atlas/security/advisories/new)** — not a public issue, not a pull request.

Please include what you did, what you expected, and what happened instead. If a
proof of concept touches a real vault, describe it rather than attaching the
vault — this project's whole premise is that your files stay yours.

There is one maintainer, so expect a first reply in days rather than hours.

## What this project is, in security terms

Ontology Atlas is **local-first**. The app reads and writes Markdown in a folder
you pick, on your own disk. There is no backend, no account, no telemetry, and
nothing is transmitted anywhere unless you explicitly ask for it. Most of the
usual web attack surface does not exist here because the server does not exist.

That shifts the interesting questions to three places.

**The desktop app's native bridge.** The macOS shell (Tauri) is what lets the web
layer touch your disk at all. Its window is granted a deliberately short list of
permissions — broad filesystem, shell, HTTP, and opener grants are refused by
`pnpm desktop:check`, and adding one requires naming it in an allowlist with a
reason. If you find a path that reaches beyond the folder you chose, that is a
vulnerability and we want to hear about it.

**The update path.** Updates are signed with a key that is separate from Apple's
certificate: Apple's signature says *who built it*, ours says *this update package
is really ours*. The app verifies our signature before it replaces anything, so an
update that we did not sign is refused even if it arrives from our own release
page. A way to make the app accept an unsigned or substituted package is a
vulnerability.

**Release credentials.** This repository is public and its release workflow holds
Apple signing and notarization credentials. See below.

## How release credentials are protected

Secrets live in GitHub Actions and **cannot be read back by anyone, including the
maintainer** — only replaced. They are never in the repository, so a clone does
not carry them.

The contribution model is what keeps them out of reach:

- **External contributions arrive as pull requests from forks.** GitHub does not
  pass secrets to workflows triggered by a fork, so a pull request that modifies
  CI cannot read them.
- **`pull_request_target` is never used.** That trigger runs a fork's code *with*
  the base repository's secrets, and it is the usual way open-source projects lose
  credentials. `tests/contract/workflow-security.contract.test.ts` fails the build
  if it ever appears.
- **Workflows triggered by `pull_request` reference no secrets at all** — enforced
  by the same contract.
- **Signing credentials are reachable only from the tag-triggered release
  workflow**, and pushing a tag requires write access.
- **Untrusted strings never reach a shell.** Pull request titles, bodies, and
  branch names are chosen by whoever opened the fork; interpolating them into a
  `run:` block is remote code execution. The contract test blocks the known
  fields. Commit SHAs and numbers are generated by GitHub and are safe.
- **Publishing a release waits for a human.** The workflow builds a draft; a
  reviewer installs it on a real Mac and approves before anything becomes public.
- The default `GITHUB_TOKEN` is read-only, force pushes and branch deletion are
  blocked on `main`, and workflows on fork pull requests require maintainer
  approval before they run.

**The remaining risk is write access.** Anyone who can push a branch can change a
workflow that runs on push, and therefore can reach the secrets. This is why
external contributions stay on forks. If maintainers are added later, that
assumption changes and this document should change with it.

## Supported versions

Only the latest release. This project is pre-1.0 in practice even where the
version number says otherwise; fixes go forward, not backward.
