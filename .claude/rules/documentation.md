# 문서 유지 규칙

## 원칙

**문서를 안 고치면 이 프로젝트는 굴러가지 않는다.** 코드만 고치고 문서를 그대로 두면 안 된다. 이 프로젝트는 AI 가 세션을 바꿔 가며 계속 작업하는데, 세션이 끝나면 대화 기록은 사라지고 문서만 남는다. 다음 세션이 읽을 수 있는 것은 문서뿐이다.

## 코드-문서 쌍

**표는 `.claude/rules/git.md` 로 옮겼다** — 상주 규칙이라 코드를 고치는 사람에게
실린다. 이 파일은 `.md` 를 열 때만 실려서, 짝을 빠뜨릴 사람에게는 도달하지
않았다.

## CI 가 문서에 대해 검사해도 되는 것 (2026-08-01 확정)

> **기계가 만들 수 있는 것만 검사한다. 사람이 판단해서 쓴 문장은 검사하지 않는다.**

이 저장소는 반대로 해 봤고 실패했다 — `check-package-contracts.test.mjs` 가
3,419줄 · 단언 2,126개였는데 **1,915개(90%)가 「README 에 이 문장이 그대로 있는가」**
를 확인하는 것이었다. 이렇게 문장을 못박아 두면(핀) 두 방향으로 다 틀린다.
도구 동작이 바뀌었는데 문서를 안 고치면 문장은 그대로니까 **통과**해 버리고,
문서를 더 나은 표현으로 고치면 내용이 맞는데도 **테스트가 실패한다.** 실제로
같은 날, 볼트를 다시 만들면서 사라진 노드를 그대로 인용하는 문장이 문서에
남았는데 그 1,915개 중 아무것도 잡지 못했다. 배경과 웹 조사 근거:
`docs/DECISIONS.md` 2026-08-01.

문서에 대한 새 검사를 만들 때는 아래 셋 중 하나여야 한다.

| 갈래 | 어떻게 하나 | 이 저장소의 것 |
|---|---|---|
| 생성한 뒤 대조 | 코드에서 문서 내용을 **다시 만들어** 커밋돼 있는 파일과 비교한다 | `pnpm docs:surface:check` — 돌아가는 MCP 서버에 `tools/list` 를 물어 `docs/.generated/mcp-surface.json` 을 만들고 커밋된 것과 비교한다. 덤으로, 등록된 도구·커맨드 이름이 README 에 다 나오는지도 본다 |
| 가리키는 대상이 실재하는가 | 문서가 가리키는 것이 진짜 있는지만 본다 | `pnpm docs:links` (깨진 링크 + 문장이 인용하는 파일 경로) · `assertPnpmScriptsExist` (문서에 적힌 `pnpm ...` 명령이 실재하는가) |
| 기댓값을 코드에서 뽑아 대조 | 기댓값을 사람이 적지 않고 **코드에서 계산해** 비교한다 | enum 전체 목록 · 공개 계약의 개수 · 버전이 서로 맞는가 |

**하지 말 것**: 사람이 쓴 문장 하나를 `assert.match` 로 못박기. 금지어를 손으로
하나씩 등록해 두는 목록(새 항목을 안 더하면 아무 신호 없이 무력해지고, 더하려면
사람이 계속 잡일을 해야 한다). 볼트 노드 수를 세는 검사(`AGENTS.md` 의
「no document writes the number」와 정면으로 부딪힌다 — 문서에는 숫자가 아니라
그 숫자를 뽑는 명령을 적는다).

**새 문서 검사는 `docs/DEVELOPMENT-CHECKS.md` 에 등재하고 `README.md` 의 명령
목록에도 넣는다.**

## 자주 하는 실수

- 구현만 하고 CHANGELOG 에 안 적기 → 리뷰에서 지적받는다
- 설계 결정을 대화로만 남기기 → 세 세션쯤 지나면 왜 그렇게 했는지 아무도 모른다
- dogfood 볼트의 capability / element 슬러그가 실제 파일과 어긋난 채 방치되기
- **문서가 이미 사라진 파일을 계속 인용하기** → `pnpm docs:links` 가 잡는다.
  볼트를 다시 만들었거나 문서를 옮긴 PR 에서는 반드시 돌린다

## Rule of Thumb

> "미래의 나와 AI에게 보내는 편지라고 생각하고 써라."

코드를 읽지 않고도 "이 프로젝트가 뭘 하는지, 어떻게 굴러가는지, 왜 이렇게 만들어졌는지"를 알 수 있어야 한다.
