# /po-pass — 매일 쓰는 경로. 사고는 여기서 났다.

카운슬(다섯 자리를 다 부르는 심사)은 드물게 열린다. **작업의 대부분은 혼자 쓰는
이 패스 하나로 지나간다** — 그리고 2026-07-27 사고는 카운슬이 아니라 **여기서**
났다. 한 패스가 채점표에서 0점이면 빌드 불가라고 못 박아 둔 두 항목에 "없음"을
쓰고, 스스로 `Build and verify` 판정을 내고, 그대로 출시됐다. 아무도 부르지 않는
카운슬은 그걸 못 잡는다. 이 스킬이 그 경로를 지킨다.

## 0. 먼저 결정 원장을 읽는다

**결정 원장은 `docs/DECISIONS.md` 파일 하나다** — 지금까지 내린 결정과 그때 졌던
반대 의견을 시간순으로 쌓아 둔 문서. 거기서 **같은 화면 · 같은 질문에 대해 전에
내린 결정**을 찾는다.

- 있으면 → 이 패스는 그 기록을 ① 여전히 유효하다고 **인용**하거나 ② 이유를 대고
  **뒤집는다**. 말없이 다시 결정하지 않는다.
- 그 기록의 **반증 조건**(그때 진 쪽이 사실은 옳았다면 나중에 무엇이 보일지를
  미리 적어 둔 문장)이 **이미 실제로 보였는지** 확인한다. 보였으면 그때 진 쪽이
  이긴 것이고, 이 패스는 그 사실에서 출발한다.

## 1. 현상과 문제를 갈라 쓴다

순서는 **관찰된 현상 → 사용자 문제 → 성공 조건 → 해법 → 구현**이다. 그런데
순서만으로는 가장 흔한 실패를 못 막는다 — **현상을 사용자 말투로 옮겨 적고 그걸
문제라고 부르는 것.** 세 시험을 통과해야 문제다:

1. **차이 시험** — 문제 문장에서 현상을 지워라. 남는 것이 ① 누가 ② 어느 순간에
   ③ 결정 · 이해 · 신뢰 · 핸드오프(다음 사람이나 에이전트에게 일을 넘기는 것)
   중 무엇을 잃는지를 여전히 말하는가?
2. **제2 관측 시험** — 이 문제가 진짜 있다면 **화면에서 본 것 말고 또 무엇이
   보이겠는가?** (이탈 · 재시도 · 질문 · 에이전트 실패 로그 · 지원 요청) 두 번째로
   확인할 곳을 못 대면, 같은 말을 다시 쓴 것이거나 확인할 방법이 없는 뭉뚱그린
   말이다. 이 시험이 "틀렸다면 무엇이 보일 것인가"에 대한 답을 겸한다.
3. **해법 독립 시험** — 해법이 바뀌어도 문제 서술이 말이 되는가. 여기서 쓰면
   안 되는 말은 **화면 이름**이 아니라 **네가 하려는 변경에서 끌어온 말**이다
   (컴포넌트 · 라이브러리 · 패턴 이름).

하나라도 통과 못 하면 Problem insight 는 **최대 2점**이고, 점수를 매기기 전에
문제를 다시 쓴다.

## 2. 패스를 쓴다

`docs/PRODUCT-OWNER-OPERATING-SYSTEM.md` 의 **Fast PO Pass** 템플릿을 읽고 그대로
채운다 — 기억으로 바꿔 쓰지 않는다. 최소한 이 여덟이 들어간다: 관찰된 현상 ·
사용자 문제 · 대상과 모먼트 · 현재 대안 · 온톨로지 가치 · 에이전트 가치 ·
단순화 · 검증.

## 3. 여섯 항목을 스스로 채점한다 — 0 · 2 · 4점 기준 문장을 인용하면서

같은 문서의 **PO Quality Rubric**(여섯 항목 · 24점 만점 채점표) 을 읽고, 각 항목의
0점 · 2점 · 4점이 무슨 뜻인지 적힌 문장을 **그대로 인용한 뒤** 점수를 준다.
기억으로 채점하지 않는다.

카운슬이 열리면 항목마다 점수를 매길 수 있는 자리가 하나로 정해져 있다. 혼자
쓰는 패스에서는 네가 전부 매기지만, 아래 표는 「이 항목은 원래 누구 몫인가」를
알려 준다.

| 항목 | 카운슬이 열릴 때 이 항목을 맡는 자리 |
|---|---|
| Problem insight · User moment | 근거 |
| Differentiation | 해자 |
| Ontology value · Agent value | 지킴이 |
| Verification | 결 |

**"해당 없음"은 0점이지 면제가 아니다.** 특히 온톨로지 가치 · 에이전트 가치를
"없음"으로 선언하는 것은 **네가 스스로 빼 줄 수 있는 게 아니다** — 그 면제가
타당한지 판단하는 건 지킴이 자리의 일이고, 판단시키려면 카운슬을 열어야 한다.
이 한 문장이 2026-07-27 사고를 막는 지점이다.

## 4. 소집 여부를 선언한다

**필수 소집** — 다음 중 하나라도 해당하면 여기서 멈추고 `/po-council` 을 부른다:

- 합계 **18/24 미만**
- **Problem insight · Ontology value · Agent value · Verification 중 0점**
- 사용자가 보는 화면(라우트)을 새로 만들거나 없앰
- 밖에서 쓰는 약속을 바꿈 — MCP 도구 시그니처 · CLI 명령 · vault 스키마
- 방향 · 포지셔닝 · 낯선 사람이 처음 읽는 문구
- 첫 공개 릴리스처럼 **한 번밖에 못 쓰는 첫인상**을 쓰는 일
- 소유자가 요청

**소집 안 함** — 18점 이상이고 0점짜리 치명 항목이 없고 위 목록에 하나도 안
걸리면, 판정을 내고 진행한다.

**절대 안 함** — 기계적 작업(오타 · 의존성 버전 올리기 · CI 설정 · 테스트 픽스처 ·
lint 설정). 여기에 카운슬을 부르는 것이 PO OS 가 경고하는 「절차를 위한
절차」(process theater) 다.

## 5. 판정과 기록

판정은 넷 중 하나: `Do not build` · `Investigate first` · `Shape a slice` ·
`Build and verify`.

위 필수 소집 목록에 하나라도 걸린 변경이면 **`docs/DECISIONS.md` 에 기록을
남긴다.** 라우트를 새로 만들거나 없앤 경우와 밖에서 쓰는 약속을 바꾼 경우에는
`pnpm decisions:check` 가 이걸 강제한다 — 기록 없이는 통과하지 못한다.

```md
**관찰된 현상**: […]
**사용자 문제**: […]
**현상↔문제 판별**: 차이 [통과/실패] · 제2 관측 [채널: …] · 해법 독립 [통과/실패]

**대상과 모먼트** · **현재 대안** · **온톨로지 가치** · **에이전트 가치** ·
**단순화** · **검증**: […]

**자가 채점**: Problem insight N · User moment N · Differentiation N ·
Ontology value N · Agent value N · Verification N = **N/24**
(치명적 0: 없음 / <행>)

**소집**: 필요 없음 / **필요 — 사유: <트리거>** → `/po-council` 호출

**판정**: Do not build / Investigate first / Shape a slice / Build and verify
```
